## 0. 本仓的测试哲学(不是通用软件工程,是这个仓库付过学费的)

### 0.1 三条铁律

| 铁律 | 出处 | 含义 |
|---|---|---|
| ⭐ **守卫必须验证能真的失败** | `feedback-verify-guard-can-fail` | 写完守卫**故意注入违规**看它变红。踩过:掏空抽象层核心函数,测试仍全绿 = 假保证 |
| **别信自述,看真实数据** | `feedback-dont-guess-look-at-real-data` | 不靠读代码脑补,靠跑、靠查库、靠离线脚本 |
| **不接受「看着成功实际没做」** | 可靠性纲领 | 一半守卫为此而写 |

### 0.2 三个已踩过的验证陷阱(`../../x/HANDOFF-refactor.prompt.md` §7)

1. **用 Python 改含中文的文件要注意编码** —— 踩过 UTF-8 写坏,tsc 报 Invalid character
2. **测注入浏览器的脚本必须真求值再 parse** —— 模板字面量会吃掉 `\/` 这类转义
3. **守卫比对源码前先剥注释** —— 否则会被自己写的说明文字骗过(**踩过两次**)

### 0.3 基线

移植开工前的基线(2026-09-07 实测):`npx vitest run tests/x/` → **40 文件 / 512 通过**。

**每一步移植后必须仍然全绿。** 哪条红了 = 真的动了行为,**必须解释清楚**,
不许为了变绿去改测试。

## 1. 四类测试,各管一段

本层的验收不能只靠单测 —— 它的核心风险(站点改版、通道静默失聪)单测根本够不着。

| 类 | 管什么 | 能不能 CI | 例 |
|---|---|---|---|
| **A 契约测试** | 接口行为符合 `06` 的定义 | ✅ | `find` 多个时不许自己挑 |
| **B 架构守卫** | 边界没被绕过 | ✅ | 业务代码里零处 `webContents` |
| **C 故障注入** | ⭐ **坏掉时真的会响** | ✅ | 掐掉 CDP,探针必须报不健康 |
| **D 真机验证** | 站点真实行为 | ❌ 人工 | selector 在真 X 上还有效吗 |

> **C 是本层最特殊的一类**,也是最该有的 ——
> 因为这层的失败形态是「**静默失聪**」,不是「抛异常」。
> 只测「正常时能用」,等于没测。

⚠️ **A/B/C 都是「AI 验」,D 是「人验」。但 D 不该只在最后做一次** ——
每层都要有**人可观察的验收界面**,与 AI 的自检**同源**。见 §3.5。

## 2. 逐模块验收标准

### 2.1 `web.page`(控制)

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | `find` 找到多个时**不自己挑** | 造两个候选,断言返回 **2 条**而非 1 条 | A |
| 2 | `find` 找不到时 `Failed`,**不兜底** | 断言不返回「随便一个」 | A |
| 3 | `pageId` 在 webview 重挂后**不变** | 模拟卸载+重挂,断言 id 相同、wcId 不同 | A |
| 4 | `pageId` 在换 slot / 换窗口后**不变** | 改 facts 的 slot,断言 id 不变 | A |
| 5 | 同 ws 三个 tab = **三个不同 pageId** | ⭐ **初版方案死在这** | A |
| 6 | `goto` **不接受裸 URL** | 传 URL 应被拒(类型层面最好) | A/B |
| 7 | 业务代码零处 `webContents` / `wcId` | 扫源码,KNOWN_DEBT 锁死 | B |
| 8 | 租约到期/页面销毁能回收 | 造泄漏场景,断言回收 | A |

### 2.2 `web.net`(输出·网络)⭐ 本层最高风险

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | ⭐ **A 结束不会掐掉 B** | **构造并发**:订阅者 B 常驻,A 跑完退出,断言 **B 仍收到载荷** | **C** |
| 2 | ⭐ **attach 失败时订阅者收到明确错误** | 让 attach 失败,断言订阅者**收到 Failed**,不是安静等 | **C** |
| 3 | ⭐ **通道被外部抢占时会响** | 步 2:外部 `detach` → 订阅者收到 `channel-lost`;<br>⚠️ **「探针报不健康」依赖 `web.trace`,属步 2.5** | **C** |
| 4 | 业务代码零处 `debugger.attach` | 扫源码 | B |
| 5 | webRequest ↔ CDP 两套 requestId 能配对 | 用 V1 那套(URL+method+type+10s)喂样本 | A |
| 6 | 载荷按 pageId 正确分发 | 两个页面各订阅,断言不串 | A |

> #1 是**移植是否成功的核心判据**。现在 X 那 8 处 CDP 就是死在这里
> (`03` §3.3 记录的疑似真 bug)。**没有这条测试,就无法证明移植修好了它。**

### 2.3 `web.dom`(读取/脚本)

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | ⭐ **预注册脚本求值后是合法 JS** | **真 eval 再 parse**,覆盖**全部**脚本 | A |
| 2 | `run` **不接受脚本字符串** | 类型层面拒绝 | A/B |
| 3 | 业务代码零处裸 `executeJavaScript` | 扫源码 | B |
| 4 | 解析失败**不静默丢** | 喂坏载荷,断言产出 degradation 记录 | C |

> #1 直接对应 `project-x-inject-template-escape`(采集恒 0 一整天,tsc 单测全绿)。
> 现有守卫 `inject-script-evaluates.test.ts` 只覆盖出事那一处,
> **移植后必须覆盖全部预注册脚本**。

### 2.4 `web.input`(输入)

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | `type` 落地失败要报失败 | 喂个不存在的锚点,断言 `Failed` 而非 `Ok` | A |
| 2 | `feed` 没接住要报失败 | 缩略图不出现,断言 `Failed`/`Degraded` | A |
| 3 | 🔴 **X 业务代码不得出现点发布的调用** | 扫 X 源码 | **B** |
| 4 | 落地确认真的会失败 | 故意让内容不落地,断言测出来 | C |

> #3 是红线的**唯一机器强制点**(底座不管,见 `06` §8.2)。
> 守的对象是 **X 业务层代码**,不是底座。

### 2.5 `web.trace`(诊断与维护)

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | ⭐ **通道哑了会自己举手** | 掐掉 CDP,探针 N 秒内变不健康<br>⚠️ **探针是拉取式**:接线时必须指定「谁来查、多久查一次」,否则探针白做(见 `08` §6.8.3③) | **C** |
| 2 | **站点改版可统计** | 故意改坏一个 selector,断言出现「格式外」degradation | **C** |
| 3 | 自愈留痕 | 触发一次自愈,断言有记录 | C |
| 4 | 配额有效 | 灌满 trace,断言按策略淘汰而非写爆 | A |
| 5 | 过滤策略由调用方给 | 断言底座无内置站点规则 | B |

### 2.6 adapter

| # | 验收标准 | 怎么证明 | 类 |
|---|---|---|---|
| 1 | adapter 拿不到 `webContents` | 类型 + 扫源码 | B |
| 2 | adapter 不输出领域对象给底座 | 底座接口只见 `NetworkRecord` 等 | B |
| 3 | 「待 spike」锚点被显式标注 | 断言标记存在,不与已验证的混同 | A |
| 4 | selector 真实有效 | **真机** | **D** |

## 3. ⭐ 故障注入清单(C 类,本层的命脉)

**每一条都必须先看它红,再看它绿。** 没红过的守卫是假保证。

| 注入什么 | 期望 | 对应风险 |
|---|---|---|
| 订阅者 B 常驻时,A 跑完 detach | **B 仍收到载荷** | X 现有疑似真 bug |
| 让 `debugger.attach` 抛错 | 订阅者收到 `Failed` | V1 只 `console.warn` 的坑 |
| 外部掐掉 debugger | 探针 N 秒内报不健康 | 静默失聪 |
| 改坏一个 selector | 出现「格式外」degradation | 站点改版可统计 |
| 喂一段坏载荷 | 解析失败留痕,不静默丢 | `judge-parse-no-silent-drop` |
| 掏空一个底座核心函数 | ⭐ **相关守卫必须红** | **防「抽象层被掏空仍全绿」** |
| 在业务代码里写一处 `webContents` | 架构守卫红 | 边界被绕过 |
| 在 X 业务里写一处点发布 | 红线守卫红 | 🔴 |

> 最后三条是**对守卫本身的攻击面测试** —— `feedback-verify-guard-can-fail`
> 明确要求钉住「抽象层被掏空」这条反向攻击面。

## 3.5 ⭐ 每层都要「AI 可验 + 人可验」的双通道

> 用户 2026-09-08 定:「每一层都应该建立 **AI / 人都可以验收**的方式,
> 而不仅仅是人。**包括验收的界面**。……这样才能确保**调试的独立和完整**。」

### 3.5.1 为什么两条通道都要

同一件事,两种验法**互相证伪**:

| | AI 验 | 人验 |
|---|---|---|
| 形式 | 结构化输入 → 结构化输出 → 断言 | **看得见的界面**,人眼对照 |
| 强项 | 快、可重复、可 CI、能覆盖边界 | 能发现「**数据对但事实不对**」 |
| 盲区 | ⚠️ **校验逻辑与被测逻辑同源,一起错就一起瞎** | 慢、易疲劳、不可回归 |

⭐ **AI 的盲区正是本仓踩过的坑**:采集器自己报「✅ 抓到 81 条」,
而真相是**滚过 433 条只抓到 81**(漏 80%)。
自测通过是因为**它拿自己的采集结果当分母**。
人拿官网点击数当分母才发现的。

> 所以判据是:**AI 验「契约成立」,人验「事实成立」。**
> 缺任何一条,这一层都不算验收完。

### 3.5.2 「调试的独立」怎么落地

关键要求:**每层能单独验,不必等下游接上。**

做法是每层暴露一个**自检入口**,不依赖任何业务:

```
web.<层>.selfcheck(场景) → { 输入, 实际输出, 期望, 判定, 证据 }
```

- **AI 侧**:调 `selfcheck`,断言 `判定 === pass`
- **人侧**:同一个 `selfcheck` 的结果**渲染成界面**,人看得见输入输出

**同一份数据,两种呈现** —— 这样人看到的和 AI 断言的**必然是同一件事**,
不会出现「测试绿了但界面显示不对」。

### 3.5.3 逐层的双通道验收

#### `web.page`(控制)

| | 输入 | 输出 | 判定 |
|---|---|---|---|
| **AI** | `find({ws:'ws-1'})` | `PageFacts[]` | 返回**全部 N 条**(不是 1 条);字段完整 |
| | 卸载+重挂 webview | 前后 `pageId` | **相同**,而 `wcId` **不同** |
| | 同 ws 开 3 个 tab | 3 个 `pageId` | **互不相同** |
| **人** | 打开「页面清单」面板 | **一张实时表**:每行 = 一个页面,列出 ws / slot / tab / owner / url / pageId / 状态 | 人对照屏幕上真实开着的页面,**行数与内容一一对得上** |

⭐ **人验的关键**:屏幕上开着 5 个网页,面板就该是 5 行。
**多一行 = 有幽灵页面(泄漏);少一行 = 有页面没被登记(会漏操作)。**
这是 AI 验不出来的 —— AI 只知道「`find` 返回了它自己登记的东西」。

#### `web.net`(输出·网络)

| | 输入 | 输出 | 判定 |
|---|---|---|---|
| **AI** | 订阅 + 触发一次请求 | 收到的事件序列 | `request-start` → `response-complete`,`bodyRef` 可取回 |
| | B 常驻时 A 跑完退出 | B 之后收到的事件数 | **> 0**(不被掐掉) |
| | 让 attach 失败 | 订阅者收到的东西 | **`Failed`**,不是静默 |
| **人** | 打开「网络监视」面板 | **实时流水**:每条请求的 url / 状态 / 有没有 body / 哪个订阅者收到了 | 人在页面上点一下,**面板里立刻出现对应请求** |

⭐ **人验的关键**:**订阅者列 + 近 5 分钟捕获数**。
「有订阅者但捕获数 0」在界面上是**一眼可见的红**,不用等谁去查。

#### `web.dom`(读取/脚本)

| | 输入 | 输出 | 判定 |
|---|---|---|---|
| **AI** | 每个预注册脚本 | **求值后**的字符串 | 能被 `parse` —— 覆盖**全部**脚本 |
| | 传脚本字符串给 `run` | 拒绝 | 类型/运行时拒绝 |
| **人** | 「脚本清单」面板 | 每个脚本:id / 求值后的源码 / 最近一次执行的**输入与输出** | 人能看到**浏览器实际收到的是什么**,而非源码里写的什么 |

⭐ 这直接对应 `project-x-inject-template-escape`:
源码里正则是对的,**求值后**才是错的。人只有看到求值后的样子才判断得了。

#### `web.input`(输入)

| | 输入 | 输出 | 判定 |
|---|---|---|---|
| **AI** | `type(锚点, "测试文本")` | `Landed` / `Failed` | 落地校验通过才 `Landed` |
| | 喂不存在的锚点 | `Failed` | **不许返回 Ok** |
| **人** | 在验收面板点「试填」 | **左边真页面,右边显示填了什么、落地了没** | 人**眼见文字进了框**,且面板说 `Landed` |

⭐ **人验的关键**:这是「看着成功实际没做」最容易发生的地方。
**面板说成功 + 屏幕上框是空的 = 立刻抓到。**
(这正是历史上那个 bug 的形态:日志说注入成功,右栏框是空的。)

#### `web.trace`(诊断维护)

| | 输入 | 输出 | 判定 |
|---|---|---|---|
| **AI** | 掐掉 CDP | `health()` | N 秒内 `alive:false` |
| | 改坏一个 selector | degradation 记录 | 出现「格式外」条目 |
| **人** | 「健康看板」 | 各层 alive / 关键指标 / 最近故障 | **一眼看出谁病了**,不用翻日志 |

### 3.5.4 验收界面:右栏一个 view,五个面板(dev-only)

**用户 2026-09-08 拍板:dev-only,不占用户界面,但随时可开。**

#### 形态

```
右栏 · Web 能力层验收台(dev-only)
├─ 页面清单     现在有哪些页面   ← 对照屏幕数行数
├─ 网络监视     实时流水 + 订阅者/捕获数  ← x-capture-monitor 升级为通用
├─ 脚本清单     求值后的源码 + 最近输入输出
├─ 动作试验台   试填 / 试点,看落地确认
└─ 健康看板     各层 alive + 最近故障 + 站点改版计数
```

#### 怎么挂:用现成机制,不发明新东西

V2 已有 self-register view 机制,`x-inbox` 就是这么挂的:

```
src/platform/renderer/index.tsx:92   import '@views/x-inbox';   // self-register(right slot)
src/views/social/SocialView.tsx:210  bus?.slot.openRight('x-inbox-view');
```

而现在的采集监视器就是 `XInboxView` 里的一页
(`view === 'capture'` → `CaptureMonitorView`)。**这套已跑通,照搬即可。**

#### 为什么不开独立窗口

| 方案 | 问题 |
|---|---|
| 独立 `BrowserWindow` | 全仓只有 `main-window.ts` 一处建窗;新窗口要重挂 `did-attach-webview` 整套 per-window hook —— 记忆 `project-per-window-webview-hooks` 踩过 |
| 塞进 Chrome DevTools | 那是 Chromium 的,插不进我们的面板 |
| **右栏 view** ✅ | 机制现成、天然 per-ws、**和被观察对象并排** |

⭐ 最后一条是关键:**验收台必须和被观察的页面同屏。**
「左边真页面、右边显示抓到什么」这个形态,**开独立窗口反而做不到** ——
人得在两个窗口之间来回看,对照就失效了。

#### 与 Chrome DevTools 的分工(不是替代)

| | Chrome DevTools | 本验收台 |
|---|---|---|
| 看的对象 | **浏览器**的原始行为 | **我们这一层**的行为 |
| 回答 | 这个请求发出去了吗 | **我的订阅者收到了吗** |
| | DOM 长什么样 | **求值后的脚本**长什么样 |
| | — | ⭐ **滚过 100 条抓到几条(分母)** |

> DevTools 看得见「X 返回了 33 条推文」,但看不见「我们只解析出 8 条」——
> **那个差值才是我们要的**。所以不是替代 DevTools,是它看不到的那一层。

#### dev-only 怎么落地

照 `registerXTestHandlers` 的既有范式(`x/index.ts` 注释:
「逐块底层测试(dev-only,ipc-bus 按需注册)」):

- 生产构建**不注册 IPC、不 import view** → 用户看不见
- 开发/排查时 `bus.slot.openRight('web-capability-devtools')` 一行打开,
  可挂命令面板或快捷键

> 「持续接待」意味着站点改版时随时要查 —— 所以是**随时可开**,不是**默认可见**。

### 3.5.5 这件事的收益

| 收益 | 说明 |
|---|---|
| **调试独立** | 每层单独可验,不必等下游接上 |
| **AI 能自查** | 移植中 AI 可反复跑 `selfcheck`,不用每次找人 |
| **人能复核** | 人不必读代码,看面板就知道成没成 |
| ⭐ **互相证伪** | AI 说 pass 但人看着不对 → **必有一方错**,而且立刻暴露 |
| **新 adapter 免费继承** | 接一个新专业站点,**这五个面板自动可用** |

> 最后一条呼应总纲的最终判据:加新站点只写 adapter。
> **验收能力也该是「免费继承」的,而不是每个站各造一套。**

## 4. 架构守卫的写法(B 类)

沿用本仓已验证的范式:`tests/views/slot-resource-guard.test.ts`。

它有三个部分,**缺一不可**:

1. **扫源码 + 白名单 + KNOWN_DEBT**,新增违规 → 红
2. **KNOWN_DEBT 逐条锁死**:修好一条也红,提示删除 —— **债只减不增**
3. **白名单只含真实存在的文件** —— 防条目腐烂后守卫静默放行

**移植期的用法**:存量违规进 `KNOWN_DEBT`(带 `file:line` + 注释说明),
每接入一个消费者就销掉一批。**清单长度 = 剩余工作量**,可见、可度量。

> ⚠️ 已知债**用 KNOWN_DEBT 锁,不并进白名单** ——
> 两者混在一起,债就被漂白成合法用法。

## 5. 真机验证(D 类)—— CI 够不着的那部分

| 验什么 | 方法 |
|---|---|
| selector 在真站上有效 | 人工跑一遍关键路径 |
| 采集完整性 | ⭐ **采集监视器**:左浏览右显示,看**分母** |
| 多窗口 / 双栏不串 | 双栏各开一个 X,填字看进哪个 |

### 5.1 采集监视器就是本层的真机验收工具

`x-capture-monitor` 的验证哲学(用户 2026-09-02 定):

> 左边原推文页,右边采集显示页,我在左边操作,你在右边显示抓取的 item。
> 理论上应该加上统计,**共滚动过多少个推文,成功采集了多少条**才算。

**关键是分母** —— 「抓到 81 条」说明不了任何问题,
「滚过 100 抓到 81」才是可判断的。

> 这比「跑一遍报 ✅」强在:那是**自己给自己打分**(校验逻辑和采集逻辑同源,
> 一起错就一起瞎),而这个是**人眼对照**。
>
> 移植后这个工具应**升级为通用**(现在只服务 X)——
> 任何 adapter 都该能用它验完整性。

## 7. 什么算「这一层建成了」

`01` §6 那六条判据,逐条给出证明方式:

| 判据 | AI 怎么证明 | 人怎么看见 |
|---|---|---|
| 站点改版只改一层 | 改一次 adapter,业务/底座零改动 | diff 只落在 adapter 目录 |
| 加新站点只写 adapter | **实测**:接第二个消费者时新增基础设施 = 0 | 新站点**直接拥有五个面板** |
| 业务拿不到 `webContents` | 架构守卫,KNOWN_DEBT 清零 | 清单长度 = 剩余工作量 |
| 没有落地确认就不算成功 | 契约测试 + 故障注入 | 动作试验台:说成功就真进框了 |
| 通道哑了会自己举手 | 故障注入(掐 CDP → 探针红) | 健康看板变红 |
| 站点改版可统计 | 故障注入(改坏 selector → 「格式外」) | 看板上那个站的计数上升 |

> **「加新站点只写 adapter」是最终判据,而且它只能在接第二个消费者时才验得了。**
> 所以步 3(接 AI)和步 6(接 X)不只是移植,**它们是这层的验收本身**。
