## 1. 一句话

> **网页的每个功能先登记进能力目录(和 X 的 90 个能力同一个目录、同一个执行器);
> Gemma 只做一件事:听懂一句话 → 从目录里挑能力、填参数;干活的永远是登记好的能力。**
> 网页太多样的问题不靠 Gemma 现场理解,靠「站点规则是数据」,将来由 AI 起草、人确认后存下来复用。

## 3. 现状盘点(2026-11-05 查)

### 3.1 网页上已有的动作

| 用户看到的 | 入口 | 干活的 | 中途要人吗 | 结果 |
|---|---|---|---|---|
| 📥 提取到笔记 | 右键菜单 | main `clipPageToRenderer` → renderer `runImportPipeline` | 否 | 新笔记(右栏打开) |
| 📥 提取题目 + 解答到笔记 | 右键菜单(命中站点规则才有) | main `clipPageWithAnswersToRenderer` | 否 | 新笔记,解答在折叠块 |
| 📸 截图正文到笔记 | 右键菜单 | main `shotArticleToRenderer` → renderer `handleWebShot` | **是**:拖框 + 确认 | 插入右栏光标处,或新笔记 |
| 📖 查词 / 🌐 翻译选中文字 | 右键菜单 | renderer 词典面板 | 否 | 面板 |
| 双栏翻译 / 选目标语言 | 工具栏 | renderer `web-translate-view` | 否 | 右栏翻译视图 |
| 打开网址 / 前进后退刷新 / 标签页 / 页内查找 | 工具栏、快捷键 | renderer 为主 | 否 | 导航 |
| 书签增删改、历史 | NavSide | 书签 main;**历史只在 renderer** | 否 | — |
| 下载文件 | 网页触发 | main `will-download` | **是**:系统存储对话框 | 本地文件 |
| ⬇ 下载视频 / 📝 抓字幕 / 🌐 翻译字幕 / 🤖 AI 翻译 | **笔记里的视频块**,不在网页上 | main yt-dlp / 字幕 / Gemma 语音转写 / 翻译 | 否 | 本地文件 / 块属性 |

### 3.2 影响设计的四个事实

1. **视频功能在笔记里,不在网页上。**「提取视频并翻译字幕」= 提取成笔记 → 抓字幕 → 翻译,天然是一条短链。
2. **提取结果主进程不知道。** 提取是 main 抓完推给 renderer 建笔记,笔记建没建成、id 是什么,main 拿不到。
   AI 调用后没法核对「真建成了」,也没法把笔记接给下一步。(截图出错还在用 `window.alert`。)
3. **两个动作中途要人。** 截图要人拖框确认;下载会弹存储对话框。
4. **一部分功能只在 renderer。** 历史、翻译视图、页内查找;能力目录在 main,要有一座桥。

### 3.3 现成可用的零件

- 能力目录 + 执行器:`platform/main/capability/capability.ts`(校验 → 前提 → 占锁 → 执行 → 写执行记录 → 统一结果)。
- 本地 Gemma:`platform/main/local-llm/ollama-client.ts` `callOllamaChat`(原生 `/api/chat`,`think:false`,`format:'json'`);
  现有调用方都用 `gemma4:12b`。经验:关思考 1~5 秒;**用对象契约,不用数组**(判断层吃过亏)。
- 网页读取:`web-capability/dom`(只跑登记过的脚本)、`page`(goto / ready / scrollUntil)。
- 站点规则先例:`content-extraction/linked-answers/rules.ts`。

## 4. 设计一:网页动作登记成能力(W1,不涉及 AI)

### 4.1 先登记哪些(建议,粒度待定)

| 能力 id(暂定) | 类别 | 参数 | 中途要人 | 说明 |
|---|---|---|---|---|
| `web.page.outline` | input | 网页 | 否 | **新做**:页面提纲,给 Gemma 读(§5.2) |
| `web.clip.page` | input | 网页 | 否 | 提取到笔记 |
| `web.clip.withAnswers` | input | 网页 | 否 | 题目 + 解答;没命中站点规则 → refused 并说明 |
| `web.shot.article` | input | 网页;可选「从哪到哪」 | **是** | 截图;W2 起可按提纲预先把框放好,人只确认 |
| `web.video.toNote` | input | 网页;可选「抓字幕」「翻译成某语言」 | 否 | 视频进笔记;字幕 / 翻译是可选步骤 |
| `web.video.download` | input | 网页或视频地址 | 否 | yt-dlp 下到本地 |
| `web.translate.page` | control | 网页;目标语言 | 否 | 打开双栏翻译(renderer 桥) |
| `web.nav.open` | control | 网址 | 否 | 打开网址(renderer 桥) |
| `web.bookmark.add` | input | 网页 | 否 | 加书签 |

**类别怎么归**(我的判断,待用户确认):写进自己的笔记、存到本地、改自己的界面,都**不是对外动作**,归 input / control,
AI 可直接调;对外动作(发帖、留言、提交表单…)才是 output,照旧要人批复。

### 4.2 改造要点

- **右键菜单 / 按钮改走 `execute(id, …, { caller: 'ui' })`**:点一次,执行记录里就有一行。人和 AI 走同一条路。
- **补结果回传**(§3.2 第 2 条):renderer 建完笔记,把 `noteId`(或失败原因)回报给 main,能力等到回报才算完成。
  回报超时 = failed 并写明,不当成功。
- **占住网页**:同一个网页同时只跑一个网页动作(`page:<wcId>` 锁),免得提取到一半被导航走。
- **中途要人的动作**:能力一直等到人确认 / 取消才返回;人取消 = refused(「你取消了」),不算失败。
- **renderer 桥**:main 能力通过 IPC 请 renderer 执行并等回报;renderer 不在线(窗口没开)= refused。

### 4.3 W1 判据

- 右键「提取到笔记」点一次 → 执行记录一行,带 noteId;故意弄坏 renderer 建笔记 → 记录是 failed 并有原因。
- 现有单测全绿;新能力有行为测试(spy 真调了,不只是源码里有这个名字)。

## 5. 设计二:一句话 → 一个动作(W2)

### 5.1 效果

```
┌ 网页工具栏 ─────────────────────────────────────────────────┐
│ ‹ › ↻ │ artofproblemsolving.com/wiki/…_Problems │ ✨ │ ⚙ ⊞ │
└─────────────────────────────────────────────────────────────┘
        点 ✨(或快捷键)
┌─────────────────────────────────────────────────────────────┐
│ ✨ 把这页的题和答案存下来                                    │
├─────────────────────────────────────────────────────────────┤
│ 我理解为:📥 提取题目 + 解答到笔记                            │
│ 进行中… 12/25 题                                             │
│ ✓ 完成:笔记「2025 AMC 12A Problems」已在右栏打开            │
└─────────────────────────────────────────────────────────────┘

听不准时不猜,给选项:
┌─────────────────────────────────────────────────────────────┐
│ ✨ 把第三题截下来                                            │
├─────────────────────────────────────────────────────────────┤
│ 我理解为:📸 截图,范围「Problem 3」到「Problem 4」之前        │
│ 框已放好,请在网页上确认(Enter)或调整                        │
└─────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────┐
│ ✨ 把视频弄下来                                              │
├─────────────────────────────────────────────────────────────┤
│ 你是想:  [⬇ 下载到本机]  [📥 放进笔记(带字幕)]               │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 Gemma 看到什么

不给整页 HTML(慢、超出小模型能力),给**页面提纲**(`web.page.outline`):

- 网址、标题、语言;命中了哪条站点规则
- 标题层级列表(h1–h3,带序号,截图「从哪到哪」就按它定位)
- 页上的视频(个数、标题、地址)、选中的文字
- 当前右栏有没有打开的笔记(决定截图插哪)

再加:**网页能力的目录**(`listCapabilities()` 里 `web.*` 的 id / 说明 / 参数说明),和用户那句话。

### 5.3 Gemma 返回什么(对象契约)

```json
{
  "understood": "提取题目 + 解答到笔记",
  "capability": "web.clip.withAnswers",
  "input": {},
  "choices": null
}
```

- 拿不准 → `capability: null`,`choices` 给 2~3 个候选(能力 + 参数 + 一句说明),界面显示成按钮。
- 返回的能力 / 参数照样过执行器校验:目录里没有、参数不对 → invalid,原样显示给人,不替它改。
- 不需要思考链:`think:false`,`format:'json'`,温度 0。

### 5.4 执行方式(我的建议,待用户定)

按「先全开放」「自设规矩只提醒不拦」:**输入类直接执行**,先显示「我理解为…」再显示结果;
不对就点「不是这个」→ 显示候选 → 记下这次纠正。不设「每次先确认再执行」。

### 5.5 留痕与评估

每句话记一行(放哪个库待定,倾向 `krig_flow`):原话、提纲摘要、Gemma 的选择、人有没有纠正 / 改成什么、执行记录 callId。

- 判据(我的建议):攒够 50 句真实用语,**挑对能力 ≥ 90%**、参数对 ≥ 80%;不到就看纠正记录改说明 / 提示,不先换大模型。
- 纠正过的句子做 few-shot 回流(同 X 回复语料那套,in-context,随时可撤)。

## 6. 设计三:短链(W3)

「把这个视频连字幕放进笔记,翻成中文」= `web.video.toNote` 一个能力带两个可选参数,**优先用参数解决,不让 Gemma 编排多步**。

确实要多步的(如「提取这页,再把里面的视频下载下来」),Gemma 返回一串能力(≤3 步),界面逐步显示、逐步执行,
前一步失败就停并说明。若届时 Module5 ② 的流程模板已就绪,改走流程模板。

## 7. 设计四:网页多样化(W4,接 04 号文档)

```
通用动作(任何网页都能做)    提取正文 · 截图 · 视频 · 翻译 · 书签
        ▲
站点规则(数据,命中才生效)   AoPS 题目 + 解答 · 将来的其他题库 / 文档站
        ▲
AI 起草规则(人确认后存下)   看一次页面结构 → 起草规则 → 用样本页回归 → 人确认 → 生效 + 留档
```

- Gemma 每次现场理解网页不可靠也慢;**规则写一次、用很多次**。
- 起草可以交给大模型(经已登录的 AI 网页,`ai.web.ask`),Gemma 只负责「这页命中了哪条规则」。
- 改规则按 04 号文档 §7–§9:样本库回归、修改档案、定期归档。

## 10. 不做的 / 边界

- 不让 Gemma 直接点网页、读整页 DOM 现场决策(超出本地小模型能力,也绕开了执行器的留痕和拦截)。
- 不放开对外动作:网页上的提交、发帖仍是 output,要人批复(Module5-03 §3)。
- 不承诺「任何网页都能提取完整」(04 号文档 §2)。
