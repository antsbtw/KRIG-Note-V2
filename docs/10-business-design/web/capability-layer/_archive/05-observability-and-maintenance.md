# 05 · 维护模块与诊断模块设计

> 属于 **Web 能力层**(`01-web-capability-contract.md` 是总纲)。

> 立于 2026-09-07。承接 `04-v1-port-assessment.md`。
> 用户拍板:「不仅仅需要功能模块,还需要**维护模块、对应的 log 诊断模块**。
> 确保有**持续接待和健康维护**的能力。」
>
> **本文是设计,不含实现。**

---

## 0. 这条要求把 L6 从「可选」变成「结构性」

上一轮我把 L6(trace/落库)列为「选搬」。用户这条要求推翻了那个定位:

**能持续接待的系统 = 功能 + 维护 + 诊断三件套,缺一不可。**

尤其对浏览器能力层,理由格外硬:

| 特点 | 后果 |
|---|---|
| 依赖**外部网站**,随时改版 | 故障是**常态**不是异常,必须能快速定位是哪一层坏了 |
| 跑在**用户机器**上 | 出事时开发者不在现场,只能靠留痕 |
| 大量**后台/无人值守**运行 | 没人盯着,坏了要能自己发现并说出来 |
| 多站点 adapter 会**越来越多** | 每加一个站点,可观测成本不能线性增长 |

> **判据**:X 那一整天「采集恒 0,日志却说『多半撞上导航』」的事故
> (记忆 `project-x-inject-template-escape`),本质是**诊断能力缺失**,
> 不是功能缺失。功能代码是对的,是**看不见哪里坏了**。

---

## 1. ⚠️ 先解决一个命名冲突

V2 **已经有** `L0/L1/L2...` 这套层号,含义完全不同:

| | V2 现有(启动期分层) | browser-capability(能力分层) |
|---|---|---|
| L0 | 平台基础 | Session/Lifecycle |
| L1 | **Window** | **Network Capture** |
| L2 | … | Page Runtime |
| L4 | … | Interaction |

证据:`src/platform/main/diagnostics/L1-alive.ts` 输出的是
`[L1] Window alive | main BrowserWindow created`,
`health-check.ts` 已占用 `HEALTH_L0`…`HEALTH_L5` 七个 IPC。

> **决定:web 能力层不得复用 `L0/L1/...` 编号。**
> 最终采用 `web.*` 本名(不用 `BC-*` 前缀,理由见 `06` §8.3):
> `web.page` / `web.net` / `web.dom` / `web.input` / `web.trace`。
>
> 否则日志里两套 `[L1]` 混在一起,**诊断模块自己先变成故障源**。

## 2. 三个模块的分工

```
┌─────────────────────────────────────────────────┐
│  功能模块   做事                                  │
│    `web.page` / `web.net` / `web.dom` / `web.input`  │
├─────────────────────────────────────────────────┤
│  诊断模块   说清楚发生了什么                        │
│    · 结构化事件流(可 grep / 可导出)              │
│    · 分层健康态(谁活着、谁坏了、坏在哪)            │
│    · 现场留痕(出事时的原始载荷)                   │
├─────────────────────────────────────────────────┤
│  维护模块   自己发现问题、自己恢复、说得出话         │
│    · 健康探针(定期自检)                          │
│    · 自愈(能修的自己修)                          │
│    · 配额与老化(不许无限增长)                     │
│    · 失效上报(修不了的,明确说出来)               │
└─────────────────────────────────────────────────┘
```

**边界**(沿用可靠性纲领 §3「遥测只记录、不决策」):

- **诊断只观察,不干预** —— 它不重试、不修复,只让事实可见
- **维护做决策** —— 基于诊断的事实,决定重连 / 降级 / 上报
- 两者分开,是为了**诊断本身永远不会成为故障源**

## 3. 诊断模块设计

### 3.1 沿用 V2 已有的两个约定,不另起

V2 已有 `diagnostics-bus`(`markAlive`/`markFailed`/`getLayerState`)
和 `health-check` IPC。**浏览器能力层应该接进去,而不是自建一套。**

| 已有 | 浏览器能力层怎么用 |
|---|---|
| `markAlive(layer, details)` | `markAlive('`web.net`', { sessions: 3, subscribers: 5 })` |
| `markFailed(layer, reason)` | attach 失败、provider 挂了 |
| `getLayerState(layer)` | 健康检查 IPC 直接可查 |

**要补的是运行期**(可靠性纲领 §3 明确指出的盲区):

> 现状盲区:`diagnostics-bus` 只覆盖启动期,且只写 console + 内存 Map,
> **进程关闭即丢失**。运行期操作故障无处落脚——这正是本次事故逃逸的空间。

### 3.2 三条流,分开存

| 流 | 内容 | 保留 | 用途 |
|---|---|---|---|
| **lifecycle** | 页面创建/导航/销毁/frame 变更 | 短(天) | 「当时在哪个页面」 |
| **network** | 请求元信息 + 是否拿到 body + 哪个 provider | 短(天) | 「载荷到底来没来」 |
| **degradation** | 每一次降级/失败/兜底(可靠性纲领 §3 的 record) | **长** | 「这类 bug 发生过多少次」 |

前两条是**高频流水**,第三条是**低频事件**。分开存是因为保留策略不同 ——
流水要老化,故障记录要留得久。

### 3.3 degradation record 直接采用纲领已定的结构

可靠性纲领 §3 已经定了契约,**不重新发明**:

```
{ ts, layer, capability, operation, category, reason, inputRef, rawSnippet }
```

`category` 用纲领 §2 的分类学(格式外 / 解析崩溃 / 资源失败 / 契约违反 / 系统级)。
浏览器能力层的映射:

| 场景 | category |
|---|---|
| CDP attach 失败 | 系统级 |
| 载荷来了但解析不出 | 解析崩溃 |
| selector 失效找不到元素 | 格式外(**站点改版的主要形态**) |
| 落地确认失败(填了没进去) | 契约违反 |
| 网络请求本身失败 | 资源失败 |

> **「selector 失效 = 格式外」这个映射很重要** ——
> 它让「X 改版了」变成一个**可统计的指标**,而不是一次次孤立的报障。
> 某个 adapter 的「格式外」计数突然上升 = 那个站改版了。**这就是持续接待能力。**

### 3.4 现场留痕:V1 的 trace-writer 正是干这个的

V1 `trace-writer.ts` 2103 行,目录结构:

```
<trace根>/<run>/
  ├ lifecycle.jsonl
  ├ network.jsonl
  ├ responses/          ← 原始响应体
  └ pages/<pageId>/extracted/
```

**这套骨架直接可用**(砍掉 61 处站点特化后约 300-400 行)。

关键价值:X 排查 429 那次(记忆 `project-x-translate-rate-limited`),
结论至今未明,正是因为**没有原始载荷留痕**,只能靠事后推测。
有了 `responses/` 就能回放。

⚠️ 但要加 V1 没有的东西:**开关 + 配额**。见 §4.3。

## 4. 维护模块设计

这是用户这次新提的、前面几轮都没有的部分。

### 4.1 健康探针:每层自己回答「我还好吗」

每个 BC 层暴露统一探针:

```
health() → {
  alive: boolean
  since: 时间
  指标: { ... }        // 每层自己定义
  问题: [ ... ]         // 空数组 = 健康
}
```

各层该报什么:

| 层 | 关键指标 | 什么算不健康 |
|---|---|---|
| `web.page` | 活跃页面数 / 租约数 | 租约泄漏(只增不减) |
| `web.net` | 挂载 session 数 / 订阅者数 / **近 5 分钟捕获数** | ⭐ **有订阅者但零捕获** = 通道哑了 |
| `web.dom` | 注入成功率 | 成功率骤降 = 站点改版 |
| `web.input` | 落地确认成功率 | 同上 |
| `web.trace` | 落盘字节数 / 是否触配额 | 写盘失败 |

> ⭐ **`web.net` 那条「有订阅者但零捕获」是本次重构最该有的探针。**
> X 现在那个疑似 bug 的形态就是「静默失聪」——通道被掐了但没人知道。
> 有了这条,**它会自己举手**,而不是等人发现「采集怎么变 0 了」。

### 4.2 自愈:能修的自己修,修不了的明确说

| 故障 | 自愈动作 | 修不了时 |
|---|---|---|
| CDP 被外部 detach | `dbg.on('detach')` → 重新 attach | 连续 N 次失败 → `markFailed` + 通知订阅者 |
| 页面销毁但租约还在 | 随页面销毁事件回收 | — |
| 页面卡死无响应 | 探针发现 → 标记不可用 | 上报,由业务决定换页/重开 |

**红线**:自愈**必须留痕**。V2 已有先例可循 ——
`recoverStuckAiJudging()` 自愈时会打印「自愈:N 条已退回 pending」。
**静默自愈 = 把问题藏起来**,违反铁律三。

### 4.3 配额与老化:诊断不许把磁盘吃满

这是 V1 trace-writer **没有**、但生产必须有的:

| 约束 | 建议 |
|---|---|
| trace 总量上限 | 到达上限后按 run 淘汰最旧 |
| 单个响应体上限 | 超限只存头部 + 标注被截断 |
| 默认开关 | **默认只开 lifecycle + degradation**;network 全量落盘和 responses/ 默认关,排查时才开 |
| 敏感信息 | ⚠️ 见 §4.4 |

> V1 是开发期工具,可以无限写。V2 跑在用户机器上,**必须有配额**。
> 否则「诊断模块」自己变成故障源 —— 这正是要避免的。

### 4.4 ⚠️ 留痕会记录敏感数据 —— 但策略归应用层

`responses/` 存的是**原始响应体**。而这些页面是**用户登录状态下的私人内容**:

- X 的私信 / 通知
- **邮件模块的邮件正文**
- AI 对话内容
- 请求头里的 **auth token / cookie**

**⚠️ 但用户已裁定:这些判断归应用层,底座不做**(见 `06` §8.4)。

底座 `web.trace` **如实记录传进来的东西,不内置过滤规则** ——
「记什么、记多少、留多久」作为**参数**由调用方给。

于是分工是:

| 谁 | 做什么 |
|---|---|
| **底座** | 提供「可按参数过滤 / 可关闭 / 可清除」的记录能力 |
| **应用** | 决定本站点/本场景记什么、headers 落不落、body 存不存、留多久 |

应用层落策略时的参考(**不是底座规则**):

1. 请求头默认不落盘,或只落白名单字段(`content-type` 等)
2. 响应体落盘默认关闭,开启时给明确提示
3. trace 留本地 userData,不随任何上报外发
4. 提供「一键清除全部 trace」

> 这样底座对未来站点保持中立 —— 接一个医疗站或财务站时,
> 敏感度判断由那个 adapter/应用自己定,不用回来改底座。

### 4.5 「持续接待」的落点:站点健康看板

用户说的「持续接待能力」,我理解为:**不断有新站点接进来,且老站点不断改版,
系统要能持续应对**。落到设计上:

```
每个 adapter 报告:
  最近成功率 · 最近「格式外」计数 · 最后一次成功时间
```

一个站点改版了 → 它的「格式外」计数上升 → **看板上自己变红**,
而不是等用户报「怎么不好使了」。

这也让「加一个新站点」的成本可控:**新 adapter 自动获得同一套可观测性**,
不用各自造轮子。

## 5. 对实施顺序的影响

`04-v1-port-assessment.md` §7 的顺序要调整——**诊断必须和 `web.net` 同期,不能后补**:

| 步 | 内容 | 变化 |
|---|---|---|
| 0 | 定 `pageId` 模型 | 不变 |
| 0.5 | ✅ 命名已定(`web.*`)· 敏感数据已裁定归应用层 | 见 `06` §8.3 / §8.4 |
| 1 | 搬 `web.page`(L0) | 不变 |
| 2 | 搬 `web.net`(L1)+ attach 失败 fail loud | 不变 |
| **2.5** | **`web.trace` 骨架 + 健康探针**(与步 2 同期) | ⭐ **从「选搬」提为必做** |
| 3 | 接 AI 验证 | **验收要加**:探针能报出「订阅者有 / 捕获零」 |
| 4 | `web.dom`(L2) | 注入失败要进 degradation |
| 5 | `web.input`(L4)+ 红线三道闸 | 落地确认失败要进 degradation |

**为什么 2.5 不能后补**:`web.net` 是最容易「静默失聪」的一层。
先有诊断,才能验证移植是否成功 —— 否则步 3 的验收只能靠「看起来能用」。

## 6. 验收判据(可验证,不是口号)

| 目标 | 怎么证明 |
|---|---|
| 通道哑了会响 | ⭐ **故意 detach 掉 debugger,探针必须在 N 秒内报不健康** |
| 站点改版可统计 | 故意改坏一个 selector,degradation 里出现「格式外」记录 |
| 自愈留痕 | 触发一次自愈,日志里能看到自愈发生了 |
| 配额有效 | 灌满 trace,验证按策略淘汰而非写爆磁盘 |
| 敏感数据不落盘 | 抓一次带 auth 头的请求,确认落盘里没有 token |

> 按记忆 `feedback-verify-guard-can-fail`:**每条都必须故意注入故障看它变红。**
> 没红过的探针 = 假保证。
