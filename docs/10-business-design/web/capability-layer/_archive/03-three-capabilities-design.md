## 0. 一个必须先说的发现:底座已经存在,别另起炉灶

设计前先查了 `src/platform/main/web-service-base/` —— **服务无关的 webview 底座已经在了**,
AI / X / Mail 三个服务共用,7 个文件:

| 已有原语 | 覆盖三层的哪格 | 质量 |
|---|---|---|
| `resolveWsWebContents` / `WithWait` | 控制·定位 | 🟢 好 |
| `createWebviewServiceRegistry` | 控制·生命周期 | 🟢 好 |
| `pasteTextToWebview` | 输入·注入文本 | 🟢 **已含落地校验 + 兜底** |
| `feedFilesToInput` / `feedVideoToInput` | 输入·喂文件 | 🟢 **已含落地确认 + fail loud** |
| `locateSendButton` | 输入·红线 | 🟢 **只定位不 click,注释明确** |
| `buildHitTestScript` | 输入·定位元素 | 🟢 好 |
| `attachWebviewContextMenu` | 控制·交互 | 🟢 好 |

> ⚠️ **这改变了设计的性质。**
> 不是「从零建一层」,而是「**底座已有一半,把 X 侧散落的那一半补齐并接回去**」。
>
> 而且底座的质量比 X 模块内部高得多 —— `pasteTextToWebview` 的落地校验注释写着
> 「不只看 length>0,那会把'粘歪了但有内容'误判成功」,`feedFilesToInput`
> 明确「没出现缩略图 → fail loud」。**「不确认就是失败」在底座里已经是事实标准。**
>
> 所以本设计的第一原则:**能进底座的进底座,X 专属的留 X 层。**

### 0.1 分界线

| | 归属 | 判据 |
|---|---|---|
| 与「是哪个网站」无关 | **底座** `web-service-base/` | AI / Mail 也能用 |
| X 特有的页面知识 | **X 基础层** `x/base/` | 只有 x.com 才成立 |

例:「poll 等 selector 出现」是底座的;「X 的 compose 框叫什么」是 X 的。

## 1. 三层出口形状

### 1.1 控制层

```
┌─ 定位 ────────────────────────────────────────┐
│ locate(意图)                → Handle | Error   │
│   意图: 'interactive'  显式 wcId,多 ws 定向    │
│         'unattended'   无人值守自找(campaign)  │
└───────────────────────────────────────────────┘
┌─ 导航 ────────────────────────────────────────┐
│ goto(h, 目标页)             → Arrived | Error  │
│   目标页是**语义**不是 URL: 'compose'|'tweet'  │
│   |'notifications'|'search'|'profile'|'article'│
└───────────────────────────────────────────────┘
┌─ 就绪 ────────────────────────────────────────┐
│ ready(h, 判据, timeout)     → Ready | Timeout  │
└───────────────────────────────────────────────┘
┌─ 占用 ────────────────────────────────────────┐
│ lease(h, 用途)              → Lease | Busy     │
│ release(lease)              → void             │
└───────────────────────────────────────────────┘
```

**`Handle` 而非裸 `WebContents`** —— 这是关键设计决策。业务层拿到的是句柄,
拿不到 `wc`,于是**物理上无法**绕过基础层去 `loadURL` 或 `executeJavaScript`。
守卫才有东西可守(否则只能靠 grep 注释)。

**导航参数是语义不是 URL** —— 因为 X 改版时变的是 URL,不变的是「我要去发推页」。
这直接服务于「X 改版只改一层」的判据。

### 1.2 输入层

```
sel(名字)                    → Selector | Missing   // 唯一来源
type(h, 目标, 文本)          → Landed | Error       // 复用底座 pasteTextToWebview
feed(h, 目标, 文件[])        → Landed | Error       // 复用底座 feedFilesToInput
tap(h, 目标)                 → Done | Error | 🔴Refused
run(h, 脚本id, 参数)         → 结果 | Error         // 参数化,不拼串
```

**`tap` 对发布类目标返回 `Refused`** —— 见 §3 红线。

**`run` 收下全部 46 处注入** —— 脚本预注册 + 参数分离传入,调用方给不了原始字符串,
模板字面量吃转义的事故**在类型层面不可能再发生**。

### 1.3 输出层

```
read(h, 提取id)              → 数据 | Error
watch(h, 接口匹配)           → Subscription        // ⭐ 引用计数,见 §2
parse(载荷, 类型)            → 对象 | Error        // 失败不静默丢
confirm(h, 判据)             → Confirmed | Failed  // ⭐ 强制
tally(sub)                   → {分母, 分子, 采集率}
```

## 2. 核心设计:CDP 通道仲裁

这是本次设计要解决的**最硬的问题**,也是 §2 那个疑似 bug 的正解。

### 2.1 病根

现在 8 个模块各自 `attach → on(message) → Network.enable → ... → off → detach`。
「共用」全靠 `catch { /* 已被 attach,共用即可 */ }` 这句注释级约定。
**先 attach 的人走时 detach,把还在共用的人一起掐掉** —— 被掐的一方
`attached=false`,不重连、不报错,静默失聪。

### 2.2 设计:通道由基础层独占,业务只订阅

```
        业务A ──subscribe──┐
        业务B ──subscribe──┤
        业务C ──subscribe──┤
                           ▼
                 ┌──────────────────┐
                 │  CDP 通道管理者   │  refCount
                 │  (每 wc 一个)     │  0→1: attach + Network.enable
                 └──────────────────┘  1→0: detach
                           │
                        wc.debugger
```

**状态机**

| 事件 | 动作 |
|---|---|
| 首个订阅 | attach + `Network.enable`;失败 → **全体订阅者 fail loud**(不静默) |
| 后续订阅 | refCount++,复用通道 |
| 载荷到达 | 按各订阅者的匹配规则分发(一份载荷可命中多人) |
| 退订 | refCount--;**归零才 detach** |
| wc 销毁 | 通知全体订阅者 `Terminated`,不静默 |
| 外部抢占 | 检测到通道被夺 → 通知全体,**不假装还在收** |

**三条不变量**

1. 一个 `wc` 最多一条 CDP 通道
2. **只要还有人订阅,通道就不许关**
3. 通道意外中断 → **全体订阅者收到明确通知**,绝不静默失聪

> 不变量 3 是关键:现在的失效形态是「静默变 0」,最难查。
> 改成「响」之后,同类问题一次就能定位。

### 2.3 顺带解决

`x-capture-monitor` 的「分母」验证哲学(滚过多少 vs 采到多少)现在只有它一家有。
通道统一后,**采集率对所有订阅者免费可得** —— `tally()` 是通道的自然产物。

## 3. 写方向红线:从注释升级为机制

### 3.1 现状

红线「绝不程序点发布」现在靠 **9 处注释**维持。底座的 `locateSendButton`
做对了(只定位不 click),但那是**约定**,不是**约束** ——
新写一个模块直接 `executeJavaScript('...click()')`,没有任何东西会拦。

### 3.2 设计:三道闸,层层收紧

| 闸 | 机制 | 拦住什么 |
|---|---|---|
| **一 · 类型** | selector 分两类:`Actionable` / `LocateOnly`。发布类只属后者。`tap` 只接受 `Actionable` | 编译期就点不了发布按钮 |
| **二 · 运行时** | `tap` 收到发布类目标 → 返回 `Refused` 并告警(不是抛异常静默死) | 绕过类型(动态取名)也拦得住 |
| **三 · 守卫** | ①`x/` 下禁止裸 `executeJavaScript`(全部走 `run`)②`run` 的预注册脚本禁止含 `.click()` 作用于发布类 selector | 拦住「自己写脚本点」这条绕行路 |

### 3.3 ⚠️ 守卫必须验证能真的失败

按记忆 `feedback-verify-guard-can-fail`:三道闸写完后,**必须故意各注入一次违规**
(写个点发布的 `tap`、写个裸注入、写个含 click 的脚本),看它们**真的变红**。
没红过的守卫是假保证 —— 这个仓库踩过。

## 4. selector 单一来源

### 4.1 现状

注册表 `XServiceSelectors` 存在且写得认真,但 **9 个模块 33 处硬编码绕过**。

### 4.2 设计

```
名字 ──► sel() ──► Selector{ 值, 类别, 是否待spike }
                      │
              找不到 → Missing (fail loud,不返回空串)
```

- 全部 selector **只此一处**定义,按语义命名(`composeBox` 而非 `[data-testid=...]`)
- 每条带 **类别**(`Actionable` / `LocateOnly`)—— §3 闸一的依据
- 每条带 **待 spike 标记** —— 现在注册表里大量「待实机 spike 抓真实 data-testid」
  的初值,这个不确定性必须**显式**,不能混在已验证的里面
- 守卫:`x/` 下出现字面量 `data-testid` → 红

### 4.3 X 改版时的动作

改一个文件。这是「X 改版只改一层」判据的具体兑现。

## 5. 错误契约:统一「三态」

现在的失败形态五花八门:`return { error }` / `catch {}` 吞掉 / `?? []` /
`console.warn` 后继续。按可靠性纲领和铁律「不要静默兜底」:

| 态 | 含义 | 调用方该做什么 |
|---|---|---|
| `Ok(值)` | 成了,且**已确认** | 继续 |
| `Failed(原因, 可重试?)` | 明确失败 | 按原因决定重试/报人 |
| `Degraded(值, 缺了什么)` | 部分成功 | **必须显式处理**,不许当 Ok |

**没有第四态。** 特别是不许有「返回空值假装成功」。

`Degraded` 是专门为这个仓库设的:采集抓了 80/100 条、
喂图成功但缩略图没校验(`uploadedMediaThumb` 未配)—— 这些现在要么被当成功、
要么被当失败,两种都错。给它一个**必须被显式处理**的态。

## 7. 实施顺序与验收

用户已认可顺序:**控制 → 输出 → 输入**。

| 步 | 内容 | 验收判据 |
|---|---|---|
| **1** | 控制层:Handle + 语义导航 + 统一就绪 | 512 条守卫全绿;`x/` 零裸 `loadURL`;9 处导航合一后**行为一致**(X 接管导航全覆盖) |
| **2** | CDP 通道仲裁 | ⭐ 构造并发场景:watch 常驻期间跑 profile 采集,**watch 不哑**;refCount 归零才 detach |
| **3** | 输出层:确认 + 解析 + 计数 | 无 `confirm` 的写动作**编译不过**;解析失败零静默丢 |
| **4** | 输入层:selector 收口 + `run` 收注入 | `x/` 零字面量 `data-testid`;零裸 `executeJavaScript` |
| **5** | 红线三道闸 | ⭐ **故意注入三种违规,三道闸各红一次** |

**贯穿铁律**:每步 512 条全绿再进下一步。哪条红了 = 真动了行为,必须解释清楚。
守卫**跟着搬,不删掉重写** —— 它们记录着大量「为什么这么写」。

## 8. 设计上的取舍(说明代价)

| 决策 | 得 | 失 |
|---|---|---|
| 业务层拿 `Handle` 不拿 `wc` | 守卫有东西可守;绕不过去 | 改动面广(所有业务模块签名要动) |
| 导航参数用语义不用 URL | X 改版只改一处 | 多一层映射;冷门页面要先加枚举 |
| CDP 通道进底座 | AI 也受益;一次修两处 | 底座变重;要考虑非 X 场景 |
| 三态错误契约 | `Degraded` 不再被误判 | 调用方必须显式处理,写起来更啰嗦 |
| 脚本预注册 | 转义事故类型层面消灭 | 动态脚本(spike/勘查)要走单独逃生口 |

最后一条要注意:`x-payload-inspector` / `x-author-timeline-spike` 这类**排查工具**
天然需要动态脚本。设计上给它们一个**显式标注的逃生口**(而非让 `run` 变松),
符合铁律「只在显式标注的兼容场景才兜底」。
