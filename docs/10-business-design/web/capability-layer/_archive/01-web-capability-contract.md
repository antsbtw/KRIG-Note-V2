# Web 能力层 · 总纲:控制 / 输入 / 输出

> 立于 2026-09-07。用户拍板:
> 「这是**所有 web 应用的能力**。web 应用(网页 / 网页衍生的内容网站)
>  它的基础功能都从这里调用三个能力(**控制 / 输入 / 输出**)。」
>
> **本文是本目录的总纲,先读这篇。**
> 本层不属于 X,不属于 AI,不属于任何单一站点 —— 它是全部 web 应用的共同底座。

---

## 0. 一句话

> **凡是在 app 里操作网页的功能,都只通过「控制 / 输入 / 输出」三个能力,
> 不直接碰 webContents、不自己 attach CDP、不自己拼注入脚本。**

---

## 1. 谁是这一层的消费者

不是「X 和别人」,而是**一族对等的 web 应用**:

| 消费者 | 它要网页干什么 | 现状 |
|---|---|---|
| **X** | 采集推文 / 填回复 / 发长文 | 🔴 自建全套 |
| **AI 对话** | 抓回答 / 填提问 | 🟡 自建一套 |
| **网页剪藏** | 抓正文 | 🟡 有引擎注册表 |
| **网页翻译** | 改响应头 / 注脚本(**不取内容**) | 🟡 自成一路 |
| **音视频下载** | 借登录态取资源 | 🟡 另一条路 |
| **邮件** | 抓邮件正文(**仅阶段 0**;阶段 1 IMAP 不走浏览器) | 🟡 |
| **将来的专业站点** | 各行各业 | ⚪ **本层为它们而建** |

> 现在是**六套各自演化**;目标是**一套底座 + 六个 adapter**。
>
> ⚠️ 关键认知:**X 不是这层的主人,只是它最痛的消费者。**
> 设计文档决策 6 说得很清楚:底层能力模型必须首先服务于**通用网页**,
> 而不是首先服务于某几个个性化页面。

## 2. 三个能力的定义

> 用**动词**说,不用形容词 —— 能力是「做什么」,不是「关于什么」。
> 接口细节见 `06-data-model-and-interfaces.md`。

### 2.0 先说边界:底座做什么、不做什么

> **底座只做两件事:如实呈现事实、忠实执行动作。所有判断都在应用层。**

| 底座做 | 底座不做 |
|---|---|
| 找得到页面、拿得到数据 | **不判断哪个页面「该」被操作** |
| 点了、填了,并确认真的成了 | **不判断哪个动作「危险」** |
| 如实记录发生了什么 | **不判断哪些数据「敏感」** |

### 2.1 控制 —— 选定作用对象

⭐ **核心是「先持有页面对象,再对它说话」** ——
这是在模拟人的操作流程:人看着一个窗口做事,**身份和动作从不分离**。
不是「填了一条推,事后猜填哪去了」。

| 动词 | 做什么 |
|---|---|
| `find` | 按事实条件找页面(ws / slot / owner / url)**如实返回全部,不替你选** |
| `facts` | 查它的位置与状态 |
| `goto` | 让它去某个**语义页面**(不是 URL),并确认真的到了 |
| `ready` | 等它到位 |
| `lease` / `release` | 占住它 / 放开它 |
| `prepare` | 改变**加载环境**:响应头 / UA / CSP / partition |

> `prepare` 是网页翻译暴露出来的第四类动作 —— 既不是「取内容」也不是
> 「往里放东西」,而是**在页面加载之前改变规则**。
> 现在全仓只有翻译在用(剥 CSP 让 Google 翻译脚本能跑),
> 但接专业站点时很可能再用到(某站 CSP 挡住注入、需要改 UA / referer 才能正常加载)。
> **底座只提供「能改」,改不改、改什么由应用决定。**

**`find` 的唯一铁律:找到多个时不许自作主张挑一个。**
底座不保证「挑得对」,只保证「不替你挑」——
挑错了是应用的问题,**悄悄替你挑是底座的问题**。

### 2.2 输入 —— 在选定页面上施加动作

| 动词 | 做什么 |
|---|---|
| `focus` | 激活任意一个输入框 |
| `type` | 往里填内容(**含落地确认**) |
| `feed` | 喂文件给网页自己的上传控件(**含接住确认**) |
| `tap` | 点任意一个可点元素(按钮 / 链接 / 选项…) |
| `press` / `scroll` / `hover` | 按键 / 滚动 / 悬停 |
| `run` | 执行**预注册**脚本(参数化,**不拼字符串**) |

**`tap` 是中立原语** —— 不分等级、不设危险词表、不拒绝任何目标。
危险与否是业务语义,底座无从判断(见 §7 红线)。

### 2.3 输出 —— 取回内容,并证明真的成了

| 动词 | 做什么 |
|---|---|
| `subscribe` | 订阅网络载荷(**应用只订阅,永不 attach/detach**) |
| `waitFor` / `list` / `body` | 等某个请求 / 列请求 / 取响应体 |
| `read` / `query` / `text` | 从 DOM 取(**辅助**,非首选) |
| `confirm` | ⭐ 我做的事**真的成了吗** |
| `tally` | 抓全了吗?**分母是多少** |

## 3. 一条贯穿全层的原则:数据分层优先级

```
1. 网络层    ← 正文优先走网络响应
2. 下载层    ← 附件优先走真实下载
3. Frame 层
4. DOM 层    ← 只做定位与结构辅助
5. 渲染截图  ← fallback,不是主链
```

**这条比「三个能力」更根本** —— 它决定了同一份内容该从哪里取。

实测对照(见 `02-consolidation-analysis.md`):

| 消费者 | 取内容吗 | 现在走第几层 | 该走 |
|---|---|---|---|
| 网页剪藏 | ✅ | **4 DOM** | 1 网络 |
| X 主采集 | ✅ | **4 DOM** | 1 网络 |
| AI 对话 | ✅ | 1 网络 ✅ | 1 |
| 音视频 | ✅ | 2 下载 ✅ | 2 |
| 邮件(阶段 0) | ✅ | 4 DOM | 待定 |
| **网页翻译** | ❌ **不取** | — | — |

> 卡在第 4 层的两个,恰好是「一改版就失效」抱怨最多的两个。**不是巧合。**

⚠️ **本表只回答「内容从哪一层取」,不是消费者全景**(全景见 §1)。

- **网页翻译不取内容** —— 它剥 CSP + 注入 Google `element.js`,
  让**页面自己翻译自己**,结果直接显示给人看,不进 note、不进库。
  实测:`web-translate-driver` / `translate-view` **零处** `executeJavaScript`、零处提取。
- **邮件阶段 1(IMAP)不在本层** —— 它完全绕开浏览器直连邮件服务器,
  不是 web 应用。只有阶段 0(webview 抓 DOM)是本层消费者。

## 4. 三个能力 ↔ 实现模块的对应

「控制/输入/输出」是**对消费者的说法**;下面是**实现模块**:

| 对外能力 | 实现模块 | 状态 |
|---|---|---|
| 控制 | **`web.page`**(页面对象 / 查找 / 导航 / 就绪 / 租约) | V1 有,身份部分要重写 |
| 输出 | **`web.net`**(网络捕获 + body provider + 事件总线) | V1 有,可搬 |
| 输入 | **`web.input`**(focus / 填字 / 喂文件 / tap) | V1 空;**V2 `web-service-base` 已有一半** |
| 输入+输出 | **`web.dom`**(DOM 读取 / 预注册脚本) | V1 空,从零写 |
| 横切 | **`web.trace`**(诊断与维护) | V1 有,砍站点特化后可搬 |

> 命名不用 `L0/L1/...`(V2 已有启动期层号 `[L1] Window alive`,会混淆),
> 也不用 `BC-*` 前缀(得先知道 BC = Browser Capability 才读得懂)。
> `web.*` 形状天然不冲突、自解释、与目录对应,
> 且前缀本身呼应定位:**它是 web 能力层,不是 X 的、不是 AI 的**。
> 推翻过程见 `06` §8.3。

## 5. 站点适配的位置:adapter 在层之上

```
   X    AI   剪藏  翻译  音视频  邮件  未来的专业站点
   └────┴────┴────┴────┴───────┴────┴──────┐
                    adapter 层              │  ← 只回答「这个站的正文在哪个接口/哪个 selector」
   ┌───────────────────────────────────────┘
   │            Web 能力层
   │   控制 · 输入 · 输出  (web.page / web.net / web.dom / web.input)
   │            web.trace(诊断与维护)
   └───────────────────────────────────────
                    Electron webContents
```

**两条铁律**:

1. **adapter 只做解释与增强,不得反向定义底层数据模型**
   —— 底层输出 `NetworkRecord` / `DomAnchor` 这类通用对象,
   不输出 `ClaudeConversation` / `TweetRecord`
2. **加一个新站点 = 只写一个 adapter**
   —— 不该再抄一套 CDP、一套导航、一套等待、一套注入、一套确认

> 第 2 条是**本层是否成功的最终判据**。
> 现在加一个新站要抄**五套**;抽象之后应该是**零套**。

## 6. 判据:怎么算这层建成了

| 判据 | 含义 |
|---|---|
| ⭐ **站点改版只改一层** | 改 adapter,不动业务、不动底座 |
| **加新站点只写 adapter** | 不再复制基础设施 |
| **业务模块拿不到 `webContents`** | 物理上绕不过去,守卫才有牙齿 |
| **没有落地确认就不算成功** | 契约强制,不靠自觉 |
| **通道哑了会自己举手** | 不再静默失聪 |
| **站点改版可统计** | 「格式外」计数上升 = 那个站改了 |

## 7. 已知的红线(从各消费者沉淀,归入本层)

| 红线 | 来自 | 落点 |
|---|---|---|
| 🔴 **绝不程序点发布** | X 写方向 | ⚠️ **X 业务层**,不在底座(见下) |
| **不要静默兜底** | 可靠性纲领铁律一 | 全层:三态错误契约 |
| **失败要留痕** | 可靠性纲领铁律三 | `web.trace` |
| **成功要对账** | 可靠性纲领铁律四 | 输出层:落地确认 + 分母 |
| **守卫要验证能真的失败** | 反复踩过 | 每条守卫必须故意注入违规看它变红 |

> 🔴 **这条不归底座。** 同一个「发送按钮」,AI 必须自动点(问答语义),
> X 绝不能点(发布不可撤回)—— 差别在**业务语义**,不在按钮本身,底座无从判断。
> 底座的 `tap` 是中立原语;红线由 **X 业务层**保证:X 写方向代码从不调 `tap` 点发布。
> 现在靠 9 处注释维持,应升级为**守卫**(「X 业务代码不得出现点发布的调用」),
> 且守卫必须故意注入违规验证过能变红。推翻过程见 `06` §8.2。
