# 09 · 取数机制全集与缓存分层

> 属于 **Web 能力层**(`01-web-capability-contract.md` 是总纲)。

> - 缓存**存硬盘**(未整理的数据)
> - **默认开,不要用户干预**
> - 「目前提取数据的方法有 SSE/CDP 还有哪些?**不同层面的缓存数据面向不同应用,分类清楚**」
>

---

## 0. 先纠正一个前提:不是 2 种,是 8 种

用户问「SSE/CDP 还有哪些」。实测全仓,**在用的取数机制有 8 种**,
而 SSE 其实不是独立机制(它是**注入 hook 拦到的一种流形态**)。

---

## 1. 八种取数机制(实测,非推断)

| # | 机制 | 拿到什么 | 谁在用 |
|---|---|---|---|
| **M1** | **CDP `Network` 域**<br>`Network.enable` + `getResponseBody` | 渲染**前**的原始响应体(全量) | `web.net` · AI(Gemini) · X 的 6 个模块 |
| **M2** | **注入 fetch/XHR hook**<br>页面内劫持 `window.fetch` | 站点自己发的请求与响应<br>(**SSE 流式增量**属此类) | ChatGPT / Claude 提取 |
| **M3** | **`session.webRequest`** | 请求/响应**元信息**(不含 body) | `web.net` · 网页翻译(改响应头) |
| **M4** | **DOM 直读** `executeJavaScript` | 渲染**后**的可见内容 | 36 个文件(全仓最广) |
| **M5** | **页面内主动 fetch**<br>带登录态调站点自己的 API | 站点 API 的完整数据 | Claude(`/api/organizations/`)· Gemini |
| **M6** | **下载管线** `will-download` | 真实文件 bytes | web-download · 附件 |
| **M7** | **cookies 导出** | 登录态,交给外部工具 | ytdlp(YouTube/X 视频) |
| **M8** | **postMessage 桥** | iframe / widget 内部数据 | Claude artifact |

### 1.1 按「数据保真度」排序(呼应总纲 §3 的分层优先级)

```
M1/M2/M5  网络层原始数据   ← 渲染前,最全
M6        下载层真实文件   ← 附件优先走这
M8        frame 层
M4        DOM 层           ← 渲染后,只有站点想显示的
M3        仅元信息(无 body)
M7        旁路(不经浏览器)
```

> ⚠️ **M4 是全仓用得最广的(36 文件),却是保真度最低的** ——
> 这正是「页面一改版就失效」的根源。

## 2. ⭐ 缓存分层:三层,面向不同应用

用户要求「分类清楚」。按**谁消费、留多久、能不能重算**分三层:

| 层 | 存什么 | 面向谁 | 保留 | 能否重算 |
|---|---|---|---|---|
| **L-raw**<br>原始层 | M1/M2/M5 拿到的**原始响应体**、M6 的文件 | **排查 / 回放 / 重解析** | ⭐ **1 个月**(用户定) | ❌ 过期即失 |
| **L-struct**<br>结构层 | 解析后的领域对象(推文 / 对话 / 正文) | **业务**(入库前的中间态) | 短(会话级) | ✅ 从 L-raw 重解析 |
| **L-domain**<br>业务层 | `x_tweet` / note / `x_author` … | **最终用户** | 永久(业务规则定) | ⚠️ 部分可从 L-raw 重建 |

### 2.1 为什么必须分这三层

**这是本仓付过学费的**:

> `tweet_feedback` 有 607 条历史采纳,其中 **449 条(74%)正文已被 TTL 删掉** ——
> 因为当时**只有 L-domain**,没有 L-raw。原始载荷丢了就永远回不来。
> (`persistent-tracking-and-profiling.md` §1.1)

有了 L-raw,同样的事故变成:**业务表删了没关系,一个月内还能从原始层重建。**

### 2.2 三层各自的边界

| | L-raw | L-struct | L-domain |
|---|---|---|---|
| 谁写 | **底座**(自动) | adapter 解析 | 业务编排决定 |
| 谁读 | 排查工具 / 重解析 | 业务 | UI / 用户 |
| 站点知识 | ❌ 零(只认 URL 和 bytes) | ✅ adapter 的活 | ✅ 业务的活 |
| 出问题时 | **回放现场** | 重解析即可 | 要人工修 |

> ⭐ **L-raw 是底座的事,L-struct/L-domain 不是。**
> 底座**只负责如实存下原始数据**,怎么解析、存哪张表,是 adapter 和业务的判断
> —— 这与 `06` §0 的边界一致。

## 3. L-raw 的落盘规格(用户已定的部分)

| 项 | 决定 | 依据 |
|---|---|---|
| **存哪** | ⭐ **硬盘**(不进 SurrealDB) | 用户:「这是未整理的数据,硬盘」 |
| **默认** | ⭐ **开,不要用户干预** | 用户明确 |
| **保留** | **1 个月**,过期清除 | 用户:「一个月以上的缓存数据予以清除」 |
| 位置 | `userData/` 下,不外发 | 沿用 `05` §4.3 |

### 3.1 待定的实现细节(需要在实现前定)

| # | 问题 | 建议 |
|---|---|---|
| a | 总量上限 | ⭐ **用户配置,不写死**(见 §3.3)—— 爬虫持久化后空间需求会很大 |
| b | 单个响应体上限 | 超限只存头部 + 标注截断(`05` §4.3) |
| c | **索引怎么建** | 至少要能按 `pageId` / URL / 时间 / 站点 查回来,否则存了也找不到 |
| d | 请求头存不存 | ⭐ **参考 Chrome 的做法**(见 §3.4)—— 未来用户需求尚未明了,不提前锁死 |
| e | 清理什么时候跑 | 建议启动时 + 每日一次;⚠️ **常驻 timer 必须有停止调用**(`project-graceful-shutdown`) |

### 3.2 ⚠️ 「默认开」带来的一条新责任

用户定了默认开、不要干预。这是合理的(**未整理的原始数据本就该留着**),
但底座因此承担了两件事:

1. **必须让用户看得见、管得着** —— 占用可查、可清理、将满时告警(§3.3)
2. **必须能被清空** —— 一键清除 + 按时间/站点选择性清除

> 这不违反「敏感数据判断归应用层」:
> **底座负责「存得住、清得掉、不撑爆」,应用负责「这些数据能拿去做什么」。**

### 3.3 ⭐ 容量:用户可配,不写死上限(2026-09-09 用户裁定)

初稿建议「1 个月 + 2GB 双闸」。**用户否决**:

> 可以考虑更大或者不设。**如果未来爬虫持久化,需要的空间就是很大的。**(或者用户配置?)

**采纳:容量做成用户可配置项,底座不预设一个会挡路的数字。**

理由(用户的判断是对的):
- L-raw 的价值随**留存量**增长 —— 能回放的历史越长,重解析越有意义
- 2GB 对「持久化爬虫」这个方向**明显不够**,写死会在将来变成障碍
- 磁盘是用户的,**多大合适该由用户定**,不该由底座替他决定

**保留的底线**(这些不是限制用量,是防止失控):

| 项 | 做法 |
|---|---|
| 默认值 | 给一个宽松默认(如 1 个月 / 不限体积),**用户可改** |
| 可观测 | ⭐ **必须能看到当前占用**(多少条 / 多大)—— 用户要能据此决定配多少 |
| 可清理 | 一键清除 + 按时间/站点选择性清除 |
| 不失控 | 磁盘将满时**告警**,不是静默写爆 |

> ⭐ 关键区别:**「不设上限」不等于「不管」。**
> 底座的责任从「限制」变成「**让用户看得见、管得着**」。

### 3.4 ⭐ 请求头:参考 Chrome,不提前锁死(2026-09-09 用户裁定)

初稿建议「默认不存请求头(含 auth token)」。**用户裁定**:

> 建议参考 Chrome,未来用户尚未明了。

**采纳。** Chrome DevTools 的实际做法可作基准:

- 它**完整保留请求/响应头**(含 `Cookie`、`Authorization`),在 Network 面板可见
- 但**不导出到磁盘**,除非用户主动 Save as HAR
- 导出 HAR 时**明确提示含敏感信息**

**对本层的含义**:
- **存**(否则排查时缺关键线索 —— 很多失败就是头部导致的)
- 但要**知道自己存了敏感信息**:不外发、不进任何上报、清理时一并清
- 将来若要导出,**在导出那一刻提示**,而不是现在就不存

> 这条比初稿更合理:**排查需要完整现场**,而「不存」是拿排查能力换一个
> 此刻并不明确的隐私诉求。真有诉求时,加一个「导出时脱敏」比「当初没存」好补。

## 4. 八种机制 → 三层缓存的映射

| 机制 | 写入哪层 | 说明 |
|---|---|---|
| M1 CDP | **L-raw** | 主力 |
| M2 注入 hook | **L-raw** | 流式要合并成完整响应再存 |
| M3 webRequest | L-raw 的**元信息**部分 | 无 body,与 M1 关联(`04` §4.4 的配对逻辑) |
| M4 DOM 直读 | ⭐ **进 L-raw**(2026-09-09 改判,见下) | 它虽是渲染后产物,但**统一存更简单、更可靠** |
| M5 主动 fetch | **L-raw** | 与 M1 同等保真 |
| M6 下载 | **L-raw**(文件形态) | 附件走文件,不进响应体库 |
| M7 cookies | ❌ **不缓存** | 是凭据不是数据 |
| M8 postMessage | L-raw(小体量) | frame 内数据 |

### 4.1 ⭐ M4 改判:进 L-raw(2026-09-09 用户裁定)

初稿主张「M4 不进 L-raw」,理由是它已是解析产物、存了也不能重解析。
**用户否决**:

> 缓存就是大海,我们要从里面获取需要的东西可能是少量,
> **但是不要把业务逻辑搞复杂影响可靠性。**

**采纳,而且这句话纠正了初稿的思路错误。**

初稿在做**存储优化**(省掉一类数据),代价是**引入一条分支规则**
(「M1/M2/M5 存,M4 不存」)。而这条规则:

- 需要每个调用点判断自己属于哪类 —— **判断错了就丢数据**
- 让「缓存里有没有这条」变成**不确定**的 —— 排查时先要想「这个是 DOM 抓的吗」
- 省下的空间,在 §3.3「容量用户可配」之后**根本不是瓶颈**

> ⭐ **原则**:缓存层要**无条件、无分支**地收下一切。
> 「取什么、怎么用」是消费端的事;**存储端加判断 = 拿可靠性换空间**,
> 而空间恰恰是这里最不稀缺的。

**实测支持**:DOM 抓取的产出是普通 JS 对象(`XExtractTweetResult` 等),
序列化后与 JSON 响应体**同构** —— 统一存**不需要**额外机制。

## 5. 这份规格解决了什么

| 现在的问题 | 有了三层之后 |
|---|---|
| 载荷只在内存,**进程一关就没**(`MAX_RESPONSE_BODIES=256`) | L-raw 落盘,一个月内可回放 |
| 排查靠猜(`project-x-translate-rate-limited` 至今未解) | **有原始现场可回放** |
| 业务表 TTL 删了就永远丢(74% 正文丢失) | 一个月内可从 L-raw 重建 |
| 解析器改进后,老数据没法重新解析 | **L-raw 还在,可批量重解析** |
| 八种机制各存各的 | 统一进 L-raw,一套索引 |

⭐ **最后一条我认为最值钱**:现在改进了解析逻辑,**只能对新数据生效**;
有了 L-raw,可以**拿一个月的历史数据重跑一遍**,立刻看出改进有没有效
—— 这对「关键词精确率体检」「回复质量评估」这类事是质变。
