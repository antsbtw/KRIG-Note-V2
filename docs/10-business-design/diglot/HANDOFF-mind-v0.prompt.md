## 1. ⭐ 一句话:这是什么

> **「语义描述」⇄「图形描述」双向一致。就像 mermaid,
> 但保证任何一边的改动,另一边跟着动。**

| | mermaid | ⭐ 本项目 |
|---|---|---|
| 文本 → 图 | ✅ | ✅ |
| ⭐ **图 → 文本** | ❌ **改不了图** | ✅ **拖了节点,文本跟着变** |

**mermaid 是单向的 —— 这既是它的局限,也正是要超越的那一点。**

⚠️ 产品定位(用户明确):**KRIG-Note 是让人更容易表达思维,画布是 note 的最有力补充。**
帮 X 做业务编排**不是目的**。需求来源是「人怎么思考」,**按工业标准建设**。

## 3. ⭐⭐ 本轮范围:mind v0

### 3.1 做什么

**目标:双向同步引擎在 mind 上跑通。**

⚠️ **为什么先做 mind 而不是 bpmn**(用户已认可这个顺序):
**双向同步引擎是这里最难、最需要先验证的东西**,而 mind 的结构简单(树),
能让引擎的问题**充分暴露而不被图元复杂度掩盖**。引擎在 mind 上跑通了,
bpmn 只是换一套 S 层文法和渲染。

⭐ **且 bpmn 有硬阻塞**:画板的箭头/方向/标签三个缺口,对 bpmn 是致命的
(没箭头就不是流程图),对 mind 可绕开。

### 3.2 ⭐ 起步策略:先兼容 mermaid `mindmap`

用户拍板:「先参考 mermaid 的所有语义语法,**并兼容 mermaid 的语法格式**,
这样前期就可以**先导入 mermaid 的文档来检验**了,后期再扩展自己的语法和语义。」

**为什么这个起步方式对**:

| 好处 | 说明 |
|---|---|
| ⭐ **检验素材现成** | mermaid 社区图例海量,**不用自己造测试用例** |
| **语法不用发明** | 争议最大的部分直接采用既有标准 |
| **导入即有用** | 用户能把现有 mermaid 图**变成可拖动的** —— 本身就是卖点 |
| ⭐ **round-trip 是硬判据** | 导入 → 拖动 → 导出 → 再导入,**图必须一致。骗不过去** |

仓库已有的 `Mindmap` 模板(`mermaid-renderer.ts` 的 `MERMAID_TEMPLATES`):

```
mindmap
  root((主题))
    分支A
      叶子1
      叶子2
    分支B
      叶子3
```

⚠️ **mermaid mindmap 表达不了的**(备注/markers/labels/自由主题/summary/boundary/联系线标签):
前期**不进 mermaid 语法**,走 G 层或后期扩展。
⚠️⚠️ **不要为了塞进 mermaid 语法而扭曲模型。**

### 3.3 ⭐ 建议的实施顺序

```
① 断言先行 —— 把 00 §8 的 C1-C9 与 01 §8 的 M1-M4 写成测试(⚠️ 先于交互代码)
② mermaid mindmap 解析 → S 层模型(树推导规则见 01 §4)
③ S 层 → 画布渲染(复用 canvas-rendering,节点走 shape-library JSON)
④ ⭐ G 层:规范形 + 稀疏纪律 + 幂等序列化
⑤ ⭐⭐ 双向同步:画布拖动 → G 层一条条目,S 层零变更(C4)
⑥ round-trip:导出回 mermaid,验 C9
```

⚠️ **①必须打头** —— 规格原话:「**九条断言即九个 CI 测试用例,先于任何交互代码存在**」。

## 5. ⭐⭐ 「注入零红」是上一轮最值钱的方法(已抓到 6 个真缺口)

写完守卫**故意注入违规看它变红**。上一轮 6 次注入零红,**每次都是真缺口**:

| 形态 | 例 |
|---|---|
| **断言成立的原因是测试自己布置的另一个条件** | 「零捕获」被时间窗顺带遮出来,对缺陷零区分力 |
| **循环变量根本没用上** | 9 次迭代跑的是同一个函数 |
| **只验了标记串,没验引擎在不在听** | 标记串是 truthy,掏空后被当成功放行 |
| **假环境不像真环境** | `throwTimes=9999` 被可控时钟跑完了,场景根本没造出来 |
| **测试数据落在不同分片,每片一行** | 「两条黏一行」的 bug 在一行一片时不会发生 |

⭐ **自检问一句:「如果被测逻辑是错的,这条断言还会成立吗?」**

⚠️ 本轮尤其要注意:**双向同步的测试极易自证**。
比如「拖动后 G 层多了一条」——如果同步引擎根本没跑,而测试自己写了那条,**也会绿**。

## 6. 环境坑(踩过,会再遇到)

**真机跑 Electron 前先清 `ELECTRON_RUN_AS_NODE`**:

```bash
env -u ELECTRON_RUN_AS_NODE <你的命令>
```

否则 `require('electron')` 命中 npm launcher 包,报 `Cannot find module 'electron'`
—— ⚠️ **与「Electron 装坏了」一模一样,极易误判**(有人为此失败 5 次)。

**做实验改文件时用 `cp` 备份还原,绝不用 `git checkout`**
—— 上一轮踩过一次,把未提交的工作全丢了,靠 `/tmp` 备份救回。

## 7. 和用户协作的方式(顺着来效率高得多)

- **他会盯着数据要证据**。说「我觉得有问题」时通常是对的,**先查再答**
- ⭐ **他会推翻你的结论,而且往往对**。上一轮被纠正至少 10 次,每次都让方案更好:
  红线→闸门 · 缓存不要分支 · 按对象拆不按字段 · 「不采」措辞错了 ·
  策略不要写死 · **画布是产品不是工具链** · mind/bpmn 是两码事
- **被纠正时先查证再认**,别急着道歉也别硬撑
- ⚠️ **他明确讨厌的**:拿一个指标否定它没测的能力;把「库里没有」当「拿不到」;
  **用注释里的说明骗过守卫**
- ⭐ **方法论(他确立的)**:**先问「这是谁在用」,再决定归哪。**
  ⚠️ 不按字段名分组 —— 那会把「碰巧都叫 `*_at`」的东西凑一起
