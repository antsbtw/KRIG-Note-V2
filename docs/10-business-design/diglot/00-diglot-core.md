# Diglot 核心 · 双向同步底座(图种无关)

> 立于 2026-09-09,由 `agent/diglot-model-spec.md` v0.2 拆分而来。
>
> **本文只写两个图种共用的东西。** 各图种自己的模型见:
> - `01-mind-spec.md` —— 思维导图
> - `02-bpmn-spec.md` —— 流程图 / BPMN
>
> ⚠️ **mind 与 bpmn 是两种画板、两种文件、两个任务**,只是构思写在一处。
> **不要试图让 bpmn 复用 mind 的语义模型。**

---

## 0. ⭐ 产品定位(2026-09-09 用户明确)

> **KRIG-Note 的方向是让人们更容易地表达自己的思维,
> 所以画布(mind / bpmn)是 note 的最有力补充。**
> **帮助 X 的业务编排不是目的,表达人思维才是目的。**

⚠️ **由此推出两条**:

1. 需求来源是「**人怎么思考**」,不是任何具体业务的编排需要
2. ⭐ **按工业标准建设** —— 图元、语义、文件格式都要能与外界互通

---

## 1. ⭐⭐ 内核:语义描述 ⇄ 图形描述,双向一致

> 用户原话:「目标是『**语义描述**』⇄『**图形描述**』要达成一致性。
> 就像 **mermaid**,但是保证画图的重组(**任何一边的改动,另外一边跟着动**)。」

### 1.1 与 mermaid 的差别就是全部价值所在

| | mermaid | ⭐ diglot |
|---|---|---|
| 文本 → 图 | ✅ | ✅ |
| ⭐ **图 → 文本** | ❌ **改不了图**,只能改代码 | ✅ **拖了节点,文本跟着变** |

**mermaid 是单向的** —— 这既是它的局限,也正是要超越的那一点。

> ⭐ **仓库里已经有 mermaid**(`package.json` `mermaid ^11.15.0` + `@mermaid-js/layout-elk`),
> 渲染器在 `src/drivers/text-editing-driver/blocks/code-block/mermaid-renderer.ts`,
> 含 8 个模板(其中**已有 `Flowchart` 与 `Mindmap`**)。
> ⚠️ **但它只活在 Note 的代码块里,只能看不能碰** —— 不能点、不能拖、不能改。

### 1.2 三个面,一份真相

```
语义描述面(S)  ⇄  图形描述面(G)  ⇄  画布
        任一处改,另两处跟着动,且不打架
```

| 面 | 是什么 | 谁能改 |
|---|---|---|
| **S 层** | 图「**是什么**」:节点、关系、内容、标注 | ⭐ 用户书写,**机器不改写** |
| **G 层** | 图「**长什么样**」:坐标、布局、样式、折叠 | **用户可写,机器规范** |
| 画布 | 渲染与交互 | 操作**分流**落到 S 或 G |

**V 类(视图属性)**:G 的一小类,不改内容也不改排版语义,只记「此刻怎么看」
(如折叠状态),逐个决定是否随文档持久。

### 1.3 双射承诺

**文档 ⇄ 图形唯一确定。** 同一张图无论经何种编辑路径到达,
其 **G 层规范形字节级一致**;S 层固定为**用户自己的书写代表元**。

⭐ **稀疏纪律**:缺省即自动(default = auto)。
只有被触碰过的元素才存在条目;**删除条目即释放回自动**。

## 2. ⭐ 起步策略:先兼容 mermaid(用户 2026-09-09 拍板)

> 「语义也很简单,**先参考 mermaid 的所有语义语法,并兼容 mermaid 的语法格式**,
> 这样前期就可以**先导入 mermaid 的文档来检验**了,后期再扩展自己的语法和语义。」

### 2.1 为什么这个起步方式对

| 好处 | 说明 |
|---|---|
| ⭐ **检验素材现成** | mermaid 文档 / 社区图例**海量且免费**,不用自己造测试用例 |
| ⭐ **语法不用发明** | 争议最大、最容易反复的部分**直接采用既有标准** |
| **导入即有用** | 用户能把现有 mermaid 图拿进来**变成可拖动的** —— 这本身就是卖点 |
| **round-trip 是硬判据** | 导入 → 拖动 → 导出 → 再导入,**图必须一致**。这个判据非常硬,骗不过去 |

### 2.2 分期

```
前期  兼容 mermaid 语法 —— 导入现成文档当检验素材
后期  扩展自己的语法与语义(mermaid 表达不了的:备注、标记、自由主题…)
```

⚠️ **扩展时的纪律**:**未知记号原样透传,round-trip 不破坏**
(原规格 §6 已定)。即便将来加了自己的语法,读到不认识的东西也**不许丢**。

### 2.3 ⚠️ 已知的语法缺口(记账,不现在解)

mermaid 语法表达不了 mind 需要的部分内容 —— 备注(notes)、markers(优先级/进度)、
labels、自由主题、summary/boundary。

**处理原则**:前期这些**不进 mermaid 语法**,走 G 层或后期扩展;
⚠️ **不要为了塞进 mermaid 语法而扭曲模型**。

## 2.5 ⭐⭐ `def` 块(`+++`)—— note ⇄ graph 的映射通道(2026-09-13 用户拍板)

> 用户原话:「这就是 note 的可扩展性,等于在 **note ⇄ graph 增加了映射的能力**。」

**这不是 mind 的语法,是所有图种共用的记法。** 本节写**图种无关**的部分;
「块里认哪些词」由各图种自己定(mind 见 `01 §7.7`,bpmn 将来见 `02`)。

### 2.5.1 解决什么(记账:为什么非有不可)

⚠️ 离线探针实测(2026-09-13):联系线**存不住**。
`snapshotToFile` 的 `semantic` 存的是 `JSON.stringify(treeToNoteDoc(s))`,
而 `treeToNoteDoc` 只吐 block 序列**不碰 edges**,`noteDocToTree` 反向**硬写 `edges: []`**:

```
连线后 edges = [{id:"rel_n2_n3_...", source:"n2", target:"n3", label:"支撑"}]
存盘产物里有 edges 吗 = false      ⭐ 存盘即丢
读回后 edges = []
```

⭐ 与 `03 §5.6.1`「正文存盘即丢」**同一形态**:不是某层代码错,是
**存储格式装不下**。所以先定记法,再谈交互 —— 否则连完线一存盘就没了。

⚠️ 更根本的:树之外的关系(联系线)、节点的图形定义(shape/color),
在 note 里**没有任何书写形态**。没有记法 = 大纲侧永远看不见、编辑不了,
「一份数据、两种写法」名不副实。

### 2.5.2 ⭐ 形态:就是普通 paragraph,零新块类型

```markdown
# 技术选型
+++
id: B
shape: 菱形
+++
这里开始是正文,**富文本**、$公式$、图片照旧
```

| 规则 | 说明 |
|---|---|
| 位置 | ⭐ **hn 之后的第一段 paragraph**,`+++` 开、`+++` 合 |
| 类型 | ⭐⭐ **就是 paragraph** —— 不新增块类型,note schema 零改动 |
| 呈现 | `+++` 画成一条分隔线(**decoration,不插块**;先例:`build-block-indent-plugin` / `build-block-frame-plugin`) |
| 折叠 | 复用 note 既有 toggle |
| 内容 | ⭐ **行数可变**,只写关键行,其余默认,可逐步补充 |

⚠️ **为什么不用 `---`**:行首 `---` 在 note 里**已被占用** ——
`build-input-rules.ts:164` 的 `horizontalRuleRule` 当场把它变成 `horizontalRule` 块,
且 `buildInputRules` 是「**始终开**」(无 toggle)。
用 `---` 就必须改 note 本体,违反「mind 适应 note」铁律(`03 §5.9.2.2`)。

### 2.5.3 ⭐⭐ 别名:A/B/C(用户拍板,推翻「取标题文字」)

```markdown
# 需求分析
+++ id: A +++

# 排期
+++
id: C
A -.-> C          ⭐ 在 C 的块里,写 A 到 C 的线
+++
```

> 用户原话:「学习 mermaid,赋值 A/B/C 之类的(只限同一个文档),
> **内部使用 node id 检索执行**。这样的好处是,用户有任意连线时,都很简单,
> **在任意一个 `+++` 之内都可以做复杂的连线操作**。」

⭐⭐ **「任意一个」是这条的全部价值**:两端都用别名指名道姓,
**不依赖「我写在谁下面」**。关系不必写在源节点里 —— 这才是 mermaid
`participant U as 用户` 范式的真正威力。

⚠️ **我提过「用标题文字当别名」,被用户否决且否得对**:
`需求分析 -.-> 排期` 又长又易打错,复杂连线根本写不动。

**两层 id,各司其职:**

| | 是什么 | 谁用 |
|---|---|---|
| ⭐ **block id**(ULID,26 字符) | **真身份**,唯一性来源,**已在跑**(`note-projection.ts:251` 优先取 `attrs.id`,债 6 靠它解掉) | 机器:配对、存储、G 层、边的确定性 id |
| ⭐ **别名**(`A`/`B`/`C`) | **人写的书写便利**,作用域限本文档 | 人:在 `+++` 里写关系 |

⚠️ **别名不是身份** —— `id: B` 只是给某个 ULID 起个短名。
所以改标题、移动节点、增删行**都不会断**(解析到 ULID)。

⚠️⚠️ 反过来说:**ULID 不能当人写的记号**。`-.-> 01HXAB1234CDEFGHJKMNPQRSTV`
没法手敲、没法读、没法核对 —— 那会废掉「像 mermaid 一样能写」这个初衷。

### 2.5.4 ⭐ 冲突与悬空:方案丙(用户拍板)

⚠️ 别名写在**文本里**,于是它有和债 6 同源的风险:身份靠文本维系,文本一动就错位。

| 用户干了什么 | 处置(⭐ 丙:用户说了算 + 系统兜底) |
|---|---|
| 别名撞车(复制节点/手改重名) | ⭐ **自动加序号**(`A` → `A2`),不报错拒绝 |
| 引用了不存在的别名 | ⭐ **保留原文 + 标红提示**,⚠️ **不删不改** |
| 删掉 `id:` 行 | 该节点无别名;指向它的行变悬空(同上处置) |
| 复制节点 | ⚠️ **必须重新分配别名**(否则必撞)——实现时钉住 |

⚠️ **否决了两个极端**:
「系统全权、用户改了就改回来」→ 那就不是「人能写」;
「撞车就报错拒绝」→ 一次手滑让整张图连线全废。

### 2.5.5 ⚠️⚠️ 共用什么、不共用什么(切错就要返工)

`00 §5` 已定:「共用的是 **G 层与同步机制**,**不是 S 层模型**」;
`02 §1` 已定:「**不要试图让 bpmn 复用 mind 的 `parent` / 树推导规则**」。

⭐ **本节遵守同一条线:共用记法,不共用语义。**

```
┌─ ⭐ 共用(本节,图种无关)────────────────┐
│  · +++ 开合、就是 paragraph、零新块        │
│  · 分隔线 decoration、toggle 折叠          │
│  · key: value 通用词法                    │
│  · 别名 A/B/C ↔ block id 映射机制          │
│  · slash 入口                             │
│  · ⭐ 未知行原样保留                       │
└──────────────────────────────────────────┘
         ↓ 各图种自定「块里认哪些词」
   mind:  -.支撑.-> C   联系线 = 树之外的**附加**关系
   bpmn:  --> C         序列流 = **骨架本身**,可汇合、可回边
   画板:  也许只有 shape/color,无关系行
```

⚠️⚠️ **同一行 `A --> B` 在两个图种里含义不同** ——
mind 里一个节点只能有一个父,bpmn 允许汇合和回边。
**共用解析器可以,共用含义不行。**

### 2.5.6 ⭐ note 本体不认(用户拍板方案丙)

| 在哪 | `+++` 会怎样 |
|---|---|
| ⭐ **普通 note** | **不认** —— 就是三个加号,note **一个字符都不用改** |
| ⭐ **任何图形化 view**(导图/画板/BPMN) | 认:画分隔线、可折叠、解析成语义 |

> 用户原话:「这就是 note 的可扩展性,等于在 note ⇄ graph 增加了映射的能力。」

⭐ **note 不需要认它** —— 只要**忠实保存**这几行文字就够了,解释权在图种手里。
这正是分区原则第三条「**不认识的一律原样保留**」的典范(`04 §0.6.3`)。

⭐ 通道是**双向**的:note 里写 `+++` → 画布长出图;画布上连线 → `+++` 区自动出现。

⏳ **将来的呈现选项(不是现在做)**:整篇隐藏所有 `+++` 区的 per-view 开关。
⚠️ 现在不做的理由:折叠已解决绝大部分干扰;而整体隐藏会让用户
**看不见它存在**却改了标题/删了节点,产生「明明删了怎么还有条线」的困惑。
它是纯 UI 开关,随时能加,不影响数据格式。

### 2.5.7 ⭐⭐ 正式名称:**def 块**(图定义块)

> 用户 2026-09-13:「我觉得 meta 或者 def?简单而且**未来可能还可以表达更加丰富的语义**呢?」

⭐⭐ **这块东西的正式名称是 `def` 块(graph definition block)。**
文档、代码、UI **三处统一用这个词**,不再叫「元数据区」(那是描述,不是名字)。

#### 为什么是 `def` 不是 `meta`

⚠️ 我起初倾向 `meta`/`graphmeta`,**用户的取名尺度更高,已采纳**:
名字不该只对今天的内容合身,要给**还没想到的东西**留地方。

| | 装得下 | 会不会限制未来 |
|---|---|---|
| `meta` | 属性 ✅ / ⚠️ 关系 ✗ | ⚠️ 「关于某物的数据」**明确排除本体**。关系已经不是 meta;将来的行为、约束、样式规则更不是 |
| ⭐ `def` | 属性 ✅ 关系 ✅ | ⭐ 「**定义**」几乎装得下一切:定义节点 / 关系 / 样式 / 行为 / 约束 |

⭐ 关键论据:**联系线不是「关于某个东西的数据」,它就是那个东西**。
叫 meta,后来人会以为这块只能写属性 —— 而「⭐ 任意 def 块内可写任意两点连线」
恰恰是本设计最有价值的一条(`§2.5.3`)。

⭐ 且 `def` 正是用户最初的原话:「节点和节点联系,**对节点进行定义**」——
名字与原始意图同词,说明它抓住了本质。
⚠️ 反面:`meta` 的边界说不清,以后有人往里写关系会犹豫「这算 meta 吗」——
**名字引发的犹豫就是设计债**。

⚠️ 另注:`graph` 在本仓库已指**画板**(`graph-canvas-view` / `graph_canvas` /
`GraphVariant`),故 slash 命令不用 `graph` 打头,避免被读成「画板专用」。

#### slash 入口

⚠️ 光有记号不够:**用户不知道要写什么**(`id:` 还是 `ID:`?`-.->` 还是 `-->`?)。
⭐ slash 一敲**直接生成骨架**,并**自动分配别名** —— 方案丙「系统兜底」的自然落点。

```
/def  →  在 hn 之后插入:

        +++
        id: A          ← ⭐ 别名已自动分配(A/B/C 顺序,天然不撞)
        +++            ⚠️ 光标落在这里(id 行末),用户接着往下写
```

| 项 | 值 |
|---|---|
| `label` | `Graph Definition` |
| ⭐ `keywords` | `['def', 'graphdef', 'meta', 'graphmeta', 'diagram', '定义', '图元', 'gd']` |
| 行为 | 插入 def 块骨架 + 自动分配别名 + ⚠️ 光标置于 `id:` 行末 |

⭐ **名字只有一个,入口可以很多** —— 打 `/meta`、`/图元`、`/graphmeta`
都搜得到同一项。这条把「叫什么」的分歧降到最小:
⭐ 用户按自己的说法搜,文档与代码只认 `def`。

⚠️ **注册到图种自己的 viewId**(mind = `MIND_SEMANTIC_VIEW_ID`),
⭐ **绝不注册到 `note-view`** —— 否则就是给 note 加了图种专属功能,撞铁律。
先例:mermaid / math 那几项走的就是这条路。

⏳ **未定(记账)**:def 块**已存在**时再敲 `/def` 的行为
(追加一行?跳过?聚焦已有块?)—— 实现时定,倾向「聚焦已有块不重复插」。

### 2.5.8 ⭐ 设计取向:像 mermaid,少发明

记法越接近 mermaid,**AI 越会写**(模型见过海量 mermaid 语料),
用户迁移成本越低。⭐ 副产品:AI 可直接生成带 `+++` 的 markdown,
粘进 note 就是一张图。

⚠️ 这不是现在要做的功能,但它**约束语法设计**:不发明独有符号,
能抄 mermaid 就抄。

### 2.5.9 ⚠️ 落地节奏:只在 mind 落地,不预建通用能力

⭐ 规格分两层写(本节 = 通用记法;`01 §7.7` = mind 词表),
但**代码只在 mind 落地**,按「将来会有第二个使用者」的形状写
(纯函数、不绑树假设)。

⚠️⚠️ **不预先建 `diglot-notation` 通用能力目录** ——
现在只有一个真实使用者(bpmn 未开工、画板未定),
**拿一个用例设计通用层,极易设计出「只适合 mind 的通用层」**。
等 bpmn 开工,它是第二个使用者,**那时才验得出抽象对不对**。

## 3. 所有权与落位规则(两个图种通用)

**S 面:纯语义,机器不动。** 增量锚定序列化,保注释、保顺序、保个性。

⭐ 语义面中键入的斜杠词(`/三角形`、`/float`)一律是**输入手势**:
落定后转化为对应的属性条目(归 G 面)或结构变更,**语义面本身不留属性 token**
—— 语义面百分之百为语义服务。

**G 面:用户可写,机器规范。** 用户可直接手写属性条目(`^arch color=red pos=420,180`);
每次编辑落定后机器重整为规范形。⭐ **体验类比 `terraform fmt`:随手写,松手变整齐。**
坏行不污染模型、行内标红。

**画布:操作分流落笔。**

| 操作类 | 落哪 |
|---|---|
| 结构操作(新建、连线、删除、改名、改层级) | **S 面** |
| 布局与样式操作(拖动、改色、折叠) | **G 面** |

⭐ **删除即缺省**:删去 G 面条目 = 该属性回到 auto。

## 4. 规范化纪律(G 层规范形)

- 条目按 `id` 字典序排列;条目内属性键按固定序(canonical 键名,英文)
- 坐标**量化为整数**,杜绝浮点噪声
- ⭐ **不写缺省值**(稀疏纪律:缺席即 auto)
- 词表值存 canonical 名(中英别名在输入层互通)
- ⭐ **规范化幂等**:对规范形再序列化,**字节级不变**

平文本投影中 G 层落于文末附录区,包裹于 HTML 注释,
使文件在任何 Markdown 环境**渲染为干净大纲**:

```
<!-- diglot
^arch pos=420,180
^root structure=logic
^todo float pos=-200,60 collapsed
-->
```

## 5. ⭐ G 层跨图种稳定

> 原规格 §7:「**图形描述面跨图种稳定**:更换的是语义面文法与画布渲染;
> G 面永远是 `^id key=value` 属性面 —— **用户学一次全图种通用,实现一次全图种复用**。」

✅ **这条成立,且是拆分后仍共用的最大一块。**

⚠️ **但要读准**:共用的是 **G 层与同步机制**,**不是 S 层模型**。
mind 的 S 层是树,bpmn 的 S 层是有向图 —— **两者不共用,也不该共用**。

| ⭐ 共用(本文) | 各自独立(分文档) |
|---|---|
| 双向同步引擎 | S 层文法与实体 |
| G 层 `^id key=value` 属性面 | 画布图元与渲染 |
| 规范化纪律 | 布局算法 |
| 统一撤销栈(§7) | 快捷键(各自对齐行业惯例) |
| id 作为三面 join 键的选区同步 | |

## 6. 交互投影:left slot / right slot

- **left slot:文本侧**。两个书写面 —— **语义描述面**(主)与**图形描述面**(次,可切换)
- **right slot:画布侧**。渲染与交互
- **任一 slot 可全屏**:文本侧全屏 = 大纲模式;画布侧全屏 = 纯图模式

⭐ **同步是持续的,不是切换时的**:
左侧改标签 → 画布即变、G 面无涉;画布拖节点 → G 面多一条、语义面零变更;
G 面改颜色 → 画布即变、语义面零变更。**同步管道带方向标记抑制回环。**

**选区同步**:三个面共享「当前选中 id 集」。**id 是三面之间唯一的 join 键。**

---

## 7. ⭐ 撤销:一条时间线

**S 面、G 面、画布共享同一撤销栈。** `Cmd+Z` 按操作时序回退,**不分面**
—— 用户不区分「刚才那步落在哪层」。

⚠️ **实现约束**:同步引擎的每次落笔生成**可逆事务**,入统一历史。
**这是双面架构在手感上完整的前提。**

## 8. 不变量(通用断言)

以下六条**与图种无关**,两个图种都要各自验一遍:

- **C1 规范化幂等**:G 层规范形二次序列化字节级不变
- **C2 双射**:同一张图经任何编辑路径到达,序列化结果一致
- **C3 语义编辑最小性**:改一个标签 → 模型 diff 仅一个 update;
  ⭐ **全部 pos 存活**(id 配对,**绝不删旧建新**)
- **C4 图形编辑分层落笔**:画布拖动一个节点 → **仅 G 层一条条目变更**,S 层零变更
- **C5 缺省即自动**:画布新建节点 → S 层恰好一处插入,**G 层零条目**
- **C6 错误隔离**:S 面坏语法 / G 面坏行**均不污染模型**,画布保持上一有效状态,错误定位到行
- **C7 释放语义**:删除一条 G 条目 → 该元素回自动布局,**其余一切不变**
- **C8 手势消解**:语义面键入斜杠属性词 → **S 层零残留**,G 层恰好一条条目

⭐ **加一条 mermaid 起步期专属的**:

- **C9 round-trip 不破坏**:导入 mermaid → 编辑 → 导出 → 再导入,
  **图一致;未知记号原样透传不丢失**

> 断言即 CI 测试用例,**先于任何交互代码存在**。
