## 1. 这个图种的语义骨架:**树**

⭐ **mind 的 S 层真相是父子关系。** 与 bpmn 的有向图**完全不同**,不共用。

| | mind(本文) | bpmn(`02`) |
|---|---|---|
| 骨架 | ⭐ **树**(`parent` 是真相) | ⭐ **有向图**(边是主结构) |
| 边的性质 | **联系线**:树之外的**附加**关系 | **序列流**:骨架本身 |
| 有汇合吗 | ❌ 一个节点只有一个父 | ✅ 多条分支可合并 |

## 3. 实体清单

### 3.1 Node(节点)

| 属性 | 层 | 类型 | 缺省 | 说明 |
|---|---|---|---|---|
| `id` | S | 稳定标识 | 自动分配 | ⭐ **两层之间的外键**,选区同步的 join 键。KRIG = block id;平文本 = `^id` |
| `content` | S | 富文本 | 必填 | ⭐ **首段为节点标签**(图上显示),**其余为备注**。KRIG 中 content 即 note block 本体 —— **公式、行内格式、图片、超链接天然承载**,XMind 需专门机制的富内容**整类白送** |
| `parent` | S(推导) | Node 引用 | 按 §4 推导 | ⭐ **真相是父子关系,不是层级数字**。层级是书写表面,parent 是解释结果 |
| `order` | S(推导) | 整数 | 书写顺序 | 兄弟间次序 |
| `role` | S(推导) | `root \| branch \| floating` | `branch` | root = 文档标题;标 `float` 者为自由主题(父为 Document) |
| `ref` | S | 不透明字符串 | 无 | 外部引用:content 为 `[[ref]]` 时指向另一文档/块。**嵌套(zoom-in / XMind 钻取)由此实现** |
| `labels` | S | 字符串集 | 空 | 自由文本标注(XMind label) |
| `markers` | S | 词表项集 | 空 | ⭐ **受控标记**(优先级 1–5、进度、旗帜):**枚举词表,可排序可比较可过滤**。与 labels 分设 —— 合并会丢掉枚举语义。KRIG 中为三元组,**「全库高优先级节点」是一句查询** |
| `shape` | G | 词表项 | `auto` | 形状。词表开放可注册,中英别名互通 |
| `color` | G | 词表项/色值 | `auto` | v0 样式最小集只收 color |
| `pos` | G | `(x,y)` 整数 | 无(= auto) | ⭐ **pos 存在即 pinned**:写入即钉住,删除即释放 |
| `structure` | G | 词表项 + 参数 | `inherit`(根 `map`) | ⭐ **该节点子树的布局算法,可挂任意节点、向下继承**(XMind 分支级结构混用) |
| `collapsed` | G(V 类) | 布尔 | `false` | ⭐ **折叠是属性不是类型**:一切节点天然可折叠。**持久** |

**`structure` 词表**(按 XMind 十结构全集登记):
`map`(顺/逆时针参数) · `logic`(左右向) · `brace` · `org`(上下向) · `tree` ·
`timeline` · `fishbone`(左右头) · `tree-table` · `matrix`

⭐ 方向变体是**参数**(`structure=fishbone dir=left`)而非独立词条。
**v0 实现 `map` 与 `logic`**,其余登记名称、布局算法后续实现。

### 3.2 Edge(联系线)

⚠️ **注意:这是「非树连线」,是树之上的附加关系** —— 与 bpmn 的序列流性质不同。

| 属性 | 层 | 说明 |
|---|---|---|
| `source` / `target` | S | ⭐ **模型统一存有向**;无向语义由渲染**弱化箭头**表达 |
| `label` | S | 关系标签 |
| `id` | S | 可显式命名以便外部挂靠 |
| `waypoints` | G | 手动走线,稀疏纪律同 pos |
| `style` | G | 线型/色 |

⭐ **两端强制显式 id** —— 显式 id 的激励设计:**想连线,先命名**。
⚠️ 但**不报错拒绝**:端点无显式 id 时系统**即时生成人类可读 id 并落两面**(见 §7.4)。

KRIG 投影:`relates(source, target) {label}` 三元组 —— **联系线直接就是图谱边,天然可查询**。

### 3.3 Span(区间引用:概要 / 边界)

对**一段连续兄弟节点**的引用实体。XMind summary 与 boundary 的共同本质,
也是 KRIG「框选一段 blocks 建立关系」Canvas 原语的先声。

| 属性 | 层 | 说明 |
|---|---|---|
| `kind` | S | `summary`(框住并挂结论) / `boundary`(仅框住) |
| `from` / `to` | S | ⭐ 同父连续兄弟段的首末**锚点。锚在 id 上,节点移动/更名不破坏区间** |
| `topic` | S | 概要的结论节点:本身是 Node,父挂 Span |
| `style` | G | 框线样式 |

**书写入口**:summary 有语义面入口(`/sum` 手势);boundary v0 **仅画布入口** ——
依据收录门槛「**有人会用文字手写它**」。

### 3.4 Document

| 属性 | 层 | 说明 |
|---|---|---|
| `type` | S | `mind` —— ⭐ **文档类型 = 解释器选择**。**同一 blocks 数据可按大纲或导图解释,切换零转换** |
| `title` | S | ⭐ **标题即 root**:Note 标题为中心主题 |
| `theme` | G | 全局主题/配色 |

⭐ **Sheet 对应**(XMind 用户迁移锚点):多 sheet = 多个 mind Note;
**「从主题新建 sheet」= 子树摘出为新 Note、原位留 `[[ref]]`**
—— block 架构「任意块提升为独立文档」的**既有操作,零新机制**。

## 4. ⭐ 树推导规则(书写表面 → 父子真相)

输入是**扁平序列**:KRIG 为「带 h 级别的 block 序列」,平文本为「带缩进的行序列」。
两者同构,推导规则唯一:

1. `parent(n)` = 序列中 n 之前、级别小于 n 的**最近**节点;不存在则父为 root
2. ⭐ **级别跳跃宽容解释**:h1 下直接出现 h3,按规则 1 归就近父级,
   **不报错、不改写用户书写**
3. `order` = 同父兄弟间的序列先后
4. 标 `float` 的顶层节点父为 Document(自由主题)
5. 推导是**确定的纯函数**:同一序列必得同一棵树

⭐ **层级数字永不落库。** 移动子树 = 改一条 parent 引用 / 平移缩进块,
**后代无需重编号**。`/h1…/hn` 与 Tab/Shift-Tab 是升降级**手势**,落成的是父子关系变更。

### 7.0.1 ⭐ 为什么这么切(消歧理由)

| 冲突 | 裁决 |
|---|---|
| 改父:拖框 vs 拖端点 | ⭐ **归拖端点** —— 端点有 magnet 提示,**看得见要连到哪**;拖框全靠猜(⚠️ 落点预览至今没做,见 7.0.4) |
| 改序:能不能拖端点做 | ⚠️ **机制上做不到** —— 端点只表达「挂给谁」,**没有「排第几」的信息**。故改序**必然**归拖框 |
| 拉线起手式 | ⭐ **磁吸点**,不是「框上任意处」——⚠️ 后者与「拖框改序」是同一起手式,机器分不开。命中优先级 1.7(magnet)早于 2(节点拖动),**天然分得开** |
| `Alt` 会不会挪作拉线 | ⚠️ **不挪** —— `Alt`+拖=钉坐标已实现且是 XMind 同款;而钉坐标**必须拖**(要落到具体像素),菜单替代不了 |

⚠️ **拉线按源节点身份分流**(不必两个手势):

| 源节点 | 拖出连线到目标 | 结果 |
|---|---|---|
| **自由主题** | 任意节点 | ⭐ **回树**:parent=目标,role→branch |
| 普通节点 | 任意节点 | ⭐ **联系线**:加一条 Edge,⚠️ 树不动 |

⭐ 理由:自由主题本来就没爹,拉线自然是认爹;有爹的拉线自然是附加关系。

### 7.0.2 ⚠️ 已知 bug:同父拖到**末位**无反应

`resolveDropTarget` 末尾:
```js
if (dragged && dragged.parent === newParent && !before) return null;
```
⭐⭐ 同父调序时若目标是**最后一位**,`before === undefined` → 直接 `return null`
→ 不产生变更,且调用侧走 `needsRelayout` **把节点弹回原位**。
⚠️ 即:**同一个父下面,没法把节点拖到末尾**。改序既然归拖框专职,这条必修。

### 7.0.3 ⚠️ 节点浮条:不是没做,是被 variant 挡掉

`GraphCanvasView.tsx`:
```jsx
{activeGraphId != null && activeVariant === 'canvas' && <GraphCanvasNodeToolbar .../>}
```
⭐ `node-toolbar` 本身是 **view-agnostic 共享 capability**(画板在用),
导图被 `variant === 'canvas'` 排除。
⚠️ **但不能简单去掉这个判断** —— 浮条依赖 `hostRef`,而导图走 **MindCanvas 自己的 Host**,
`GraphCanvasView` 的 `hostRef` 在导图下**恒为 null**(与缩放控件同一个坑)。
必须把导图自己的 host 传进去。

⭐ 分工:**浮条管外观**(上色/字体/shape),**右键菜单管结构**
(转自由主题/挂回树/改父/解钉/删除)——⚠️ 两处不重复放同一项。

### 7.0.4 ⚠️ 落点预览:规格要求但**一项都没做**

§7.2 明写「拖动预览必须在松手前区分三义:缝隙插入高亮 / 钉住虚影 / 自由主题标识」。
⭐ **实测:三种预览一个都没有** —— 这正是用户说「拖动框有可能无法对准自己需要的部分」的根因。
⚠️ 注释里还留着实测踩坑:「左→右布局下同层节点 x **完全相同**(分支A/分支B 都在 x=117)
…… 拖到分支B 旁边却归给了分支A」。

⭐ 职责一拆(拖框只在**同父兄弟**里按 y 排序),这个坑**自然消失** ——
不必再猜「落点左边最近的是谁」。

### 7.2 ⭐⭐ 拖动三义分流(本图种核心约定)

> ⚠️ **v0.2 修订(2026-09-10,用户拍板)**:裸拖由「钉住坐标」改为「**改父/改序**」。
> 自由摆位下沉为修饰键手势。见 §7.2.1 修订理由。

| 拖动落点 | 语义 | 落笔 |
|---|---|---|
| 另一节点上 / 兄弟缝隙间 | **改父 / 改序** | S:parent/order 变更 |
| ⭐ **空白处(裸拖)** | **改父 / 改序**(就近归位) | S:parent/order 变更;**G 零** |
| `Alt` + 拖动 | **钉住坐标**(自由摆位) | G:一条 pos 条目 |
| ~~`Shift` + 拖动~~ | ⚠️ **已改为右键菜单**(§7.0,2026-09-13) | — |

⚠️ **拖动预览必须在松手前区分三义**:
缝隙插入高亮(结构)vs 钉住虚影(布局)vs 自由主题标识。
对应 XMind 的 drag-reparent / Alt-drag 自由摆位 / Shift-drag 转 floating。

> ⚠️⚠️ **2026-09-13 修订(用户拍板):大纲侧升降级的入口不是 `Tab`。**
>
> 原文写「大纲侧 Tab」是照搬 XMind。但 mind 的大纲侧**不是 XMind 的大纲**,
> 它是一个**真正的 note 编辑器**,而 note 里 `Tab` 早有三种既定行为
> (块缩进 / 插两个全角空格 / `Cmd+Shift+I` 首行缩进)。
>
> ⭐ 实测:大纲侧改层级**本来就做得到** —— 把块从 h2 改成 h3,
> `parent` 自动跟着变(层级由 heading level 推导,不是 `parent` 字段)。
> 入口是 **slash 的 h1~h6** 与 **⋮⋮ handle 的 turn-into**,两个都是 note 原生的。
>
> ⭐⭐ **总原则(用户原话)**:
> 「**我们要让 mind 来适应 note 的编辑方式,除非 note 本身改变了。**」
>
> 故大纲侧**不为 mind 另派键位、也不关闭 note 的既有键位** ——
> `Tab` 在这里就是 note 的 `Tab`,一模一样。
> ⚠️ 曾试过给 mind 加 per-instance 开关关掉 `Tab`(理由:它会把两个全角空格
> 插进标题,而标题文字就是画布上的节点名),**已被用户否决并整体回退** ——
> 一致性本身就是价值,开关就是「规则裂成 N 套」的口子。
> 完整判例与推论见 `03-projection-map.md` §5.9.2.2。

#### 7.2.1 ⭐ 修订理由:导图的位置是**算出来的**,不是摆出来的

真机实测(2026-09-10)暴露的问题:拖一个叶子出去 → 它被 pinned 在落点,
**其余节点仍按自动布局排** → 两套坐标混在一起,整张图立刻变丑,
而且**再也回不去**(没有释放入口时,pinned 是单向的)。

⭐ 根因是**心智模型套错了**:

| | 自由画板 | ⭐ 思维导图 |
|---|---|---|
| 位置的性质 | **本体** —— 我放哪就是哪 | ⭐ **派生** —— 由结构算出来 |
| 用户关心 | 视觉布局 | **谁是谁的子节点、谁排在谁前面** |
| 拖动的含义 | 移动 | ⭐ **改结构** |

XMind 的默认行为正是如此:**裸拖 = 改结构,自由摆位要按 Alt**。
v0.1 把「拖到空白 = 钉坐标」做成默认,等于把画板的心智套在了导图上。

⚠️ **这条修订不推翻稀疏纪律**:`pos` 仍然「存在即 pinned、删除即释放」(C7),
只是**产生 pos 的入口**从「裸拖」收窄为「Alt+拖」——
默认路径下 G 层保持为空,图永远整齐(缺省即自动,C5)。

## 7.7 ⭐⭐ mind 的 `def` 块**词表**(块与词法归 note,见 `00 §2.5`)

> ⭐⭐ **归属(用户 2026-09-13)**:`def` 块是 **note 的能力**,mind 是**调用者**。
> note 提供**块 + 词法**(有这么个块、`key: value` 与关系行、怎么存怎么渲染);
> ⭐ 本节只定 **mind 的词表与含义** —— `role:` 是什么、`-.->` 是联系线。
> ⚠️ 前一版把解析实现放进 `diglot-model/`,**已整体回退**(见 `00 §2.5.9`)。

> `00 §2.5` 定的是**记法**(图种无关);本节定 **mind 在块里认哪些词**。
> ⚠️ 同一行 `A --> B`,mind 是「树之外的附加联系线」,bpmn 是「骨架本身」——

### 7.7.1 认哪些行

```markdown
# 技术选型
+++
id: B                  ← ① 别名声明
shape: 菱形            ← ② 图形定义 → ⚠️ 落 G 层
color: red             ← ②
marker: p1             ← ③ 语义定义 → ⚠️ 落 S 层
B -.支撑.-> C          ← ④ 联系线 → 落 S 层 Edge
# 这行是注释                ← ⑤ 忽略
随手写的一句话              ← ⑥ ⭐ 不认识 → **原样保留**
+++
```

| # | 形态 | 落哪 | 说明 |
|---|---|---|---|
| ① | `id: <别名>` | — | 本文档内唯一;冲突自动加序号(`00 §2.5.4`) |
| ② | `shape:` / `color:` / `structure:` | ⚠️ **G 层** | 图形属性,稀疏覆盖(C7:删条目=回自动) |
| ③ | `marker:` / `label:` | ⚠️ **S 层** | 语义属性(`markers` 受控词表 / `labels` 自由文本) |
| ⭐ ③b | `role: floating` | **S 层** | ⭐ **自由主题的 note 表达**(用户 2026-09-13 拍板),见 7.7.7 |
| ④ | `<别名> -.<标签>.-> <别名>` | **S 层 Edge** | ⭐ 见 7.7.2 |
| ⑤ | `#` 起头 | — | 注释,解析忽略,⭐ 写回时保留 |
| ⑥ | 其它 | — | ⭐⭐ **原样保留**,不报错、不删(`04 §0.6.3`) |

⚠️⚠️ **同一个块里写、落到两个层去** —— 这条必须钉死,否则打穿 `00 §3` 分层。
⭐ 有现成范式:`semantic.slashShape` 就是「语义面手势 → 消解成 G 条目,S 零残留」(C8)。

### 7.7.2 ⭐ 联系线的语义(mind 专属)

```
B -.支撑.-> C      虚线箭头 + 标签 = 联系线
B -.-> C           无标签
```

| 性质 | 说明 |
|---|---|
| ⭐ **树之外的附加** | ⚠️ **不改变任何父子关系**;树纹丝不动 |
| **任意两点** | ⚠️ **不限叶子** —— 根/分支/叶子/自由主题皆可 |
| ⭐ **方向敏感** | `A→B` 与 `B→A` 是两条边,**绝不排序两端**(`03 §3.6`) |
| ⭐ **确定性 id** | `deterministicEdgeId(source,target)`,重复连同一对 = **覆盖非新增**(债 3 已做) |
| **写在哪都行** | ⭐ 任意 `+++` 块内(`00 §2.5.3`) |
| 删除连带 | 端点被删 → 悬空边清理(§7.1 删除那行已定) |

⚠️ **`-->`(实线)在 mind 里不认** —— 树的父子由 hn 层级表达,
不该有第二种写法。留给 bpmn 当序列流。

### 7.7.7 ⭐⭐ `role:` —— 自由主题在 note 里怎么表达(用户 2026-09-13 拍板)

⭐ **两条规则各管一件事,不打架**:

| 管什么 | 谁表达 |
|---|---|
| **层级**(是不是顶层) | ⭐ **h1** —— 用户口径「**每个 h1 都是一个主题**」 |
| **身份**(root 还是 floating) | ⭐ **def 块的 `role:`** |

```markdown
# 主题                  ← 顶层 · 首个 → root(隐式,照旧)
## 分支A

# 另一个想法            ← ⭐ 仍是 h1(顶层)
+++
role: floating          ← ⭐ 把身份**写明**
+++
```

**优先级**:写了 `role:` **以它为准**;没写则回落既有隐式规则
(§4 第 4 条:首个顶层为 root,其余为 floating)。⭐ **向后兼容**,老文档照旧工作。

⚠️ **为什么需要显式**(隐式规则的三个毛病,实测):
1. **看不出来** —— 「第一个 h1 是 root」只存在于代码里,note 面板上两个 h1 长得一样
2. ⚠️ **顺序一变身份就变** —— 把第二个 h1 挪到最前,它就成了 root。⭐ 身份靠位置维系,与债 6 同源
3. **右键「转自由主题」在 note 侧看不出发生了什么** —— 有 `role:` 行才有落点

⚠️ **不用 Tab 表达自由主题**(曾考虑):Tab 表达「更深一层」,
而自由主题的本质是**顶层**(父为 Document)—— 用缩进表达它自相矛盾。
⭐ 且 Tab 在 mind 语义面已定「什么都不做」(`03 §5.9.2.2`)。

⚠️ **副作用(要如实告知用户)**:右键转自由主题会把该块提到顶层(h2→h1),
note 里那段文字**位置会移动**。这不可避免 —— 它真的变成顶层了;
⭐ 但有 `role: floating` 写着,用户看得懂为什么。
