## 1. ⭐⭐ 四个面各是什么(先分清,再对应)

| 面 | 是什么 | 谁写 | 完整性 |
|---|---|---|---|
| **S 层** | 图「**是什么**」:树、内容、标注 | ⭐ 用户书写,**机器不改写** | 全量 |
| **G 层** | 图「**长什么样**」:坐标、样式、折叠 | 用户可写,**机器规范化** | ⭐ **稀疏** |
| **DB** | 怎么落库 | 机器 | 全量 |
| **Instance** | 画布运行态 | 引擎生成 | 全量 |

### 1.1 ⚠️⚠️ Instance ≠ G 层(最容易犯的错)

```
Instance { id, type, ref, position, size, endpoints, doc, ... }
                         ↑ 每个节点都必须有,否则画不出来
```

`Instance.position` 是**全量**的 —— 没有坐标就渲染不了。
G 层的铁律恰恰相反:**只有被碰过的元素才有条目**(`00 §1.3` 稀疏纪律)。

> ⚠️ **把 G 层直接存成 `Instance[]` 会当场违反稀疏纪律,C5 / C7 全废。**
> (C5:画布新建节点 → S 层一处插入,**G 层零条目**)

正确关系是「**稀疏覆盖全量**」:

```
S 层(树) ──推导──┐
                 ├─→ ELK 自动布局(全量坐标) ─→ Instance[](喂画布)
G 层(稀疏 pos) ──┘   ⭐ 有条目的覆盖自动值;没条目的用算出来的
```

⭐ **一句话:G 层是「对自动布局的稀疏覆盖层」,不是画布状态的存档。**
想清楚这句,C5 / C7 / M3 才有可能真绿。

## 3. ⭐⭐ 落库模型:文档本体零边(用户 2026-09-09 拍板)

> 用户原话:「**先以文档作为存储单元,尽量少边的关系,
> 边的错误不会影响文档的完整性、正确性。**」

⭐ **这不是新决定,是 `Decision 028` 的复用** ——
而 028 是被一次**真实事故**打出来的。

### 3.1 事故与教训(为什么树绝不能靠边)

[028](../../90-archive/refactor-v2/data-model/persistence/decisions/028-block-structure-via-attrs.md) 触发场景:

> 一篇正常长笔记(数百 block)新建 image 后,**重启重新打开,块顺序错乱**。
> image 内容其实存对了,**坏的是顺序**。

根因(028 §1.3 原文):

> **根本矛盾:用「一堆独立的关系边」表达「一个文档的线性结构」,
> 把本该原子的东西(文档=有序块树)拆成了几百个可独立失败的写操作。**

当年结构靠三类边(`belongsToNote`/`childOf`/`nextSibling`),几百条边
**必须全部正确且无冗余**,任一条写错/写重/没删 → 整篇结构坏,
且 **`putEdge` 不幂等 → 损坏累积、不可逆**。

拍板结论(用户 2026-06-08):

> **一个原始文档,不应该包含任何边关系。** 边只在**需要关系化**时才创建。

**且已落地跑着**:`src/platform/main/note/assemble-pm-doc.ts` 现在就是
「按 `noteId` 拉全部 → 按 `parentId` 建树 → 同级按 `order` 字典序排」,**零边遍历**。

### 3.2 ⭐ mind 的树 = note 的块树(同一个结构,不是两个)

| mind 模型 | 已有 block 属性 | 要新造吗 |
|---|---|---|
| `parent` | `parentId` | ❌ **现成** |
| `order` | `order`(lexrank 字典序串) | ❌ **现成** |
| 归属某张图 | `noteId` | ❌ **现成** |
| `content` | block 本体 | ❌ **现成** |

⭐ 由此,`01 §4` 那句「**层级数字永不落库,移动子树 = 改一条 parent 引用,
后代无需重编号**」**字面成立** —— lexrank 中插只写 1 块
(整数序号中插要把后续全部 +1,写放大 N 块)。

⭐ 且 **M3「子树移动后全部 pos 存活」天然成立**:
改 `parentId` 不触碰任何 id,G 层按 id 配对当然存活。
规格要求「id 配对,**绝不删旧建新**」—— 属性化模型下**根本没有删旧建新的机会**。

⭐ 于是 `01 §3.4`「**同一 blocks 数据可按大纲或导图解释,切换零转换**」也字面成立:
mind 文档就是一篇 note,`type=mind` 只是选了个解释器。

### 3.3 三类东西的落位

| 类 | 落法 | 理由 |
|---|---|---|
| ① **树骨架** | ⭐ **零边,纯属性**(`parentId`/`order`/`noteId`) | 028;全现成 |
| ② **G 层** | ⭐ **零边,note 内单独一个 G 层 block**(纯文本 `^id key=value`) | 见 §3.4 |
| ③ **联系线 Edge** | ⚠️ **`relates` 边**(唯一真用边处) | 总纲「业务关系」类,该建边 |

### 3.4 为什么 G 层存成 note 内一个 block

- **C1 幂等验的是字节** —— 存字符串才验得动(存结构体只能验对象相等,弱得多)
- 跟着 note 走**一套持久化**,不新增写路径
- ⚠️ **一个 block 一次写 = 一次原子写**。G 层坏了最多这一块坏,**坏不出「半张图」**
- 稀疏纪律天然:没条目就是没那行

平文本投影形态(`00 §4`,包裹 HTML 注释使 Markdown 环境渲染为干净大纲):

```
<!-- diglot
^arch pos=420,180
^root structure=logic
^todo float pos=-200,60 collapsed
-->
```

### 3.5 ⭐⭐ 硬约束:边坏,树不坏

用户原话:「**边的错误不会影响文档的完整性、正确性。**」

钉成可执行判据:

> **把一张 mind 的全部 Edge 行整批删除 / 整批损坏 → 重新打开,
> 树结构、每个节点 content、全部 G 层条目 —— 逐项一致。**

⭐ **这条能真失败**:哪天有人图省事把树也存成边,它立刻红。
**它守的正是 028 那个事故不再重演。** 编号 **M5**,见 §5。

### 3.6 ⚠️ Edge 必须用确定性 id(记账)

028 §1.2 记着 `putEdge` **不幂等**:无 id 时 `generateUlid() + CREATE`,
每次 put 同一条逻辑边**产生新行**,SurrealDB 不去重 → 重复累积。

联系线量小,累积不像树那样致命,但「**拖一下多一条边**」仍是 bug。

对策:**Edge 用确定性 id**(`01 §3.2` 本就要求两端强制显式 id、
「想连线先命名」),重复写同一条逻辑边 = **覆盖而非新增**。

✅ **已实现**(用户拍板 v0 做掉):`src/capabilities/diglot-model/edge-id.ts`

id 形态 `rel_<source净化>_<target净化>_<fnv1a(source␀target)>`,性质:

| 性质 | 为什么必须 |
|---|---|
| **确定** | 同参永远同输出,跨进程跨重启 —— 这是「覆盖而非新增」的前提 |
| ⭐ **方向敏感** | `01 §3.2` 统一存有向。**绝不排序两端** —— 否则 A→B 与 B→A 塌成一条,用户画的边被悄悄覆盖 |
| **分隔符取 NUL** | 用户手写 `^id` 可能含空格/下划线;可打印分隔符会让 `("a_b","c")` 与 `("a","b_c")` 撞 |
| **hash 吃未截断全文** | 否则超长 id 仅前缀相同就撞 |
| **净化非法字符** | 平文本 `^id` 是用户写的,可能含中文/标点,需产出合法 record id 段 |

⚠️ **调用侧配套契约(本模块给不出)**:`putEdgeViaTx` 的 `input.id` 分支走
`UPDATE ... RETURN AFTER`,**边不存在时抛 `Edge <id> not found`**。
故写联系线**必须走 UPSERT 语义**(仓库先例:`schema.ts` 用 UPSERT 避免重复 CREATE),
否则「第一次连线」直接失败。此契约由接线时的 M5/E1 断言守。

断言:`tests/capabilities/diglot/edge-id.test.ts`(10 条,**全部注入验过能红**)。
⚠️ 其中注入 3 抓到一个真缺口:E4 初版样本**不含分隔符本身**,
改 SEP 后照样全绿(零区分力)—— 已改真碰撞对,详见该文件台账。

## 5.5 ⭐⭐ 节点 = 标题 + 它的正文(2026-09-10 用户拍板,**改了 §2 对照表**)

> 用户原话:「主题框可以映射多个 block,首行取自 hn,第二行以后,取自正文或其他。
> **要默认它作为一个整体才行。**」

### 5.5.1 改之前是什么样(以及为什么不对)

`noteDocToTree` 把 `heading` 和 `paragraph` **一视同仁**地当树节点:

```
note:   # 主题2                    →  节点 A「主题2」
        $x^2+2$   (紧跟的段落)     →  ⭐ 节点 B(独立!)
```

⚠️ 于是「标题下面写一行正文」会**凭空多出一个节点**。真机现象是公式看着像
从主题框里溢出来 —— 其实它压根不在那个框里,**它自己就是个框**
(mathInline 没有可见文字宽度,框塌成一条缝)。

⭐ 排查教训:我一开始把它当成「框装不下内容」,连改了撑高 / insetY / 几何重渲
三轮都没解决 —— 因为**内容根本不在那个框里**。用户先一步指出「问题出在
note 和 shape 的映射」。**现象相似不代表根因相同**。

### 5.5.2 现在的规则

| note 里的块 | 归属 | 依据 |
|---|---|---|
| `heading` (h1~h6) | ⭐ **开一个新节点**,是该节点的**首行** | 深度 = level - 1 |
| `paragraph` **带 `indent ≥ 1`** | ⭐ **开一个新节点**(h6 之后的层级) | 深度 = 6 + indent - 1 |
| `paragraph` **无 indent** | ⭐⭐ **并入上一个节点**,作为它的第 2 行及以后 | 正文,不是层级 |
| 其它块类型 | 同上,并入上一个节点 | 正文 |

⭐⭐ **两条规则不冲突的原因**(实测验证过):
`noteFormForDepth` 产出的层级段落**永远带 `indent ≥ 1`**
(depth 6 → indent 1,depth 7 → indent 2 …),**从不产出无 indent 的段落**。
所以「无 indent 的 paragraph」这个形态是空出来的,拿它表示正文**不会撞**。

⚠️ 边界情形:文档**以无 indent 的 paragraph 开头**(前面没有任何 heading)——
没有「上一个节点」可并入。此时它**自成节点**(维持旧行为),否则内容会凭空消失。

### 5.5.3 ⚠️ 两个方向必须严格互逆

- 正向 `noteDocToTree`:heading + 后续无 indent 段落 → **一个** SNode,
  `content` 里装**多个块**
- 反向 `treeToNoteDoc`:一个 SNode 的 content 有 N 个块 → 首块按深度取
  heading/indent 形态,**其余原样 emit 成无 indent 的 paragraph**

⚠️ 反向若把正文也按深度加 indent,再正向读回来就变成层级 → **往返不收敛**,
节点会一轮轮增殖。这是本节最容易写错的地方,必须有往返断言钉住。

⚠️ `content` 信封从「单段落」变成「可多块」——
`inlineOf` / `contentToText` 只取首块的既有行为**仍然正确**(标签 = 首行),
但**画布渲染要吃全部块**,否则正文显示不出来。

## 5.6 ⭐⭐ S 层改存 note doc,mermaid 降为导入/导出(2026-09-10 用户拍板)

### 5.6.1 为什么必须改

⚠️ 实测(不是推理):节点正文**存盘即丢**。

```
内存 S 层:2 块(标题 + 公式)
  → toMermaidMindmap → "mindmap\n  root((主题2))"
  → parseMermaidMindmap → 1 块        ⭐ 公式没了
```

真因:`MindFile.semantic` 存的是 **mermaid 文本**,而 mermaid 的 mindmap 语法
**一个节点只有一行纯文本标签**,装不下「节点 = 标题 + 正文」(§5.5 用户拍板的语义)。

⭐ 现象很迷惑:note 面板显示正常(读内存态)、画布只剩标题(读存盘后的)。
**逐层查渲染链路全是对的** —— 分组 ✅ content 3 块 ✅ instance.doc 3 块 ✅
atom-bridge 全透传 ✅ atomsToSvg 遍历全部 ✅ —— 问题在**存储格式的表达能力**,
不在任何一层代码。排查教训:「每层都对但结果不对」→ 查**数据经过的格式**。

### 5.6.2 mermaid 到底能表达什么(实测,别高估)

| | 保住 | 丢弃 |
|---|---|---|
| 结构 | ⭐ 层级、兄弟顺序 | — |
| 标签 | 标题的**纯文本** | ⚠️ marks(加粗/颜色)、**行内公式** |
| 节点 | — | ⭐ **正文块**(第 2 块起)、图片 |
| 其它 | — | G 层坐标、折叠态 |

⚠️ 注意比直觉更窄:**连标题那一行也只剩纯文本** ——
`contentToText` 是 `runs.map(r => r.text ?? '')`,`mathInline` 没有 `text`,
**标题里的公式会变成空串**。所以 mermaid 不是「只丢正文」,是
「只保住**层级 + 标题纯文本**」的有损投影。

⭐ 这正是把它从真源降级的理由:它**本来就在丢东西**,
只是以前节点只有一行、没撞上。真源不该迁就兼容层的表达能力。

### 5.6.3 定位(用户口径)

> 「大概率不会导出 mermaid 的代码,应该是 **mermaid 导入**的情况居多。」

- **导入**(主用法):粘社区图例 / 现成 mindmap → 生成导图。**这条要做扎实**
- **导出**(次要):便利功能,不投入过度设计

### 5.6.4 ⚠️⚠️ 导入的硬约束:不许静默毁数据

现状 `handleChange`(MindSemanticPane)是**整份替换 S 层**:
解析 mermaid 文本 → 得到新 SLayer → 覆盖。

⚠️ 在 v1 语义下这条路径会**把每个节点的正文全删掉** ——
因为 mermaid 里根本没有正文,解析结果自然没有。
用户「点进 mermaid tab 看一眼」就可能毁数据,与 §7.3 variant 闸门同族。

⭐ 硬约束(落地必须满足):
1. mermaid 文本**没变**时,绝不重建 S 层(纯查看不改模型)
2. 导入若会覆盖已有富内容,**明确告知**丢什么、丢几处,不默默拍平
3. 解析失败只报错不改模型(C6 既有约束,保持)

## 8. ⭐ 债 6:稳定 id 与 C4 不可兼得(2026-09-10 实测)

### 8.1 现象

解析器按**行序**分配 id(`m001`/`m002`…)。用户在语义面中间**插入或删除一行**后,
其后所有节点的 id 整体位移 → G 层里原本钉在 `m003` 的坐标,落到了别的节点上。

⚠️ 改标签**不受影响**(树形没变、行数没变,id 不动);**只有增删节点会错位**。

### 8.2 ⚠️ 试过的解法,被断言挡回

思路:序列化时给「有 G 条目的节点」写显式 id(`m002[分支A]`),
解析器本就认这个语法(mermaid 文法规则 27 的 `id[descr]` 形态)。

**结果:C4 断言变红。** 因为:

```
拖动节点 → 产生 G 条目 → 序列化时给它补显式 id → 语义文本多出 `m002[...]`
                                                    ↑ 违反 C4「拖动 → S 层零变更」
```

⭐ **本质是不可兼得**:**id 不能既是语义面的内容,又对语义面透明**。
写进去就会被拖动改动(破 C4);不写进去就没有跨编辑的稳定锚点(债 6)。

⭐ 这次是**断言先挡住了我**,不是我先想明白 —— 记在这里以免下次再试一遍。

### 8.3 正解方向(未做)

把稳定 id 变成**书写表面之外**的东西:

| 投影 | id 从哪来 |
|---|---|
| ⭐ **KRIG(note block)** | **天然存在** —— block id 就是稳定 id(01 §5),文本里根本不用写 |
| 平文本(mermaid) | `^id` 由**用户主动写**(01 §3.2「想连线,先命名」),机器不补 |

⚠️ 也就是说:**债 6 在 KRIG 投影下自动消失**,它是平文本投影的固有代价。
这也是规格方向(mind = 一篇 note,03 §7)比当前脚手架更对的又一个理由。

⚠️ 当前 v0 的实际影响:语义面里增删节点后,已钉住的坐标可能错位 ——
可用 toolbar 的「⟲ 恢复自动布局」一键清掉重来。
