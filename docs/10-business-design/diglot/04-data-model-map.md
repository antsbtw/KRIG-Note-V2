# mind 数据模型对照表 —— 一份数据,三个 view 各取所需

> 用户 2026-09-10:「先搞清楚 mind 是如何存储的,note 是什么格式,mermaid 是什么格式,
> 图形描述又包含什么,他们哪些字段是共用的,哪些是各自特有的。
> **它们只要从一份数据读出来,不同的 view,使用不同的部分就好了。**」

⚠️ 这份文档是在我「一个现象修一处、连修六轮」之后补的。
**打转的根因就是没有这张表** —— 每次都从现象出发找最近的可疑点,
而不是先问「这个字段属于谁、谁该读它」。

---

## 0. ⭐⭐ 一句话结论

```
                 ┌──────────────────────────────┐
   一份数据  →   │  mind_doc { semantic, graphic } │
                 └──────────────┬───────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        ↓                       ↓                       ↓
   note view              mermaid view             画布 view
   读 S 全部              读 S 的**投影**           读 S + G
   (富文本无损)          (有损:层级+标题纯文本)   (S 给结构,G 给覆盖)
```

⭐ **S 是唯一真源,G 是稀疏覆盖层。** 三个 view **都不拥有数据**,
各自只是 S(+G) 的不同投影。谁都不能反过来定义 S 该长什么样。

---

## 0.5 ⭐⭐ 数据 = 三个 view 需求的**并集**(用户 2026-09-10 定的原则)

> 「使用同一份数据,但是不同的 view 做不同的解析,**数据是这三者的并集就可以了**。」

这句话把职责划得很干净,值得当成硬规矩:

```
数据 ⊇ (note 要的) ∪ (mermaid 要的) ∪ (画布 要的)
```

### 0.5.1 三条推论(都能直接当检查项)

| 推论 | 说明 | 违反时的症状 |
|---|---|---|
| ⭐ **数据不为任何单个 view 裁剪** | 某 view 用不上的字段**照存**,不删 | 正文存盘即丢(为了迁就 mermaid 的表达能力) |
| ⭐ **view 只读自己那部分** | 读不到的字段**跳过**,不报错、不清空 | mermaid tab 显示一坨 JSON(读了不属于它的那份) |
| ⭐⭐ **view 写回只能改自己那部分** | 表达不了的字段**必须保留旧值** | 点进 mermaid tab 改一个字 = 全图正文删光 |

⚠️ 第三条最要命,因为它**看起来像正常保存**。
`mergeKeepingBodies` 就是这条推论的实现:
**mermaid 表达不了的东西,不该由 mermaid 的解析结果决定其存亡。**

### 0.5.2 ⭐ 并集完整性检验(实测通过)

| view | 需要 | 数据里有吗 |
|---|---|---|
| note | content(多块富文本) / parent / order / id / role / collapsed | ✅ 全有 |
| mermaid | parent / order / 标题纯文本 | ✅ 全有 |
| 画布 | content / parent / order / id / pos / color / shape / collapsed / structure | ✅ 全有 |

⚠️ **唯一的真实缺口**:mermaid **表达不了 `id`**。
这不是数据缺字段(S 层有 id),而是 **mermaid 这个投影面容不下它** ——
写显式 id 进 mermaid 文本会违反 C4(画布拖动 → S 层零变更),已记为 §8.2 的取舍。
⭐ 所以 mermaid 只能做**导入/导出**,永远不能当真源:
它往返一趟会把 id 弄丢,而 id 是 G 层条目的挂靠点。

### 0.5.3 ⚠️ 反面:什么**不该**进这份数据

并集不等于「什么都往里塞」。**派生物不进**:

- `Instance[]` —— S+G+布局算出来的,**绝不落库**(见 §3.2)
- 层级数字 `hn` —— 由 `parent` 深度推出,**永不落库**(01 §4)
- `title` —— 派生自 root 的文字(01 §3.4),库里那列只是冗余缓存

⭐ 判据:**能从别的字段算出来的,就不是数据,是投影。**

## 1. 库里到底存了什么(实测 `mind-store.ts`)

表 `mind_doc`,**整张图一行**(不是一块一行):

| 字段 | 类型 | 内容 | 谁写 |
|---|---|---|---|
| `mind_id` | string | 图的 id | 建图时 |
| `title` | string | ⭐ **派生自 root 的文字**,不单独维护(01 §3.4) | flushSave |
| ⭐ `semantic` | string | **S 层**序列化串 | flushSave |
| ⭐ `graphic` | string | **G 层**序列化串(稀疏,空串=全自动布局) | flushSave |
| `folder_id` | string? | 所在文件夹 | — |
| `created_at` / `updated_at` | number | 时间戳 | — |

⚠️⚠️ **表里不存 `format`** —— 实测(mind-store 文件头注释)存进去读回来是
`undefined`,所以那层只留两段纯文本。
⭐ 后果:加载时必须**从内容判版本**(`detectMindFormat`),
写死任一版本会让另一版本的图打不开。

⚠️ **与 note 的存法根本不同**:note 是**一块一行 atom**(`atom` 表,
`payload.attrs` 带 `noteId/parentId/order`,Decision 028 结构属性化);
mind 是**整图一个字符串**。这是有意的(用户 2026-09-09 拍板:
「先以文档作为存储单元,尽量少边的关系」)。

## 2. ⭐⭐ 字段归属:谁拥有什么

### 2.1 S 层(语义)—— `semantic` 字段

`SNode`(见 `types.ts:75`):

| 字段 | 含义 | note view | mermaid view | 画布 view |
|---|---|---|---|---|
| `id` | 节点稳定 id | ⭐ 落在 block `attrs.id` | ❌ **表达不了** | 用作 instance id |
| `content` | ⭐ **富文本信封**(可多块) | ⭐ **全部读** | ⚠️ 只取首块**纯文本** | 全部读(渲成 mesh) |
| `parent` | 父节点(⭐ 真相是父子,不是层级数字) | 推出 hn 层级 | 推出缩进 | 推出连线 |
| `order` | 兄弟次序(lexrank) | 块的先后 | 行的先后 | 布局次序 |
| `role` | root / branch / floating | 首块是否文档标题 | `root(())` 记号 | — |
| `ref` / `labels` / `markers` | 外部引用 / 标注 / 标记 | 部分 | ❌ | 待做(债 1) |

### 2.2 G 层(图形)—— `graphic` 字段

`GEntry`(见 `types.ts:172`),**稀疏**:有条目才覆盖,没条目走自动布局。

| 字段 | 含义 | note view | mermaid view | 画布 view |
|---|---|---|---|---|
| `pos` | ⭐ 钉住的坐标(存在即 pinned) | ❌ | ❌ | ⭐ **覆盖自动布局** |
| `color` / `shape` | 外观 | ❌ | ❌ | ⭐ 读 |
| `structure` | 子树布局算法(向下继承) | ❌ | ❌ | ⭐ 读 |
| ⭐ `collapsed` | 折叠(**持久**,是图的一部分) | ⭐ **读**(三角+藏内容) | ❌ | ⭐ 读(裁子树) |
| `float` | 自由主题 | ❌ | ❌ | 读 |
| `unknown` | ⚠️ 未知记号**原样透传**(C9) | — | — | — |

⭐ `collapsed` 是**唯一被 note 和画布共用的 G 字段** ——
所以它必须**单一真源**(踩过 split brain:三角切了、文字没藏)。

## 3. ⭐⭐ 三种「格式」到底是什么关系

⚠️ 最容易混的一点:**「note 格式 / mermaid 格式」不是两种存储格式**,
它们是**同一个 S 层的两种表面形态**。只有一种东西真的落库。

| | 是什么 | 落库吗 | 有损吗 |
|---|---|---|---|
| **S 层(内存)** | `SNode[]` + `SEdge[]` | — | — |
| ⭐ **note doc(PM JSON)** | S 的**无损**序列化 | ⭐ **是**(v1 的 `semantic`) | ❌ 无损 |
| **mermaid 文本** | S 的**有损投影** | ⚠️ v0 曾是(已废) | ⭐ **有损** |
| **G 层规范形** | `GEntry` 的文本序列化 | ⭐ 是(`graphic`) | 无损 |
| **Instance[]** | S+G+布局 的**派生物** | ❌ **绝不落库** | — |

### 3.1 ⚠️ mermaid 能表达什么(实测,别高估)

```
保住: 层级、兄弟次序、标题的**纯文本**
丢弃: 正文块、行内公式、marks、图片、id、G 层全部
```

⚠️ 连标题那行也只剩纯文本:`contentToText` 是 `runs.map(r => r.text ?? '')`,
`mathInline` 没有 `text` → **标题里的公式变成空串**。

⭐ 所以 mermaid **只配做导入/导出通道**,不能当真源。
用户口径:「大概率不会导出 mermaid,应该是 **mermaid 导入**的情况居多。」

### 3.2 ⚠️⚠️ Instance ≠ G 层(最容易犯的错)

```
S 层(树) ──推导──┐
                 ├─→ ELK 自动布局(全量坐标) ─→ Instance[]
G 层(稀疏 pos) ──┘   有条目的覆盖自动值
```

`Instance.position` 是**全量**的(没坐标画不出来);
G 层是**稀疏**的(只有被碰过的才有条目)。
⚠️ 把 Instance 存成 G 层 = 当场违反稀疏纪律,C5/C7 全废。

## 4. ⭐ 「一份数据,各取所需」落到代码上

| 投影方向 | 函数 | 无损? |
|---|---|---|
| S → note doc | `treeToNoteDoc` | ⭐ 无损 |
| note doc → S | `noteDocToTree` | ⭐ 无损(与上互逆,有往返断言) |
| S → mermaid | `toMermaidMindmap` | ⚠️ 有损 |
| mermaid → S | `parseMermaidMindmap` | ⚠️ 只能还原层级+标题 |
| S + G → 画布 | `projectToInstances` | 派生,不回存 |
| 存盘 | `snapshotToFile` | S→note doc 串 + G→规范形 |
| 读盘 | `fileToSnapshot` | 反之(按 `detectMindFormat` 选分支) |

### 4.1 ⚠️ 跨投影写回的铁律

- **note view 改了** → 整棵 S 换掉(无损,安全)
- ⭐ **mermaid view 改了** → **必须 `mergeKeepingBodies`**:
  mermaid 表达不了的东西(正文块),**不该由 mermaid 的解析结果决定其存亡**。
  否则用户点进 mermaid tab 改一个字 = 全图正文删光(静默毁数据)
- **画布拖动** → 只写 G 层一条(C4:S 层零变更)

## 5. ⚠️ 这张表能防住的坑(都是踩过的)

| 坑 | 本该先问的问题 |
|---|---|
| 正文存盘即丢 | 「`content` 是多块的,`semantic` 这个格式装得下吗?」 |
| mermaid tab 显示 JSON | 「改了 `semantic` 的存法,**谁还在读它**?」 |
| 字号叠乘成 90px | 「深度→字号,是 `text_size` 管还是块 `level` 管?**两个都管就会乘**」 |
| 折叠 split brain | 「`collapsed` 被几个 view 读?」 |
| 加载写死 v0 | 「表里存 `format` 吗?」(不存 → 必须探测) |

⭐ 共同形态:**同一份数据有多个消费者,只验了其中一条路。**
改任何一个字段前,先在本表里查「谁读它」。
