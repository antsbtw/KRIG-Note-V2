# X 发文(发推)设计 —— 待用户确认(2026-10-26)

> 前情:[HANDOFF-posting-control.prompt.md](HANDOFF-posting-control.prompt.md)。本文是「定了效果之后的设计」,用户确认后开工。

## 0. 用户定的效果(10-26)

- **架构(用户原话)**:「发推是 x 模块的一个独立功能模块,note 调用接口就可以发推,要保持 AI 也同样能够调用这些功能。」
- **发哪些**:短推、长推(超 280)、带图、X 文章;并且「把 note 的格式如何发成各种格式的推文,保证有好的阅读性」。
- **发前**:KRIG 里弹确认窗(预览 / 字数 / 提示),人点「发」→ KRIG 在 X 上点发布并核对推文真的出现了。
- **发后**:note 顶部一条提示(成 → 推文链接;没成 → 停在哪一步);**note 记着发过**(何时、哪个号、链接),再发同样内容先提醒。
- **入口**:note 右键、拖 block 到 X、回复指定推文、定时发。AI 也能调。

## 1. 形状:一条主线,四个入口

```
入口(谁发起)                          X 模块的发文能力(主进程,execute 一道关)
─────────────                          ───────────────────────────────────────
note 右键(选区 / 整篇)  ─┐
拖 block 到 X 发推框/回复框 ├─→ 内容(note 片段) ─→ x.post.prepare  排版:note → 发文方案(纯计算)
回复指定推文            ─┤                          │
AI                     ─┘                          ▼
                                            确认窗(人看方案、可改字、点「发」)
                                                   │
定时发(到点) ──────────────────────────────→  x.post.send     占网页 → 填 → 点发布 → 核对 → 留痕
                                                   │
                                            note 顶部提示 + x_post 记录(note 读 x.post.history 显示「发过」)
```

- **一切入口都只做两件事**:拿到 note 内容 + 目标(新推 / 回复谁 / 文章),交给同一组能力。入口之间没有各自的发推代码(上次去重的教训)。
- **AI 和人走同一组能力**。`prepare`(只排版不对外)AI 随时能调;`send` 是 output 类,AI / 收件箱调用照现在规矩 refused「要人批复」,等 P3 批复入口(⚠️ 本期不做 P3)。
- **X 自带一切**:菜单项、命令、确认窗、能力、记录表都在 `src/modules/x/`;note 不认识 X。删 X 目录 = 发推连菜单一起消失。

## 2. 能力清单

⭐ 用户 10-26:「发到 x 上再确定如何?多一个确认环节」→ 发布拆成两步:**先填进 X(人在 X 上看真实样子)→ 人再点一次 → 才发**。
所有形态(普通推 / 回复 / 推串 / 长推 / X 文章)都一样,不给 X 文章单开一套。

| 能力 | 类别 | 做什么 | 前提 | 占网页 | 核对 | 留痕 |
|---|---|---|---|---|---|---|
| `x.post.prepare` | input | note 内容 → 发文方案(形态、正文、配图、加权字数、超长时的可选发法) | 无 | 不占 | — | krig_flow 自动 |
| `x.post.fill` | output | 按方案打开发推框 / 回复框 / 文章编辑器,填正文、喂图,**不发**;返回一个「待发草稿」 | 认号;节奏额度 | 占 `page:<wc>`,**一直占到 publish / cancel**(不然采集会把页面导航走) | 框里的字、图数对得上方案 | `x_post` 一行(状态 filled) |
| `x.post.publish` | output | 人在 X 上看过、点「发布」/「确认定时」→ 点 X 的发布 / 定时按钮 | 有待发草稿且锁还是它的 | 复用 fill 的锁(`reuse`),发完放 | 推文出现、作者是我、正文对得上;推串逐条;定时 → X 的「已定时」列表里有它 | `appendAction` + `x_post` 更新 |
| `x.post.cancel` | control | 不发了:清掉 X 框里的内容、放锁 | 有待发草稿 | 放锁 | 框清空了 | `x_post` 更新(cancelled) |
| `x.post.history` | input | 某 note(或某几个块)发过 / 排着哪些、哪个号、链接 | 无 | 不占 | — | probe |
| `x.post.schedules` | input | 待发列表(任务页用) | 无 | 不占 | — | probe |
| `x.post.unschedule` / `reschedule` | output | 取消 / 改时间(要去 X 的「已定时」里改) | 认号 | 占 | X 列表里确实没了 / 时间变了 | 同上 |

- 待发草稿人一直不点:超过 10 分钟 → 自动 cancel、放锁,note 提示「草稿已撤回(超时没确认)」—— 不能让发推框永远占着网页。
- AI 调 `fill` / `publish`:照现在规矩 refused「要人批复」(P3 之前);`prepare` / `history` 随时能调。
- 「做了一半」照 `x.ask.run`:推串发了 2/5 停了 → failed + partial(已发的链接),note 提示里如实写。

## 3. 排版:note → 推文

**目的(用户 10-27 原话)**:「1、更好的管理自己的推文;2、有更好的文字和图形排版能力,这样可以让发出来的推文有更丰富的文字和图文表达方法。」
→ 不是「把 note 降级成纯文本」,而是 **note 是推文的原文和管理地**,发推那一步给出「发出去的样子」并在那里调排版。

用户 10-27 选定:排版手法四种全要(图文卡片 / 封面图 / 多图拼版 / Unicode 粗斜体)。

### 3.1 用户发推的流程(10-27 用户提出、讨论后定)

1. **在 note 里写内容** —— 普通 note,不为发推做任何准备,note 里没有任何发推标记(最多顶部一行「𝕏 发过 2 次」)。
2. **选中(或不选 = 整篇)→ 右键「𝕏 发到 X」** → 算加权字数、看有什么(图 / 公式 / 表格 / 代码 / 标题)、看结构 → **给建议的发法**,并直接显示成 X 上的样子:

   | 内容 | 建议 |
   |---|---|
   | ≤ 280,只有文字 / 图 | 单条推 |
   | 超 280,几段文字 | 推串(按段落拆) |
   | 超 280,有标题 / 表格、像文章 | X 文章 |
   | 短,但有公式 / 表格 / 代码 | 单条推 + 转成图附上 |

   ```
   ┌ 发到 X ─────────────────────────────── @antsBTW ┐
   │ 建议:推串 3 条(412 字,超过 280)               │
   │ 换发法:[推串✓] [长推] [X文章] [整段转图]        │
   │ ┌─────────────────────────────────────────┐     │
   │ │ (头像) antsBTW @antsBTW                  │     │
   │ │ 今天读了一篇论文…                    1/3 │     │
   │ │ ┌────────┬────────┐                     │     │
   │ │ │  图1   │  图2   │  ← 按 X 实际裁切     │     │
   │ │ └────────┴────────┘                     │     │
   │ │ 第二个发现是…                        2/3 │     │
   │ │ ┌ 卡片 ────────────────┐ ← 点段落改样式  │     │
   │ │ │ 「一句金句」 —— 作者  │                  │     │
   │ │ └──────────────────────┘                  │     │
   │ └─────────────────────────────────────────┘     │
   │ ⚠ 表格已转成图                                   │
   │        [回 note 改]  [⏰ 定时]  [发布 ▸]          │
   └──────────────────────────────────────────────────┘
   ```
3. **确认 → 发布 / 定时**:填进 X → 人在 X 上看真实样子再点一次(§5.2 两道确认)。
4. **发完**:note 顶部结果(✅ 链接 / ❌ 停在哪步),记进「我的推文」。

**讨论定下的四条(用户 10-27「采纳你的建议」)**

- **A 排版在预览里调,调过的记住**:点段落 → 卡片,点标题 → 封面,拖图片焦点;样式绑在那几个块上(`x_post_layout`:note id + 块 id → 样式,存 X 的表,不写进 note 文档),下次再发 / 定时发样子一样。
  → 上一版「在 note 块上挂 𝕏 标记 + note 给块装饰挂点」**作废**,note 侧少一个挂点。
- **B 字只在 note 里改**:预览只调发法和样式,不能改字。点「回 note 改」预览留在旁边、note 一改预览跟着刷新。note 是唯一原文,「我的推文」每条都对得回 note 里的原话。
  (§5.2 里「在 X 框里再改几个字」仍允许,但会在记录里标「在 X 上改过」—— 那是最后一道兜不住的现实,不鼓励。)
- **C 选区按字算**:选到哪个字就是哪个字;选区里带的图一起发;选区跨了半个表格 → 整个表格转图。
- **D 先保留两道确认**:KRIG 预览是模拟的(链接卡片、裁切可能和 X 不同),所以点「发布」后先填进 X、人在 X 上再点一次;等用户觉得模拟和真实对得上了再改成一道。定时发的第二道在排队那一刻做,到点不再问。

### 3.2 四种手法

| 手法 | 效果 | 规则 / 限制 |
|---|---|---|
| 图文卡片 | 一段文字 / 引用 / 金句 → 一张设计过的图(主题色、字体、留白、署名) | 主题先给 3 套(浅 / 深 / 纸质);图里文字同时放进图片 alt 文字,不丢可读性 |
| 封面图 | 标题 + 副标题 → 首图(推串第一条 / X 文章封面) | 尺寸按 X 首图比例(推文 16:9,文章 5:2) |
| 多图拼版 | note 里的图按 X 的 2 / 3 / 4 宫格裁切比例预览,关键部分不被 X 裁掉 | 人可拖焦点;图片说明 → alt 文字;超 4 张推串分到后续条 |
| Unicode 粗斜体 | note 里的 **粗体** / *斜体* → 𝗯𝗼𝗹𝗱 / 𝘪𝘵𝘢𝘭𝘪𝘤 | ⚠️ **只有拉丁字母和数字有**,汉字没有花体 —— 中文粗体用「【】」包起来或改排成卡片;⚠️ 这些字 X 搜不到、读屏念乱码 —— note 级开关,开了确认窗里标 ⚠️,只提醒不拦 |

### 3.3 基本转写(没设样式的块)

**形态**:加权字数 ≤ 280 → 普通推;超了 → 确认窗让人选发法(§5.1);有回复目标 → 回复。
⚠️ 字数按 X 的加权算法:中日韩字算 2、链接一律算 23 —— 280 加权 ≈ 140 个汉字。

| note 里 | 推文里 |
|---|---|
| 标题 | 单独一行,前后空行(设了封面就进封面图) |
| 粗体 / 斜体 | 开花体 → Unicode;没开 → 去标记留文字 |
| 行内代码 | 去标记留文字 |
| 列表 | `• ` / `1. ` 每项一行 |
| 引用 | 「」包起来(设了卡片就进卡片) |
| 链接 | 文字 + 空格 + 网址(算 23 字) |
| 图片 | 附图,一条最多 4 张,按拼版设定 |
| 公式 / 代码块 / Mermaid / 表格 | 渲染成图附上;渲染失败 → 确认窗标红,不静默丢 |
| 视频 | 附视频(与图互斥,X 规则) |
| 分隔线 | 推串的切分点 |

**推串怎么切**:分隔线 → 标题 → 段落;一段放不下才按句号切,绝不在句子中间断。每条末尾 `1/5`。图片 / 卡片跟着它所在的那段走。

**X 文章**:块大多原样(标题 / 列表 / 引用 / 表格 / 代码 / 公式走 X 文章原生能力,旧 `x-article-driver` 是知识来源);卡片 / 封面照样渲染成图插入。

### 3.4 管理:「我的推文」(用户 10-27 选:只管从 note 发出去的)

```
┌ 𝕏 我的推文 ── @antsBTW ───────────────────────┐
│ [草稿 2] [待发 1] [已发 38] [没成 1]            │
│ 10-26 今天读了一篇论文…   ♥ 12  👁 840           │
│       📝 来源 note:论文笔记 ↗   在 X 上看 ↗     │
│ 10-25 推串 1/3 第二个发现…  ♥ 4  👁 210          │
│       📝 来源 note:周记 ↗                       │
└────────────────────────────────────────────────┘
```

- 放在「运营」(运营 = 看;记忆 feedback-x-ops-vs-tasks-placement)。待发的 改时间 / 取消 也在这里点(调 `unschedule` / `reschedule` 能力)。
- 点赞 / 浏览数:不另起采集,复用已有采集落进 `x_tweet` 的数据,按 tweet id 对上;多久没刷新就显示「数据是 X 天前的」,不装作是最新。
- 从 note 这头:note 顶部「𝕏 发过 2 次」点开就是这个列表筛到本 note。

## 4. 记录

- 新表 `x_post`(X 模块自带):号、note id、块 id 列表、形态、正文摘要、内容哈希、推文链接(推串是一组)、状态(成 / 做了一半 / 没成 + 停在哪步)、时间、谁发起的(ui / timer / ai)。
- note 不存任何 X 的东西(数据模型总纲:实体优先、关系放在 X 这边)。note 显示「发过 2 次」是去问 `x.post.history`。
- 再发同一内容:按内容哈希查到 → 确认窗顶上 ⚠️「10-26 已用 @xxx 发过」,**只提醒不拦**(用户 10-21「有问题提示就好了」)。
- note 顶部那条提示需要 note 给一个**通用的「顶部提示」挂点**(不是给 X 开的,别的模块也能挂)—— X 往里挂,删 X 就没了。

## 5. 三个流程(用户 10-26 答复后定)

### 5.1 超长:提示换发法(用户:「要计算字数,如果超过了,提示用户是否换一种方式?比如发 article,分成连续的推文?还是专程一个图片发出来?」)

不定默认,确认窗里让人选;每个选项下面直接是那种发法的预览。

```
┌ 发到 X ─────────────────────── @antsBTW ┐
│ ⚠ 412 / 280  超了 132(一个汉字算 2)    │
│ 换一种发法:                             │
│  ● 推串  拆成 3 条(按段落断)           │
│  ○ 长推  一条带「显示更多」(要 Premium)│
│  ○ X 文章  标题 + 正文,表格公式原样     │
│  ○ 转成图  整段排成一张长图 + 一句话正文 │
│  ○ 回去删减                             │
│ ┌ 预览 ─────────────────────────────┐   │
│ │ 1/3 今天读了一篇论文…              │   │
│ │ 2/3 第二个发现是…  [图]            │   │
│ │ 3/3 结论…                          │   │
│ └────────────────────────────────────┘   │
│        [取消]  [⏰ 定时]  [填到 X ▸]      │
└──────────────────────────────────────────┘
```

- 号认得出不是 Premium → 「长推」灰掉并写明原因(不藏起来)。
- 「转成图」:按 note 的排版渲染成图(标题 / 列表 / 公式都在图里),正文放第一句 + 「全文见图」。

### 5.2 两道确认(用户:「发到 x 上再确定如何?多一个确认环节」)

```
① KRIG 确认窗         ② 填进 X(左栏切到 X 网页)             ③ 结果
┌──────────┐        ┌─ X 网页 ─────────────────────────┐
│ 预览/选法 │ 填到X▸ │ ┌ KRIG ── 这是发出去的真实样子 ─┐ │   note 顶部:
│          │ ─────▶ │ │ [✅ 发布] [✏ 回 note 改] [取消]│ │ ─▶ ✅ 已发到 X · 查看 ↗
└──────────┘        │ └──────────────────────────────┘ │   ❌ 没发出去:停在「核对」…
                    │  发推框 / 文章编辑器里已填好      │
                    └──────────────────────────────────┘
```

- ② 那条 KRIG 条浮在 X 网页上方;人可以直接在 X 框里再改几个字,KRIG 核对时以框里的为准、并在记录里标「在 X 上改过」。
- 点「回 note 改」= cancel + 回到 note,改完重新走 ①。

### 5.3 定时发(用户:「要给出一个友好的流程和格式」)

```
① 确认窗点 [⏰ 定时]                ② 同 5.2:填进 X、人看真实样子、点 [⏰ 确认定时]
┌ 什么时候发 ─────────────────┐
│ ○ 今晚 20:00   ○ 明早 09:00 │     ③ note 顶部:
│ ○ 自定义 [10-28] [21:30]    │       ⏰ 排在 10-28 21:30 · @antsBTW · [改时间] [取消]
│ 按本机时区(UTC+8)          │
└─────────────────────────────┘     ④ 「任务」页多一栏「待发」:
                                      10-28 21:30  @antsBTW  今天读了一篇论文…  [改][取消]
```

- **到点发的是你确认过的那一版**,不是 note 最新内容。确认后 note 又改了 → 顶部多一行
  「⚠ note 改过了,排着的是旧版 · [用新版重新确认]」;不会自己换成新内容。
- 到点之后:✅ 变成链接;没发出去 → ❌ + 停在哪步。
- 实现两条路,先 spike 再定(用户只看效果,不在这里二选一):
  - X 自带的定时(发推框里的日历按钮):KRIG 不用开着,X 到点自己发;要验它对 免费号 / 推串 / 文章 支不支持。
  - 不支持的形态:KRIG 定时器到点按确认过的那版填 + 发(caller = timer,人排进去 = 人批过)。
    ⚠️ 到点 KRIG 没开着 → 下次启动提示「错过了 10-28 21:30 的一条 · [现在发] [改时间] [取消]」,**不自动补发**。
