## 2. 三个客观对象

### 2.1 人(`x_person`)

**客观事实**,谁抓的都一样:

```
handle(归一化)· 显示名 · bio · 头像
粉丝数 · 关注数 · 发推数 · 建号时间 · 认证状态 · 所在地 · 网站
```

⚠️ **不放**:`blocked` / `watched` / `is_self` —— 那些是**我和这个人的关系**,不是他的属性。

### 2.2 推文(`x_tweet`)

**客观事实**:

```
tweet_id · 正文 · 作者 handle · 发布时间 · 语言
媒体 · 引用推 id · 父推 id · 会话根 id
```

⚠️ **`metrics`(点赞/转发/回复数)不是不变的事实** —— 见 §4。

### 2.3 事件(`x_event`)

**「谁 · 对谁/对哪条 · 做了什么 · 什么时候」**

```
kind(like/retweet/reply/follow/quote/mention)
actor(谁做的)· target(对哪条推 / 对谁)
时间 · 来源(哪次采集看到的)
```

⭐ **实测依据**:通知页载荷**自带 `timestamp_ms`**
(`x-notifications.ts:267`,注释还记着「字段名叫 `timestamp_ms`,实际值却是 ISO 字符串」)——
**这是 X 主动推给我们的一条条流水,不是我们从状态里推的。**

## 3. ⭐ 一条关键区分:能记录的事件 vs 只能推断的动作

用户提出:「**动作是不可记录的,应该是状态来推断动作吧?**」

**实测结果:两种都有,分界线在「谁的动作」。**

| | 载荷给什么 | 能不能记录 | 依据 |
|---|---|---|---|
| **别人对我** | ⭐ **事件**(带时间戳) | ✅ **可以记录** | 通知页 `timestamp_ms` + `from_users[]` + `target_objects[]` |
| **我对别人** | ⚠️ **状态**(无时间) | ❌ **只能记快照** | 每条推挂 `legacy.favorited/retweeted/bookmarked` —— 只有 true/false |
| **第三方对第三方** | — | ❌ **拿不到** | X 2024 移除,与技术水平无关 |

### 3.1 「我对别人」为什么只能推断

载荷只给 `favorited: true` —— **没有时间**。

如果今天看到 `true`、昨天看到 `false`,只能推断「这一天之间赞了」。
**中间赞了又取消再赞,完全不知道。** 更糟的是:**我不知道我上次看是什么时候。**

> ⭐ 所以用户的判断在实践上成立:
> **「我对别人」这一侧,与其假装记录事件,不如老实记状态快照,把「动作」标成分析结果。**

### 3.2 落到模型上

```
x_event       别人对我做的     ← 事实,X 推来的流水
x_observation 某时刻我看到的状态 ← 快照,可重复
```

**由观察推断出的「动作」是分析结果**,不许存成 `x_event` 假装确定 ——
它的不确定性(不知确切时刻、不知有没有反复)**必须显式标出来**。

## 4. ⭐ `metrics` 归哪:观察,不是推文属性

一条推的点赞数**每时每刻都在变**。

现在 `metrics` 存在 `x_tweet` 行上 = **只记得最后一次看到的值**,
而且**不知道那是什么时候看到的**。

**改成观察**:

```
x_observation: { tweet_id, 看到时间, likes, retweets, replies, views }
```

⭐ **收益**:同一条推可以有多条观察 → **能画出「这条推的热度曲线」**,
而现在只能知道「最后一眼看到多少」。

> 这也解决了记忆里 `project-x-persistent-tracking` 提的「74% 正文被 TTL 删掉」的另一半:
> 正文能重建,但**当时的 metrics 是当时的事实,过后再也采不到**。

## 5. 关系归哪:第四类,但不是「客观对象」

```
x_relation:  我和这个人/这条推的关系
             blocked · watched · is_self · adopted · replied · ai_verdict
```

⚠️ **它是「我方意志」,不是客观事实** —— 换个人用这个 app,关系全不同,人和推文一模一样。

**所以四张表,但性质分两组**:

| 组 | 表 | 性质 |
|---|---|---|
| **客观**(谁抓都一样) | `x_person` · `x_tweet` · `x_event` | 事实 |
| **我方**(只对我成立) | `x_observation` · `x_relation` | 视角 / 意志 |

## 6. 验证:七类取数场景都能用这套表达吗

| 类别 | 解析出 |
|---|---|
| ① 本人数据 | 推文 + 观察 |
| ② 好友数据 | 人 + 推文 + 观察 |
| ③ 自然推送 | 人 + 推文 + 观察 |
| ④ 特定推文检测 | 推文 + **事件**(谁回了这条) |
| ⑤ 搜索结果 | 人 + 推文 + 观察 |
| ⑥ 入向互动 | ⭐ **几乎纯事件** |
| ⑦ 追踪名单 | 人 + 推文 + 观察 |

✅ **七类全覆盖。** 而 ⑥ 几乎纯粹是事件 ——
这解释了通知页数据为什么现在无处安放(`x_tweet` 存不下「谁赞了」这件事)。

## 8. 这套模型解决了什么

| 现在 | 之后 |
|---|---|
| 七类里只有一类存推文,其余用完就扔 | **全录全存**,来源变成一个字段 |
| 通知页数据无处安放 | 进 `x_event` |
| metrics 只有最后一眼 | **观察序列,可画热度曲线** |
| 「谁赞过我」查不了 | 查 `x_event` |
| 人表 36 行(见过 3458 个) | **见过就存**,关系另记 |
| 改进解析只对新数据生效 | ⭐ **拿 L-raw 重跑历史** |

### 9.1 `x_observation` 为什么先全记

曾考虑「只在变化超阈值时记」以省空间。**否决**,理由:

- ⚠️ 与 `web/capability-layer/01-contract.md` §13 的原则冲突:
  **「存储端加判断 = 拿可靠性换空间」**
- 一行观察就几个数字,**比 L-raw 的响应体小几个数量级**
- 真嫌大了,**压缩历史(如一个月前按天聚合)比一开始就不记好** ——
  后者丢了就没了

> ⭐ 同一条原则第二次生效(第一次是 M4 要不要进 L-raw)。

### 9.2 为什么先拆 `x_author`

| | `x_author` | `x_tweet` | `tweet_feedback` |
|---|---|---|---|
| 行数 | **36** | 6800+ | 6900+ |
| 病情 | ⭐ **一表六语义,7 模块都写** | 三层语义混一行 | 单一职责 |
| 不可再生 | ❌ | ⚠️ 真档案 | ⚠️ **已推翻**(见 `redesign-05` §8) |
| 风险 | **最低** | 中 | ⚪ **不适用**(已定不迁,见 `redesign-05` §8) |

⭐ **它病最重、行最少** —— 拆它能**验证整套方法**,又不会伤到真档案。
