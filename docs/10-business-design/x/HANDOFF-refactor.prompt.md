> 立于 2026-09-07。用户判断:「越做到后面,发现业务太乱了,需要重构一次才行。」
> 本文交给**新对话**执行(上一轮对话上下文已过长,继续做会开始遗忘早期决定 ——

---

## 0. 重构的顺序:业务先于代码

⚠️ **这一节是用户亲自定的顺序,别跳过、别倒过来做。**

> 「重构的目的是**先理清楚现在有哪些功能**,如何对功能进行**分层分块**,
>  分别都是怎样的**业务流程、数据流程、时序**,这些都搞清楚后,
>  才是对代码的梳理和重构。」

所以任务的顺序是:

```
① 功能清单      —— 这个模块到底提供哪些能力?(用业务语言,不是文件名)
② 分层分块      —— 这些能力该怎么归类?边界在哪?
③ 三张流程图    —— 每块的业务流程 / 数据流程 / 时序
④ 对照代码      —— 现有代码怎么落在这张图上?哪些错位、重复、悬空?
⑤ 才是重构      —— 有了图和差距,才谈怎么改
```

**前三步一行业务代码都不要写。** 写代码之前先能回答:
「这个模块有几件事要做?每件事的输入输出是什么?谁触发?什么时候发生?」

初稿(上一轮)直接从「32 个文件各自什么职责」开始 —— 那是**代码盘点**,
不是业务梳理,顺序反了。用户指出后重写为本文。

## 3. 阶段②:分层分块

功能清单出来后,回答:**这些能力该怎么归类?**

已知的候选切分维度(至少给两个方案并说明代价,让用户拍板):

- 按**业务流程**:采集 → 判断 → 回复 → 追踪 → 活动
- 按**数据层次**:人 / 事 / 分析维度(设计文档 §4.1 的三分法)
- 按**运行位置**:main 采集侧 / renderer 呈现侧 / 共享契约

⚠️ 用户的架构方向是「**模块可独立部署 / 构建 / 迭代**」
(见记忆 `project-module-boundary-governance`),切分要往这个方向靠。

## 5. 阶段④:对照代码,找差距

有了上面三张图,**再**去看代码,回答:

- 现有代码怎么落在这张图上?
- 哪些模块**职责错位**(做了不属于它的事)?
- 哪些**重复**(同一件事两处实现)?
- 哪些**悬空**(没有对应任何业务能力 = 死代码)?
- 哪些**边界模糊**(改一处要连带改三处)?

### 已观察到的结构问题(上一轮几天连环 bug 的归因)

| 现象 | 病根 |
|---|---|
| `tweet_inbox` 是死表,repo/类型却都叫这名字 | 命名撒谎 |
| 采集恒 0,日志却说「多半撞上导航」 | 日志把猜测当结论 |
| 落错页面照样入库 | 信任外部输入,无边界校验 |
| 两个「配方」下拉分不清(筛选 vs 采集) | 概念没分开 |
| `wcId` 一天踩两次 | 同一约束没有统一执行点 |
| 预取口径与列表不一致 | 同一份数据两套查询各自演化 |
| `XInboxView.tsx` 2199 行 | 视图职责过载(混着 5 个子视图) |

## 6. 阶段⑤:执行

**分步做,每步全绿再进下一步。**
512 条守卫是安全网:全绿 = 行为没变;哪条红了 = 真的动了行为,必须解释清楚。

⚠️ 守卫本身也是资产:它们记录着大量「为什么这么写」。
重构时**守卫要跟着搬,不是删掉重写**。

## 7. 如何验证(这个仓库的特殊之处)

### 查真实数据

app 开着时 SurrealDB 在 `127.0.0.1:8533`:

```bash
curl -s -X POST http://127.0.0.1:8533/sql \
  -u "root:<密码见 app 启动参数>" \
  -H "Accept: application/json" -H "surreal-ns: krig" -H "surreal-db: krig_x" \
  -d "SELECT count() FROM x_tweet GROUP ALL;"
```

- ⚠️ app 关掉 SurrealDB 就退出,**查不到 ≠ 数据没了**
- ⚠️ **活动爬虫跑在另一台 Windows**,本机查它恒为 0,那是预期不是 bug
- ⚠️ SurrealDB 要求 `ORDER BY` 的字段出现在 `SELECT` 里,否则 parse error

### 跑测试

```bash
npx vitest run tests/x/           # 全量,应 512 passed
npx tsc --noEmit -p tsconfig.json # XInboxView.tsx:773 有一条既有错误,与你无关
```

### 三个已踩过的验证陷阱

1. **用 Python 改含中文的文件要注意编码** —— 踩过:UTF-8 被写坏,tsc 报 Invalid character
2. **测注入浏览器的脚本要真的求值再 parse** —— 模板字面量会吃掉 `\/` 这类转义
3. **守卫比对源码前先剥注释** —— 否则会被自己写的说明文字骗过(踩过两次)

## 9. 和用户协作的方式

这位用户的工作方式很明确,顺着来效率高得多:

- **他会盯着数据要证据**。说「我觉得有问题」时通常是对的,先查再答。
- **他不接受「看着成功实际没做」**。仓库里一半守卫为此而写。
- **他会推翻你的结论,而且往往对**。上一轮被他纠正至少五次:
  产品定位(单向→双向)、上文顺序、预取分页、「库里没有≠拿不到」、
  以及本文档的顺序(代码盘点→业务梳理)。
  被纠正时**先查证再认**,别急着道歉也别硬撑。
- **他要可解释**:每个数字、每个判断都要说清依据。

⚠️ **他明确讨厌的**:拿一个指标去否定它没测的能力;把「库里没有」当「拿不到」;
用注释里的说明骗过守卫;为了让测试变绿去删掉最该留的说明。
