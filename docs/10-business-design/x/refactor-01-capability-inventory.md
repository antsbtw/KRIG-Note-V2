## 3. 三个结构病灶(为下一阶段分层做铺垫)

### 3.1 `x-timeline-handlers.ts` 是唯一的收口点,也是唯一的病灶

42 个 handler 涵盖了**上面 A~H 全部八类业务**:采集、判断、回复、屏蔽、身份、
角色、文章、通知、活动状态、勘查工具 —— 全在一个文件里。

后果:**任何一类业务改动都要动这个文件**,它成了所有并发修改的碰撞点。
这直接解释了交接文档里「改一处要连带改三处」的观察。

### 3.2 命名撒谎(已确认,不是传闻)

`tweet-inbox-repo.ts` 里 26 处 SQL,**写的全是 `x_tweet`**。
文件名、类型名(`TweetInboxRecord`)、IPC 名(`X_INBOX_QUERY`)、注释里
还有 4 处写着 `tweet_inbox` —— 但那张表早已没人维护。

代码里自己也承认(`tweet-inbox-repo.ts:496`):
> ⚠️ 只写 x_tweet。`tweet_inbox` 是**遗留表**……那张表早已没人维护

### 3.3 「概念没分开」在数据层的投影

同一份推文数据,`x_tweet` 一张表同时承载了:
**采集产物 / 判断状态 / 人工标注结果 / 回复状态**。
`status` 字段一个枚举串起四条不同生命周期(`pending`→`ai_judging`→`worth`/`skip`→`replied`),
而「已回复」和「已研判」其实是两件正交的事 —— 代码里已经为此打了补丁
(`replied: false` 显式排除),补丁本身就是边界错位的证据。

## 4. 可达性核实(证明没有模块级死代码)

逐个查引用,32 个文件全部有活引用链:

| 模块 | 被谁引用 |
|---|---|
| `x-notifications` | timeline-handlers / notification-watch / campaign-loop / campaign-repo + 5 测试 |
| `x-notification-watch` | timeline-handlers + 1 测试 |
| `x-article-driver` | handlers / test-drivers ← `send-to-x.ts` |
| `x-article-replies` | campaign 全家 / notification-watch + 6 测试 |
| `x-payload-inspector` | timeline-handlers(`X_PAYLOAD_SURVEY`) |
| `x-author-timeline-spike` | timeline-handlers(`X_WATCHLIST_SPIKE`) |
| `x-capture-monitor` | timeline-handlers(`X_CAPTURE_START/STOP`) |
| `x-reply-collector` | timeline-handlers(`X_COLLECT_REPLIES`) |
| `x-plan-cache` | `main/index.ts` |
| `google-translate` | timeline-scan / timeline-handlers |
| 其余 | 均有 ≥1 活引用 |

> 结论:**删文件不是这次重构的内容**。要治的是职责分布,不是代码量。
