## 2. ⭐ 归纳:只有 4 种形态

### 形态 A —— 「去某页,滚到底,收全部」

```
goto(某页) → scrollUntil(到底) → capture(载荷) → 解析成推文[]
```

**谁是这一类**:`x-timeline-scan` · `x-timeline-harvester` ·
`x-notifications` · `x-article-replies` · `x-reply-collector`(复用 harvester)

⭐ **五个入口,同一形态** —— 差别只在:
- 去**哪个页**(搜索页 / 通知页 / 文章页 / 某人主页)
- **滚到什么时候**(到底 / N 轮 / 见到某元素)
- 载荷里**取哪个接口**

> 这正是 `scrollUntil` 必须与 `capture` 解耦的原因:
> 五个消费者对「滚多久」的需求不同,但「怎么滚」完全一样。

### 形态 B —— 「去某页,不滚,收一次」

```
goto(某页) → ready(就绪) → capture(单个接口) → 解析成对象
```

**谁是这一类**:`x-author-profile`(画像)· `x-parent-tweet`(父推)

⭐ **它们其实是 A 的退化**(滚 0 轮),只是**目标是一个确定的对象**,不是列表。

### 形态 C —— 「不导航,就地读当前页」

```
read(当前页) → 解析
```

**谁是这一类**:`x-extract-tweet`(右键提取)· `x-self-account`(我是谁)

⭐ **关键差别:不许导航。** 用户正看着这一页,导航会把他的位置弄丢。
`x-extract-tweet` 还多一个约束:**按坐标定位**用户右键的那一条。

### 形态 D —— 「不导航,被动听」

```
subscribe(当前页的载荷) → 边浏览边收
```

**谁是这一类**:`x-capture-monitor`(排查工具)

⭐ **人在开车,程序在记录。** 这是唯一一个「用户主导、程序跟随」的形态。

---

## 3. 四种形态的正交维度

| | 导航? | 滚动? | 目标 | 谁主导 |
|---|---|---|---|---|
| **A 批量采集** | ✅ | ✅ | 列表 | 程序 |
| **B 定点取值** | ✅ | ❌ | 单个对象 | 程序 |
| **C 就地读取** | ❌ | ❌ | 当前页/选中项 | 程序(但不打扰) |
| **D 被动跟随** | ❌ | ❌ | 流 | **用户** |

**两个维度就够了**:

```
            程序主导            用户主导
导航    │  A(滚) B(不滚)  │      —
不导航  │  C(就地读)      │   D(被动听)
```

> ⭐ **「谁主导」这一维是我之前漏掉的。**
> C 和 D 都不导航,但 C 是「程序去读」,D 是「程序在听」——
> 前者有明确的开始和结束,后者跟着用户的节奏走。

## 4. 组合出这 4 种形态需要的原子

对照 `web` 能力层已有 / 待有的能力:

| 原子 | 归哪个能力 | 状态 | A | B | C | D |
|---|---|---|---|---|---|---|
| `goto(语义页)` | 控制 | ⚠️ **未实现**(要 adapter) | ✅ | ✅ | | |
| `ready(判据)` | 控制 | ✅ **已完成** | ✅ | ✅ | | |
| `scrollUntil(判停)` | 控制 | ✅ **已完成** | ✅ | | | |
| `subscribe(载荷)` | 输出 | ✅ 已有 | ✅ | ✅ | | ✅ |
| `read(提取器)` | 输出 | ✅ 已有 | | | ✅ | |
| `find(定位页面)` | 控制 | ✅ 已有 | ✅ | ✅ | ✅ | ✅ |
| **按坐标定位** | 输出 | 🟡 底座有 `buildHitTestScript` | | | ✅ | |
| **L-raw 落盘** | 输出 | ✅ **已完成**(2026-09-09) | ✅ | ✅ | ✅ | ✅ |

⭐ **结论:四种形态所需的原子,底座已经齐了。**
**只缺 `goto`** —— 它要 adapter 的语义页面表,属业务对象阶段。

⚠️ 但**没有一条真实数据流进过新层**(接线阶段的事,见 `../web/capability-layer/01-contract.md` §15.1)。

## 5. ⭐ 由此得出的三个业务判断

### 5.1 「配方」不是采集能力,是**编排参数**

`x-timeline-scan`(配方采集)和 `x-timeline-harvester`(通用采集)
**是同一形态 A**,差别只在:

| | 去哪页 | 滚多久 |
|---|---|---|
| 配方采集 | 搜索页(关键词拼成 URL) | 到底 |
| 通用采集 | 任意页 | 到底 |

**「配方」的本质是「怎么拼搜索 URL + 什么时候跑」** ——
它是**编排层的配置**,不是一种独立的采集能力。

> 这解释了为什么 4 种模板里只有 `help-wanted` 有专属逻辑:
> 另外三种(`trending`/`vip-tracking`/`custom`)**本来就不需要专属逻辑** ——
> 它们只是不同的 URL 拼法。

### 5.2 三个「排查工具」中,只有 D 是真正独立的

| 工具 | 形态 | 能否被业务能力取代 |
|---|---|---|
| `x-payload-inspector` | B(去几个页,收载荷) | ⭐ **能** —— 有了 L-raw,它就是「查一下缓存」 |
| `x-author-timeline-spike` | A(去某人主页滚到底) | ⭐ **能** —— 就是形态 A |
| `x-capture-monitor` | **D** | ❌ **不能** —— 它是唯一的「用户主导」形态 |

> ⭐ **有了 L-raw,两个排查工具可以退休。**
> 「载荷勘查」变成「查缓存」,「spike」变成「跑一次形态 A 再看缓存」。

### 5.3 「按坐标定位」是 C 独有的,不该混进 A/B

`x-extract-tweet` 要抓的是**用户右键的那一条**,不是页面上第一条。
这个能力底座有(`buildHitTestScript`),但**只有形态 C 需要**。
