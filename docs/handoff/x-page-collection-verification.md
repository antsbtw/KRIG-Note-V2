## ⚠️ 最重要的一条方法论(用户定的,别违背)

> **先单条完整性,再条数对账。**

理由:每条推本身就缺字段的话,条数再对也没用;而且单条完整性**不需要分母**,
任何页面都能验 —— 包括那四个 X 不报总数的页面。

⚠️ 而且要量**入库后**的,不是只量解析出来的 —— 见 bug ③④,
「解析对了」和「存对了」之间隔着两层,都断过。

## 怎么验(操作步骤)

1. 起 app:`npm start`
2. 面板 → **能力控制台 → 采集 tab**
3. 下拉选页面(**显示的是人话名**,如「搜索结果 — x.search」)
4. 填参数(缺的框会**橙色高亮**,按钮会禁用)
5. 点 **「← 跳过去」** 让左边跳过去,**肉眼确认到了目标页**
6. 点 **「采集」**(「秒」填 60-90 即可,验字段不验条数)

### 采完**必看**这四行

```
✓ 入库回读:抽查 N 条,采集该给的字段都在库里    ← 最要紧
🧮 解析率:X 给了 E 个条目,解出 P 条(X%)
字段完整性:19/19 项 100%
停止原因:…
```

### 然后查库核对(别只信报告自述)

```bash
C=~/Library/Application\ Support/KRIG\ Note\ V2/.db-credentials
U=$(python3 -c "import json;print(json.load(open('$C'))['username'])")
P=$(python3 -c "import json;print(json.load(open('$C'))['password'])")
curl -s -X POST http://localhost:8533/sql -u "$U:$P" -H "Accept: application/json" \
  -H "surreal-ns: krig" -H "surreal-db: krig_x" \
  -d "SELECT tweet_id, tweet_url, author_avatar, author_name_at_post, conversation_id, fetched_at
      FROM x_tweet ORDER BY fetched_at DESC LIMIT 30;"
```

⚠️ **查库的两个坑**(都踩过):
1. **裸字符串比 datetime 不报错但结果错** —— `counts_at > '2026-09-21T13:00Z'`
   会返回**全表**;两头夹又返回 0 行。**全量取回、在 python 里按前缀筛**。
2. **总数不变 ≠ 没入库** —— `upsertTweet` 现在会更新已存在的行,
   重采老推**总数不变但内容更新了**。要看 `fetched_at` 有没有变。

## ⚠️ 本轮查出的 4 个真 bug(理解代码现状必读)

按发现顺序,一个比一个深 —— **全都只有实采才能发现**,单测/类型/schema 全正常:

### ① 载荷路径不产出 `tweet_url`/`author_avatar`/`author_name_at_post`

只有 DOM 路径产出 → 库里这三个字段 77-80% 空,
而 `coverage` **不量它们**,所以报告一直显示「15/16 项 100%」。
⚠️ **不量的字段永远是 100%**。

### ② `conversation_id` 类型没声明

schema 有列(还带索引)、解析器有值,唯独 `TweetInboxRecord` 没声明 → 写不进去。
「schema 有、解析有、类型没有」是最难发现的丢失:三处各自看都正常。

### ③ 写库语句是**第四处清单**,没跟上

补了 schema/解析/类型/toRecord 四处中的三处,漏了 `upsertTweet` 的 SQL ——
那条语句把字段**逐个写死**在 SET 子句和参数对象里。
⚠️ 现象极具迷惑性:同批里 `tweet_url` 进库了、**只有它全空**。

### ④ ⭐⭐ `upsertTweet` 根本不 upsert(最严重)

```sql
INSERT IGNORE INTO x_tweet   -- 已存在就整条跳过、不更新、不抛错
```

调用方 `saved += 1` 照加 → 报告显示「入库 50 条」,**库里纹丝不动**。

⚠️ 这推翻了一个共识:用户说「老数据等再次采集时补上」——
**按原实现永远补不上**。全库 `conversation_id` 卡在 9%、`tweet_url` 卡在 76%
正是这么来的。

已改成 `INSERT … ON DUPLICATE KEY UPDATE`,**只更新采集该负责的字段**。
⚠️ 不能无脑全覆盖:`accepted`/`ai_verdict`/`translation` 是业务与人工填的,
覆盖掉**不可逆**。守卫正反两向都钉了(漏采集字段要红、混业务字段也要红)。

## 🔴 给接手者的工作方法提醒

本轮绕的弯路,都源于同几件事:

1. **别用间接观测否定直接事实**。我三次拿留痕/库总数推断「采集没发生」,
   而用户截图和终端日志证明它跑了。**查不到 ≠ 没发生**,先问「我的观测本身对吗」。
2. **诊断消息必须带真值**。报「参数不合法」却不说是哪个值 ——
   我为此查了四处全是对的,因为真值没进过视野。用 `JSON.stringify`:
   空串/空格/零宽字符/类型不对,肉眼下长得一模一样。
3. **守卫的锚点别用会变的东西**。本轮有 5 条守卫因改动挪位而假红、
   3 条因切片太宽或注释干扰而假绿。**每条守卫写完必须注入违规验证能变红**。
4. **修 A 不能砍掉 B**。我为修「下拉选了又跳回」把「左边点右边跟」整个关掉,
   被用户指出「怎么只有一个单向的功能」。
   两个症状同一个根因时,要找那个根因,不要二选一。
