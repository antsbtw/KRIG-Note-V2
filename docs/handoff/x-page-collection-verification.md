### ⑤ 入库回读把 `Date` 误判成空 —— **工具谎报**(`b76aa368`)

报告红着脸说「`created_at` 整片为空(抽查 20 条全空)」,库里是 **1785/1785 全有值**。

真因:`created_at` 是 `datetime`(写入处 `new Date(...)`),SDK 读回来是 `Date` 实例,
而判空那条 `Object.keys(v).length === 0` 对 `Date` **恒为真**。

⚠️ 那条「空对象」规则本来是**给 `metrics` 用的**(真的 `{}` 才算空),
不该套到所有 object 上。已改成按原型只判普通对象。

⭐⭐ **工具谎报比采集出错更坏:它会让人去改没坏的代码。**
报告自述与库里事实不一致时,**先怀疑观测工具**。

### ⑥ ⭐⭐ 长文(Article)正文全丢 —— 只存进 23 字短链(`06c80445`)

同一次采集、同一页:长推取到 957 字,而**两篇长文各只存进 23 字**:
`text = 'https://t.co/e5H5321Vh9'` —— 标题和几千字正文**全丢**。

**真因**:长文的 `legacy.full_text` **就只有一个 t.co 短链**,正文在
`article.article_results.result.content_state`(DraftJS),而解析器原本只走
`note_tweet ?? full_text`,**`article` 零处理**。

⚠️⚠️ **长推(note_tweet)与长文(article)是两回事,别混**。
报告里「长推(Show more) ✓ 全文已取回」量的是 `note_tweet`,**不量长文** ——
又一次「不量的字段永远是 100%」。

**实测结构**(非推测,来自诊断日志):
```
article.article_results.result
  ├─ title                       ← 标题(不在 blocks 里)
  └─ content_state.blocks[]      ← 正文,每块 { text, type }
       unstyled    正文段
       header-two  小标题
       atomic      媒体占位 ⚠️ text 是**单个空格**,不滤会留孤立空行
```

**修复效果**(同一条推重采,bug ④ 修好后老行能被更新):

| tweet_id | 前 | 后 | 类型 |
|---|---|---|---|
| `2099916828529082572` | 23 字 | **16081 字** | 长文 ✅ |
| `2102084427903860755` | 23 字 | **6812 字** | 长文 ✅ |
| `2102084431095726330` | 957 字 | 957 字 | 长推 ✅ **未误伤** |
| `2102085080638235058` | 241 字 | 241 字 | 普通推 ✅ **未误伤** |

⚠️ **遗留**:`title` 挂哪一层**没看全**(诊断日志截断在 4000 字),
现在是「按已知几处依次探查、找不到也不失败」。真实结构确认后可收窄成一处。

⚠️ **遗留**:报告口径仍把长文算进「长推(Show more)」统计。数据对、名字不准。

## 怎么验(操作步骤)

1. 起 app:`npm start`(⚠️ **改了代码必须重启**,否则跑的是旧编译产物)
2. 面板 → **能力控制台 → 采集 tab**
3. 下拉选页面(显示人话名,如「搜索结果 — x.search」)
4. 填参数(缺的框会橙色高亮)
5. 点 **「← 跳过去」**,**肉眼确认到了目标页**
6. 点 **「采集」**

⚠️ **「轮数」留空 = 上限 5000 轮**,不是你填的秒数。验字段完整性填「轮数=50」即可,
否则会跑十几分钟(踩过:填了秒=40 仍跑了 1800 秒预算)。

### 采完必看这四行

```
✓ 入库回读:抽查 N 条,采集该给的字段都在库里    ← 最要紧
🧮 解析率:X 给了 E 个条目,解出 P 条(X%)
字段完整性:19/19 项 100%
停止原因:…
```

### 然后查库核对(别只信报告自述)

```bash
C=~/Library/Application\ Support/KRIG\ Note\ V2/.db-credentials
U=$(python3 -c "import json;print(json.load(open('$C'))['username'])")
P=$(python3 -c "import json;print(json.load(open('$C'))['password'])")
curl -s -X POST http://localhost:8533/sql -u "$U:$P" -H "Accept: application/json" \
  -H "surreal-ns: krig" -H "surreal-db: krig_x" \
  -d "SELECT tweet_id, string::len(text) AS chars, tweet_url, conversation_id, fetched_at
      FROM x_tweet ORDER BY fetched_at DESC LIMIT 30;"
```

⚠️ **查库的三个坑**(都踩过):
1. **裸字符串比 datetime 不报错但结果错** —— `counts_at > '2026-...Z'` 返回**全表**,
   两头夹又返回 0 行。**全量取回、在 python 里按前缀筛**。
2. **总数不变 ≠ 没入库** —— upsert 会更新已存在的行。**看 `fetched_at` 变没变**。
3. **库静止 ≠ 采集没跑** —— 采集是**滚完才批量入库**,滚动中库里本就是静的。
   判据看终端有没有在刷 `[harvest] 轮N/...`。

## 🔴 给接手者的工作方法提醒

1. **别用间接观测否定直接事实**。上一轮拿「库里总数没变」「进程 CPU 低」断言
   「采集没在跑」,而用户的截图和终端日志证明它正跑着。**查不到 ≠ 没发生**,
   先问「我的观测本身对吗」。
2. ⭐ **报告说谎时先怀疑工具**(bug ⑤)。屏幕上有卡片而报告说「这页没有推文」,
   信屏幕。
3. **别猜结构**。长文正文是靠**临时诊断打印真实载荷**定位的,不是读代码猜的。
   诊断用完必删(本轮已删)。
4. **守卫要能变红**。本轮两条守卫都**注入了真 bug 验证**
   (article 不参与 text → 红 3 条;atomic 空格不滤 → 红 1 条)。
   ⭐ 行为测试 > 源码扫描:`void 0 && parse(...)` 能让 `toMatch` 全绿。
5. **修 A 不能砍掉 B**。长文修复的守卫**反向也钉了**普通推/长推不受影响,
   并在真机上验证了(957 字和 241 字两条一字未动)。
6. **测试载荷要抄真实日志**。编的形状只能证明「代码按我想的跑」,
   证不了「它接得住 X 真给的东西」。
