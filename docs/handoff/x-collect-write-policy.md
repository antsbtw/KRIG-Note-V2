## ⚠️ 一、写库合并策略(改动最大的一块)

### 为什么需要它

同一条推会被**不同深度的路径**反复采到:

| 路径 | 产出 |
|---|---|
| 载荷路径 | 全字段(含 `tweet_url` / `author_avatar` / `conversation_id`) |
| **DOM 兜底路径** | **这三样根本没有**(只在载荷里,见 `x-capture-monitor.ts:685`) |
| `UserArticlesTweets` / `UserOriginalsTimeline` | 长文**只给标题+摘要**,没有正文 |

原来是无条件覆盖 → **后来那趟浅的把先前采全的数据抹掉**。
⚠️ 这不是理论风险,**实测被毁过 3 行**(都已从备份回灌):

```
2099916828529082572  16081 字 → 267 字
2102084427903860755   6812 字 → 295 字
2102058908387094563    782 字 → 278 字(长推被 full_text 截断)
```

### 策略:按「会不会变」分三类

代码在 `src/platform/main/db/tweet-inbox-repo.ts` 的 `upsertTweet`。

| 类别 | 字段 | 规则 |
|---|---|---|
| **主体内容** | `text` | **只许变长**(浅摘要盖不掉全文) |
| **不可变事实**(发出来就定了) | `created_at` `tweet_url` `conversation_id` `in_reply_to` `in_reply_to_user` `author_name_at_post` | **只补不覆盖**(老值非空就不动) |
| **会变的现状**(本来就该更新) | `metrics` `metrics_at` `author_avatar` `lang` `author_handle` | **有新值就更新**,但空值不许覆盖非空 |
| **业务/人工填** | `accepted` `ai_verdict` `translation` `replied` `status` | **完全不碰**(覆盖不可逆) |

⭐ 底线一句话:**空值永远不许覆盖非空值。**

### ⚠️⚠️ 三个必须知道的坑

**① `??` 把空串当成有值。**
实测:`tweet_url = tweet_url ?? $tweet_url` 在老值是 `''` 时**永远补不上**。
今天库里恰好 0 行空串,但写入侧随时可能产生一行 —— **不能靠运气**。
→ 一律写成 `IF x != NONE AND x != '' THEN … ELSE … END`。
(`created_at` 是 datetime 不会是空串,保留 `??` 即可。)

**② `string::len(NONE)` 会抛错。**
实测报 `Expected string but found NONE`,而且**整条 upsert 会失败**。
→ 必须 `string::len($text ?? '')`。

**③ `INSERT` 段与 `ON DUPLICATE` 段是两份独立清单。**
加字段要**两边都动**,外加参数对象绑值 —— 这就是 bug ⑥ 的成因(见第六节)。

## 二、`metrics_at`:没有观测时刻的计数不可比(migration 1.2.6)

### 为什么加

实测 2000 条带 `views` 的推,**采集时距发推多久**:

```
最小 0 小时 · 中位 2.8 小时 · 最大 12633 小时(约 18 个月)
其中 31% 不足 1 小时
```

「发出 10 分钟拿到 500 阅读」和「发出半年拿到 500 阅读」**在库里长得一模一样**。
要从数字里找规律,这两条**根本不能放在一起比**。

⭐ `x_author` 早就做对了(1.0.4 的 `counts_at`:「没有时刻的计数无法判断新鲜度」),
`x_tweet` 一直缺这个,现在补上,口径一致。

### ⚠️ 两条约束

- **不复用 `fetched_at`**:那是「最后一次碰这行」,`text` 回灌、字段补全都会更新它,
  **不专指「这组数字是何时看到的」**。
- **只在真的更新了 `metrics` 时才推进** —— 否则就是给旧数字盖个新时间戳,
  比没有更糟。

⚠️ 现状:`metrics_at` 只有**被重采过的行**才有值(设计如此)。
全库比例会随采集慢慢涨,**别把低比例当 bug**。

## 三、采集留痕(`x-collect-journal`)

### 为什么有

用户点破的:**「面板的内容你不记录,如何做验证?」**

面板上一整屏判断依据(接口名、长文深度、解析率、停止原因、字段完整性)
**只渲染一次,关掉就没了**,库里只存 `text`。
于是核对时只能反过来让用户截图。

⭐⭐ 与可靠性纲领铁律③(**故障**要留痕)的区别 —— **这是新的一刀**:
那趟采集**完全成功**,依据照样蒸发。**成功路径的判断依据同样要留痕。**

### 怎么用

每趟采集落一份 JSON:

```
~/Library/Application Support/KRIG Note V2/x-collect-journal/
  collect-<ISO时刻>-<入口>.json
```

含:入口/URL/采到多少/入库多少/轮数/停止原因/解析率/**按接口聚合的请求清单**
(带每个接口给的长文篇数与**带正文篇数**)/字段覆盖率/problems/notes。

⚠️ **只存元数据不存正文**(正文在 `x_tweet` 里),写盘失败只 warn 不上抛,
只留最近 200 份。

⭐ 它立刻就派上了用场:本轮**三个 bug 是靠读留痕发现的**,不用问用户要截图。

## 🔴 七、给接手者的工作方法提醒(本轮血的教训)

### 1. ⭐⭐ 守卫容易钉在「上次出事的地方」

bug ⑥ 最能说明问题:我**昨天刚写完**「加字段要登记四处」的守卫,
今天加 `metrics_at` 时**又漏了一处**,而 19 条守卫**全钉在 `ON DUPLICATE` 子句上**
(那是上一个 bug 的位置),**没有一条看 `INSERT` 段**。

→ 写守卫时要问:**这个字段还会出现在别的什么地方?**

### 2. ⭐ 守卫写完必须注入违规验证能变红

本轮每条守卫都注入了真 bug 实测(退回无条件覆盖 / 去掉 `??` 兜底 /
删掉 `INSERT` 段那行 / 首次就覆盖 …),**全部确认能红**。

⚠️ 还修了一条**假红**:`single-tweet-completeness` 用 `slice(ui, ui + 4000)`
固定字数切,SQL 加注释变长后参数对象被切掉一半,把明明绑了值的字段报成没绑。
→ **别用固定字数切**,切到函数真正的结尾;
→ 修完假红要**注入真违规确认它仍能红**,不能靠放宽换绿。

### 3. ⚠️ 别拿证明不了的字段去论证

我曾看见备份里长文标着 `source='watchlist'`,就断言「正文来自普通时间线」,
据此宣布立项前提被证否 —— 而 `source` 是**写死值**(`x-auto-collect.ts:361`),
**根本推不出接口**。后来实采直接打脸。

### 4. ⭐ 报告自述 ≠ 事实,查库;库里异常 ≠ 代码坏,先怀疑观测工具

本轮我自己就用错过字段名(`ai_verdict.verdict` 实际是 `worth`),
9678 行**全返回 null 且不报错**,差点据此断言「判断结果全空」。
**字段全空先怀疑字段名。**

### 5. ⚠️ 清理数据别只按时间窗

清 1281 条首页污染时,用 `fetched_at >` 时间窗删,**误删了同时段重采的两条长文**。
已从备份回灌。→ 删之前先看清楚**这个窗口里还有什么**。

⚠️ 回灌踩的坑:`CREATE ... CONTENT` 时 datetime 字段传字符串会被拒
(`Expected none | datetime`),要写 `<datetime>"..."`;emoji 要 `ensure_ascii=False`
(JSON 代理对 SurrealQL 不认);文本里的 `$MNTD` 会被当参数,要用 `LET` 绑定。
