## 一、这次实跑给出的三条硬约束

真实数据(`run_20260924103609_l3nhel`):

```
1. goto       ok   0.1s    已到 搜索 ("VPN" OR "翻墙" OR "科学上网")(live)
2. collect    ok  30.8s    采 43 条 / 入库 43 条 · 游标翻页:请求失败(HTTP 404)
3. judge      ok 330.8s    判了 10/10 条,其中值得回复 0 条
4. planReply  ok   0.5s    扫了 10 条,拟出 0 条,跳过 10 条
```

| # | 观察到的事实 | 对面板的约束 |
|---|---|---|
| ① | 耗时 **0.1s ~ 330s**,差 3000 倍 | **必须有实时进度**。判断那步 5.5 分钟没反馈,人会以为又死了(用户这次就说了「没有任何反应」) |
| ② | 每步产出形态**各不相同**(到了哪页 / 采几条 / 判几条值几条 / 拟几条跳几条) | 不能做成统一的「进度条 + 数字」,每步要有**自己的一句话** |
| ③ | 最想知道的不是数字,是**为什么** | 「跳过 10 条」没用,「已回过×7 · 模型说不值×3」才有用 |

⭐ ③ 这条是本轮最大的收获:用户看到「跳过 10 条」的第一反应就是要去查为什么 ——
**编排的价值正是消灭这个「再去查一次」**。

## 三、面板长什么样

沿用工作台已有的**左列表 / 右详情**布局(用户 2026-09-15 定的乙方案),不另起一套。

```
┌─ X 工作台 ────────────────────────────────────────────────┐
│ 面板          │  编排:X 搜索 → 采集 → 判断 → 拟回复        │
│ ─────────     │  ────────────────────────────────────────  │
│ 🎯 盯人对照    │  搜索词 [VPN, 翻墙, 科学上网      ] 翻页[3] │
│ ▶ 编排 ←──    │                        [▶ 开始] [⏸ 停止]   │
│               │                                            │
│               │  ● 1 导航到搜索页            ✓ 0.1s        │
│               │    已到 搜索 ("VPN" OR "翻墙")(live)       │
│               │                                            │
│               │  ● 2 采集搜索结果            ✓ 30.8s       │
│               │    采 43 条 / 入库 43 条                    │
│               │    ⚠️ 游标翻页:请求失败(HTTP 404)          │
│               │                                            │
│               │  ◐ 3 AI 判断                 ⏳ 3分12秒…    │
│               │    判断中…(一批 10 条,约 30s/条)          │
│               │                                            │
│               │  ○ 4 拟回复草稿                            │
│               │                                            │
│               │  ── 历史 ──────────────────────────────   │
│               │  09-24 10:36  ✓ 四步全通        6分12秒    │
│               │  09-24 10:22  ✗ 断在「goto」     0.1s     │
└───────────────┴────────────────────────────────────────────┘
```

### 每步一行,状态四态

| 符号 | 状态 | 说明 |
|---|---|---|
| `○` | 未开始 | 灰 |
| `◐` | 进行中 | **带已用时**(这是①那条约束的答案) |
| `✓` | 成功 | 带耗时 + **那一句话** |
| `✗` | 失败 | 带**错误原文** |
| `–` | 跳过 | ⚠️ 必须写明是哪一种:前面断了 / 人停的 / 档里关掉 |

### ⭐ 「那一句话」直接用 `FlowStepOutcome.note`

已经在跑的数据里了,**面板不自己拼**:

```
已到 搜索 ("VPN" OR "翻墙")(live)
采 43 条 / 入库 43 条 · 游标翻页:请求失败(HTTP 404)
判了 10/10 条,其中值得回复 0 条
扫了 10 条,拟出 0 条草稿,跳过 10 条(already_replied×7 · ai_declined×3)
```

⚠️ 面板拼一份 = 第二份实现,两份必漂(本轮反复踩过)。

## 四、必须解决的技术问题:实时进度

⚠️ 现在 `runFlow` 是**一个 invoke 等到底** —— 6 分钟里 renderer 什么都收不到。
这就是「点了没反应」的根源,光加 UI 解决不了。

### 方案:main → renderer 广播每步状态

```
WEBC_FLOW_PROGRESS  (main → renderer 广播)
  { runId, seq, stepId, status: 'running'|'ok'|'failed'|'skipped', note?, elapsedMs }
```

- `runFlow` 每步**开始时**和**结束时**各广播一次
- 面板订阅,收到就更新那一行

⚠️⚠️ **广播必须带 wsId,面板必须核对** —— 记忆里「宿主广播×多ws扇出」那条:
多窗口下每个 ws 都会收到,不核对就会「A 窗口的进度显示在 B 窗口」。

⚠️ 广播失败**不能影响执行**(与留痕同一纪律:降级要局部)。

## 五、刻意不做的事

| 不做 | 为什么 |
|---|---|
| 编排档的**可视化编辑器**(拖步骤、连线) | 现在只有一份档、四步固定。等**真的需要第二份档**再说 —— 否则又是凭空设计 |
| 分支 / 循环 / 条件 | Module5 设计 2026-04 就定过:编排档是「可重组的步骤序列」,不是小语言 |
| 步骤级重试按钮 | 先看实跑中**哪一步真的常失败**。现在只跑过两次,没有依据 |
| 把盯人对照改掉 | 它是工作台已有的东西,不在本次范围 |

## 六、分步实施

| 步 | 做什么 | 判据 |
|---|---|---|
| **1** | 进度广播(main 侧)+ 面板订阅 | 判断那步跑 5 分钟时,面板上秒数**在动** |
| **2** | 工作台「编排」pane:参数 + 开始/停止 + 四步实时状态 | 不用再去控制台点 |
| **3** | 历史列表(读 `flow_run` / `flow_step_run`) | 关掉面板后还能回看上次跑了什么 |
| **4** | 删掉控制台那个临时按钮 | 一件事只有一个入口 |

⚠️ 每步都要能单独验收,不攒到最后一起试。
