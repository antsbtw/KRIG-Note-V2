# X 操作台的 Console —— 设计（待拍板）

> 用户 2026-10-01：
> 「在 x 的操作面板上先构建一个 console？专门用于调试控制、输入、输出（采集）等子函数使用」
> 「数据模型——建议采集信息尽可能使用关系型数据库的方法，而不要采用图数据库的方法，
> 　图数据库的方法尽量后期分析时再构建回更好」

---

## 〇、⭐ 先答数据模型那一问：你说的和本仓已立的纲领**完全一致**

这不是「我同意你」，是**三条实测证据**：

### ① 仓里的纲领早就这么定了

`docs/00-architecture/data-model-charter.md` 原文：

> **原则 1：实体优先** —— 每个实体必须能被独立地、完整地描述，不依赖任何关系才成立。
> ✅ **一条推文：id、正文、作者、发布时间、互动数 —— 单独存在就是完整的**
>
> **原则 2：关系是第二性的** —— 后建、可重算、可删除，不得侵蚀实体本身。
> 关系分三类：结构关系 / 业务关系 / **分析关系**（相似度、共现、推荐）——
> 算法产生，**随用随建、整批清除**。

⭐ 它连「推文」都直接拿来当实体的例子了。

### ② 旧 X 的 19 张表实测**零图边**

```
grep "RELATE|TYPE RELATION" src/storage/surreal/x-schema.ts  →  0 处
19 张 SCHEMAFULL 表
```

→ 上一版 X 虽然被推倒了，但**它的数据建模方式是对的**，这一点不必重做。

### ③ 「边分三层」那条记忆也指向同一处

`project-edge-layering`：文档本体零边（属性）/ A 类业务结构边 / **B 类分析图谱边（独立命名空间，可随意整批清）**。

⭐ 所以你的「采集用关系型、分析时再建图」正是 B 类的定义 ——
**采集产实体，分析产边，边可整批重算**。

### ⚠️ 但有一条要说清楚

本仓用的是 **SurrealDB**，它同时支持关系表与图边。
「用关系型方法」在这里的准确含义是：

| 做 | 不做 |
|---|---|
| `DEFINE TABLE x_tweet SCHEMAFULL` + 明确字段 | `RELATE author->posted->tweet` |
| 外键放字段里（`author_handle: string`） | 靠边来表达「谁发的」 |
| 查询用 `SELECT ... WHERE` | 查询用图遍历 |

⭐ 代价也写明白：**跨表查要自己 join**。但换来的是
「一条推文单独取出来就是完整的」—— 而那正是原则 1。

## 一、Console 要什么：按三类能力分，不按功能分

⭐ 这是**调试台**不是功能面板：目标是**逐个原子能力单独跑、看原样返回值**。

### 控制（`web.page`）

| 动作 | 底座函数 | 参数 |
|---|---|---|
| 跳转到语义页面 | `goto` | 页面名下拉（**从真表读**）+ 参数 |
| 等到位 | `ready` | 判据（anchorAppears / urlIncludes…） |
| 滚动直到 | `scrollUntil` | 停止判据 + 轮数上限 |

⚠️ 页面名下拉**必须从 `listPageNames()` 真表读**，不许面板自己抄一份 ——
抄一份就会漂，漂的表现是「面板上有这个名字、点下去说没登记」
（旧实现的注释专门记了这条）。

### 输入（`web.input`）

| 动作 | 底座函数 |
|---|---|
| focus 某个锚点 | `focus` |
| 输入文本 | `type`（含落地校验） |
| 点击 | `tap` |
| 按键 | `press` |

⚠️⚠️ **红线：绝不程序点「发布」**。
用户反复确认过：只填内容，发布永远由人点。
⭐ Console 上要能试 `type`（填进输入框），但**不提供「点发布」这个按钮**。

### 输出（`web.net` / `web.raw`）

| 动作 | 说明 |
|---|---|
| 开/关载荷捕获 | 捕的是 X 的 GraphQL 响应 |
| 看最近 N 条载荷 | **原样 JSON**，不解析 |
| 解析成实体 | 载荷 → `x_tweet` / `x_author` 的字段 |

⭐ **「原样载荷」与「解析结果」必须分两栏看** ——
解析错了要能一眼看出是「没采到」还是「采到了但解错」。
⚠️ 这正是旧实现栽过的：报告说「长推✓全文已取回」而长文根本不量
（`project-x-article-body-lost`：**不量的字段永远 100%**）。

## 二、⭐ 数据模型：先定实体，边一个不建

### 本期只建两张表

```sql
-- 人
DEFINE TABLE x_author SCHEMAFULL;
  handle         string     -- ⚠️ 归一化(去@、小写),UNIQUE
  display_name   option<string>
  bio            option<string>
  followers      option<int>
  ...
  fetched_at     datetime   -- ⭐ 什么时候采的

-- 推文
DEFINE TABLE x_tweet SCHEMAFULL;
  tweet_id       string     -- UNIQUE
  author_handle  string     -- ⭐ 外键放字段,不建边
  text           string
  created_at     datetime
  is_article     bool       -- ⚠️ 长文与长推是两回事
  metrics        option<object>
  raw_payload    option<string>  -- ⭐ 原样留一份
  fetched_at     datetime
```

⭐ **一条推文单独取出来就是完整的** —— 符合原则 1。
⚠️ **零 `RELATE`** —— 「谁发的」用 `author_handle` 字段表达。
「谁回复了谁」将来也是字段（`in_reply_to`），不是边。

### ⚠️ 三条从旧实现继承的血泪（都是实测，不是推断）

| 坑 | 教训 |
|---|---|
| `INSERT IGNORE` 已存在就整条跳过、**不报错** | 报告说「入库 50 条」库里纹丝不动；判据看 `fetched_at` 变没变，**不看总数** |
| 重采用浅摘要**覆盖**长文正文（16081 字 → 267 字） | `text` 只在**变长或旧值为空**时覆盖 |
| 加字段要登记**四处**（schema/类型/toRecord/**写库 SQL 的 SET 与参数两处**） | 漏任一处**静默丢失** |

⭐ 这三条写进 repo 的注释里，不是只记在文档。

## 三、⏸️ 本期**不做**的

| 不做 | 为什么 |
|---|---|
| 任何 `RELATE` / 图边 | ⭐ 分析关系「随用随建、整批清除」—— 采集期建边等于提前锁死分析方式 |
| AI 判断 / 拟回复 | Console 是**调试台**，不是业务流水线 |
| 定时采集 / 配方 | 同上，先把原子能力逐个验通 |
| 「点发布」按钮 | ⚠️⚠️ **红线** |

---

## 四、实施顺序（每步都能单独验）

```
1. Console 骨架 —— 三栏(控制/输入/输出),每个按钮调一个底座函数,
                   ⭐ 返回值**原样显示**(Result 三态,不美化)
2. 控制那栏接通 —— goto/ready/scrollUntil，页面名从真表读
3. 输出那栏接通 —— 载荷捕获 + 原样 JSON 展示
4. 两张表 + repo —— 解析结果能落库，带三条血泪的防护
5. 输入那栏接通 —— focus/type/tap(⚠️ 不含发布)
```

⚠️ 每步真机验，判据写在那一步里。
⭐ 1-3 步**不碰数据库** —— 先证明「能采到」，再谈「存得对」。
