## 二、验收项(两件事,一次跑完)

### ① 草稿落库

**做**:X 工作台 → 采集任务 → ▶ 开始(跑完约 8~14 分钟,判断那步最慢)

**判据**:
| 看哪 | 期望 | 不对说明什么 |
|---|---|---|
| 编排报告 planReply 那行 | `拟出 N 条草稿 · **已落库 N 条**` | 只有「拟出」没有「已落库」= 适配器没接上 |
| 两个数 | **相等** | 不等 → note 里会写「⚠️ M 条没存进库」,看错误原文 |
| 查库 | `x_reply_draft` 行数 = N | 报告说存了、库里没有 = 又一次「看着成功实际没有」 |

```sql
SELECT count() FROM x_reply_draft GROUP ALL;
SELECT tweet_id, status, ai_text FROM x_reply_draft ORDER BY created_at DESC LIMIT 3;
```

⚠️ **N=0 也可能是对的** —— 判断层说「值得回复 0 条」时本来就拟不出草稿。
那时看 note 里的跳过原因(`ai_declined` / `duplicate_text` / `ai_no_answer`),
**不是故障**。

### ② 否决原因

**做**:X Inbox → 挑一条 → ✎拟回复 → **跳过这条**

**判据**:
| 看哪 | 期望 |
|---|---|
| 点「跳过这条」之后 | 弹出 6 个原因按钮(答非所问/太像广告/语气不对/事实错误/这条不该回/其他) |
| 选一个之后 | 弹窗关闭 |
| 查库 | 那一行的 `dismiss_reason` 有值 |

```sql
SELECT tweet_id, action, dismiss_reason, dismiss_note
  FROM x_reply_feedback WHERE dismiss_reason != NONE;
```

⚠️ **点「填入 X」不该弹原因框** —— 采用是常态(424/425),弹窗会打断节奏。
弹了就是 bug。

## 五、这条线到现在暴露过的 bug(都已修)

⭐ **每一个都是原来就在、只是没人看得见的** —— 是编排把它们逼出来的:

1. `endRun` 算出 **NaN** → 所有 run 永远停在 `running`(而 catch 吞成 warn)
2. 跳过原因**不分类** → 「跳过 10 条」看不出为什么
3. **双重计数** → 每条都被判「模板刷屏」,这条线**永远拟不出草稿**
4. `ai_declined` 混了「模型没答」与「模型说不该回」两种
5. **草稿没落库** → 报「拟出 6 条」而库里一条都没有

⚠️ 所以「先用一阵」不是拖延 —— 真实使用是目前最有效的 bug 暴露方式。
