## 1. 六步（用户定的，逐字保留）

```
① 搜索配方 ──► 获取约定时间内的数据
② 提取目标内容数据
```

⭐ 实测补充（2026-09-26 查库，60 条真 AI 判 worth 样本）：

| | |
|---|---|
| 有 bio | 20/60 |
| 能凑出 ≥3 条上下文 | **3/60** |
| `parent_text` 有值 | **0/60** |
| 孤立原创推（天生没上下文） | **39/60** |

**这个功能存在，但从没在 worth 推上真正跑出过结果**。

⚠️ 39/60 是孤立原创推，这个比例**不会因为改采集层而变好**

## 5. 抽象建议（用户要求：「对历史的函数如果有抽象不够的，可以提出建议」）

⚠️ **本节只提建议，不在本次动手** —— 抽象有代价，且本仓有「先复用后抽象」的既定决策。
每条都标了「现在做 / 接线时做 / 先别做」。

### 5.1 ⭐⭐ 建议一：`FlowStepOutcome` 缺「往下传什么」——**接线时必须做**

**现状**：

```ts
interface FlowStepOutcome { ok; produced; error?; note?; elapsedMs; }
```

`produced` 是**一个数**，语义由各步自己定：采集=采到几条、判断=**判了几条**、拟回复=拟了几条。

**病**：2026-09-26 实测 —— 判断步 `produced: 10`（判了 10 条），
而真正该当闸门的 `值得回复 0 条` **只写在给人看的 note 里，编排读不到**。
于是第 4 步照跑、空转 125 秒。

> 用户原话：「既然值得回复是零条，为什么第四步还需要跑呢？」

⚠️ 这不是第 4 步的 bug，是**契约缺了一格**：步与步之间只能传「一个数」，
传不了「这一步产出的**是什么**」。而 ③④⑤ 全都要往下传东西
（③ 传打包好的语境、④ 传 Claude 的建议、⑤ 传用户的选定）。

**建议**（两条路，倾向 B）：

- **A. `produced` 改成「候选数」** —— 改动小，但 `produced` 的含义被业务绑架，
  「判了 10/10 条」这个信息要另找地方；下次换个组合又得重来。
- **⭐ B. 加一格结构化产出**：

```ts
interface FlowStepOutcome {
  ok; produced; error?; note?; elapsedMs;
  /** ⭐ 往下传的东西 —— 下一步从这里取，不从库里捞 */
  payload?: unknown;
  /** ⭐ 有没有候选；false = 后续步骤跳过（不是失败） */
  hasCandidates?: boolean;
  /**
   * ⭐⭐ 观察点 —— 用户 2026-09-26：「每一个环节都应该有观察点，
   * 这样才可以真正追溯效果。」
   */
  evidence?: {
    /** 关键判据：判断=每条 verdict+理由 / 取数=命中缓存还是现取 / 送Claude=prompt多长、回多少字 */
    items?: unknown[];
    /** ⭐ 跨库的锚 —— 采集 journal 的文件名等。跨库不能 join，就存路径 */
    journalRef?: string;
  };
}
```

**观察点的三条设计约束**：

1. ⭐ **`evidence` 由 runner 统一落库**，不靠各步自觉写 ——
   ⚠️ 靠自觉的话新步骤天然在视野外（同 `feedback-guard-hardcoded-list-never-grows`）。
2. ⭐ **成功路径也要记** —— 用户已立的铁律：「这次采集完全成功，依据照样蒸发」。
   判断对了也要知道**凭什么对**，否则没法回归分析。
3. ⭐ **跨库用锚不用 join** —— journal 文件名存进 `flow_step_run`，要看时按名取。

⚠️ **另需修掉 `kindToStepType` 的兜底**（`flow-runner.ts:260`）：
末尾 `return 'fetch'` 会让**新增的 ③④ 两步默认变成 fetch**，
和现在 `planReply` 被归进 `judge` 同一个毛病。
→ 要么按 `step_id` 存真身份，要么**新增步骤时强制指定**，不许兜底。

跳过时状态标 `skipped`、措辞写明「上一步没产出候选」——
⚠️ 必须与「出错了」**分得开**（现在两者在面板上都长得像「跑完了」）。

⭐ 选 B 的理由：这套编排以后会加步骤，A 那种「把业务判据塞进通用字段」
下次还要重来；而且 `flow-runner` 的分派本来就是泛型的
（`caps[step.kind]`，`flow-runner.ts:183`），**加能力不用动 runner** ——
契约扩一格是唯一要动的地方。

### 5.2 建议二：「进某页 → 等载荷 → 解析 → 回写」是第 4 次重写 —— **先别做**

同一个形态已经有四份：`fetchParentTweet` / `harvestAuthorProfile` /
长文正文补全 / `autoCollect`。③ 再接就是第五份。

**建议**：抽一个 `visitAndHarvest({ url, waitFor, parse, persist })`。

⚠️ **但现在别动**：四份各有真实差异（超时预算、停止判据、失败语义），
贸然合并会把「差异」变成「参数」，参数多到一定程度比重复更难维护。
⭐ **判据**：等 ③ 接完、真的出现第五份且形态确实一致，再抽。
（本仓既定决策：「先复用后抽象」。）

### 5.3 ⭐ 建议三：`askAI` 的 prompt 打包该独立成层 —— **现在做**

④ 要把 bio + 上下文 + 推文拼成 prompt。⚠️ 别把拼装逻辑写进 flow capability：

- prompt 格式会反复调（这是**学习环节的主战场**：改 prompt 比训练模型快得多）
- 拼装是**纯函数**，可单测、可离线回放，不需要 webview
- 将来「问 Claude 要选题建议」「要素材」都要复用这一层

**建议**：`x-reply-prompt.ts`，纯函数 `buildReplyPrompt(items) → string`
+ `parseReplyAdvice(markdown) → Advice[]`。
⭐ 一进一出都是纯函数 —— ④ 的 capability 只管调 `askAI` 和存结果。

⚠️ `parseReplyAdvice` 必须**fail loud**：Claude 的回答格式变了要**报**，
不能静默返回空数组（否则现象是「点了没反应」——本仓最贵的一类 bug）。

### 5.4 建议四：三张「人的表态」表口径不一 —— **先记账，别动**

`x_reply_draft`（AI 产出流水）/ `x_reply_feedback`（人的结论）/
`tweet_feedback`（标注语料）—— 三张表都在记「人怎么看这条推」，口径不同。

⚠️ 现在合并**风险极高**：`tweet_feedback` 有 9714 条历史语料且**自带 text 不 join**
（记忆 `project-x-audit-view-miss-rate` 记着这是它不受删除影响的原因）。
⭐ 本次只**加字段**（§6），不动表结构。等 ⑥ 的点评数据积累一轮，
看清真实读写口径再谈合并。

## 6. 数据模型：只加字段，不动表

⚠️ 本仓铁律 `project-x-field-four-place-registration`：
加字段要登记**四处**（schema / 类型 / toRecord / **写库 SQL 的 SET + 参数两处**），
漏任一处都**静默丢失**。

`x_reply_draft` 增：

| 字段 | 为什么非有不可 |
|---|---|
| `context_snapshot` | ⭐⭐ 拟稿当时看到的 bio + 上下文。**没有它这批数据教不了任何人** —— 模型学不到「在这种语境下该这么答」，只能学到「照抄这句话」 |
| `advice_raw` | Claude 的建议原文（用户改之前的） |
| `user_edit_diff` | ⭐ 用户改了什么。**diff 本身就是最强学习信号**，不用用户额外打字 |
| `review_note` | 可选的「为什么这么改」 |
| `reviewed_at` | ⚠️ 可**多次**更新 —— 已发送仍可回头改点评（§1.2） |

⚠️ `option` 字段一律传 `undefined` 不传 `null`（SurrealDB `NONE ≠ NULL`）。

### A 的实现注意（⚠️ 别做成「填了不生效」）

⚠️ `fetchParentTweet` **当前只能取紧邻 1 条** —— 不是参数没开，
是**实现只读那一条**。所以「做成变量」≠ 加个参数就完事，
必须同时把实现改成「能往上翻 N 条」，否则就是本仓最常见的死参数形态
（`ArrowStyle`/`slack` 那一类：类型有、JSON 有、消费层零消费）。

⭐ 代价不大：它已经在详情页了，X 的 status 页**本来就把整条会话链渲染出来**，
多读几条是同一次导航里的事，**不用多跳页**。

⚠️ 守卫要求：参数必须**真的改变行为** —— 传 1 和传 10 取回的条数不同，
不能只断言「参数传下去了」（源码扫描看不见「会不会执行」）。

## 8.5 ⚠️⚠️ 自动填入的额外约束（用户 2026-09-26 定，**开工前必读**）

> 「真正自动输入还得多检查，而且见一个做一个变量，
> 　如果没次最大自动填入的条目不得大于多少。」

### 三条，缺一不可

**① 每次最多填 N 条 —— 变量，由用户设**

`maxPerRun` 可配，默认给小（如 3）。**上限由用户定，代码不封顶**。

⚠️⚠️ **我曾在这里加过一个「代码硬顶」，被用户否决**（2026-09-26）：

> 「你这是剥夺我的自由权。不用自由权？」

⭐ 用户是对的，而且我的理由站不住：我当时写「参数会被人改大」——
**那个人就是用户本人**，他改大它就是他的决定。
⚠️ 这与 `feedback-dont-record-own-choices-as-user-requirements` 同形：
**把自己的保守当成硬约束写进文档**，此后就再没人质疑它。

⭐ 正确做法：把**代价**说清楚（这个数 = 一次跑最多影响多少条对外发言），
让用户看着数字决定，而不是替他封顶。
判据：这个数必须**一眼看得到**，不能藏在配方 JSON 里。

**② 见一个做一个，不批量并发**

⚠️ 「一次填 N 条」不是「同时填 N 条」：
逐条走（填 → 回读确认填进去了 → 再下一条），任何一条失败就停，
**不继续后面的**。
⭐ 理由：批量并发时一条出错，你不知道前面几条是什么状态；
而这一步动的是**公开时间线上的回复框**。

**③ 每条都要回读确认**

填完必须确认「正文真的进了回复框」才算这条成功。
⚠️ 本仓最忌「看着成功实际没有」——而这一步的失败形态正是那种：
`pasteReply` 返回 success 但框里是空的。

### ⚠️ 红线仍然是红线

自动**只到填进回复框**，发布永远是人点。
上面三条是在红线**之内**再加的保险，不是放宽的理由。

### 为什么这三条要写在这里

⚠️ 自动填入是整条流水线上**唯一会真的动 X 页面**的一步，
而且动的是对外发言。它的错误**不可回滚**（发出去了收不回来）。
⭐ 前面每一步出错最多是「数据不好看」，这一步出错是「人设崩了」。
