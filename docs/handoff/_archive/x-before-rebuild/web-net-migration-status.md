## 3. 真因：还没查到

已排除（有证据）：

- ❌ X 改了接口 —— 用户截图里 bio 明明在
- ❌ 采集 detach 掐断 —— 迁完照样失败
- ❌ partition 名推错 —— 目录时间戳证否

⭐ 未排除：`candidatesFor(pageId)` 为什么恒空。链条是：

```
webRequest 侧 recordRequestStart  →  bus.requests[pageId]
                                       ↓
CDP 侧 attachProviderBody  →  findClosestMatch(candidatesFor(pageId))
                                       ↓ 配不上
                              「关联失败」→ onPayload 永不触发
```

⚠️ 下一步该查的是 **`pageOf()` 反查**（`webContentsId` 对不对得上、
`registerPageIdLookup` 注册时机），而不是再猜。

## 4. ⚠️ 结构性问题：`wireWebRequestSide` 绕了一道

```
现在：wc → readPartition(wc) → 名字 → session.fromPartition(名字) → session
改成：wc → wc.session
```

⭐ `wc.session` **就是**那个 Session 对象，不需要名字。
⚠️ 而 `fromPartition(名字)` 的语义是「同名返回已有的，**不同名就新建一个空的**」
（已查证 Electron 类型定义）—— 名字一旦对不上就静默挂到空 session 上。
⚠️ Electron **没有** `session.partition` 这个 getter（只有 `storagePath`），
所以现有代码只能反推 —— 不是偷懒，是 API 逼的。

**这一条无论真因是什么都该改**：它消除的是一整类风险。

## 5. 收口方案（用户定方向后再动）

### 原则

⚠️ **旧的没下线之前，新的不许再接管任何模块。**
本次事故证明：往一个没有成功案例的抽象层上迁东西，
等于拿能用的换没验过的。

### 三条路

| | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 先修好新机制，再迁** | 查清 `candidatesFor` 恒空的真因 → 修 → 用 bio 验证（0/192 → 有数）→ 再逐个迁 | 中 | ⭐ 低：有成功案例才迁 |
| **B. 放弃新机制，全回旧的** | 把 2 个已迁的改回自己 attach | 小 | ⚠️ 回到「8 处各自 attach/detach」的老问题（`47582b72` 想消灭的那个） |
| **C. 维持现状** | 什么都不做 | 0 | ⚠️ bio 永远 2%；且下次有人又会踩「迁过去就坏」 |

⭐ **倾向 A**，判据是：
**新机制必须先有一个真实成功案例**（bio 从 0/192 变成有数），
才有资格接管第二个模块。

### A 的执行顺序

```
1. 查 candidatesFor 恒空的真因（诊断已加宽，跑一次备料就有答案）
2. 修 wireWebRequestSide 收 wc.session（无论真因是什么都该做）
3. 修真因
4. ⭐ 用 bio 真机验证：0/192 → 必须有数
5. 有成功案例之后，才逐个迁剩下 5 个
6. 每迁一个都真机验证 payloads ≠ 0（单测证明不了 CDP 行为）
```
