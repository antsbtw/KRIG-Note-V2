## ✅ 已定稿:采集链路

### 核心原则:PDCA 闭环(已立为可靠性纲领**铁律五**)

见 `docs/00-architecture/reliability-charter.md` §1。用户原话:
> 「要把函数做的健壮,就必须是正反馈的 —— 执行没有?执行结果是什么?能够执行下一步了吗?」
> 「必须有判断--执行--再判断--再执行这样的 PDCA 环。」

具体到采集循环:

```
滚一轮 → 回读(位置/UserCell 数/新增人数) → 判断
   ├─ 有新数据      → 继续
   ├─ 位置不动      → 换位置(scrollIntoView 跳到末尾卡片)
   └─ 连续 40 轮零新增 → 采到底了,停
```

⭐ **轮数是安全网不是目标**(默认 5000,正常走不到);面板两个框**留空即可**。
⭐ 阈值 40 用实测定:正常页间隔最大 7 轮(5.7 倍,不误停);真到底时空转 259 轮。
⭐ **每轮落盘** `/tmp/x-scroll.log` —— 今天正是它一举定案,**建议保留**。

## ✅ 已定稿:增量采集

`x_list_snapshot` 表(migration 1.2.5)每次采集存一份完整名次表,与上次求**差集**。

### ⭐ 排序证据(悬了三天的问题,已有答案)

**X 的 followers 列表是严格按关注时间倒序的**,2770 人实测:

- 11 个新人全部落在 **seq 0-10**(最前面,连续无间断)
- 老人位移**全体 +10 或 +11**(净增正好 10)
- 相对顺序颠倒 **0 / 2769 对**

⚠️ 判断时别用「位移要小」当判据(我一开始写错过)——
正确期望是**位移 ≈ 净增人数**(整体平移),以及**相对顺序零颠倒**。

⭐ 2026-09-19 补:面板上那句判词**原来正是错的**(写的 `medianShift <= 5`),
而真实那跑 `medianShift = 10` —— 旧判据会把**教科书级的时间倒序**
判成「证据还不够」。已改成 `|medianShift - 净增| <= 2`。

⭐ 另:唯一那个取关者在上次的 seq=868,**恰好**是位移从 +11 变 +10 的切换点 ——
模型分毫不差地解释了全部 2770 个位移。这条证据强到可以直接拿来做早停。

### 1. ~~快速增量~~ ✅ 已落地,但**没真机跑过**

面板上多了一个「**快速增量**」按钮(挨着「采集」)。两个按钮走**同一条链路**,
只差 `fastIncremental` 一个参数。

**离线回放实测**(拿库里真实的 2781/2771 两份快照跑判据):

| 模拟新增 | 停在第几人 | 翻了几页 | 采到新增 | 漏掉 |
|---|---|---|---|---|
| 11(真实情况) | 41 | 1 | 11 | **0** |
| 100 | 130 | 3 | 100 | **0** |
| 500 | 530 | 11 | 500 | **0** |

#### ✅ 真机验收(2026-09-19 23:10,用户实跑)

| 检查项 | 结果 |
|---|---|
| **没写快照** | ✅ 最新批次仍是 20:09 的 2781,**无新增批次** |
| 只翻一页 | ✅ 采 **50 人**(list_seq 0..49)即停 |
| 新人全在最前 | ✅ 9 个新人全在 **seq 0..8**,连续无散落 |
| 之后全是老人 | ✅ 第 9 号位之后 **41 人全部已知** |
| 基线没被动过 | ✅ `基线快照 - x_author = 0`,一个人没丢 |

本次新增 9 人:`@qian_xh @jing69712168 @realoldforest @doctorchaocn @wrapmoney
@ddw88523 @dcmxnhucc @frankwang3927 @freexiao84`

**对账**:`x_author` 现有 **2799** = 2781(基线全量)+ 9(本次)+ 9(更早零星采到的,
基线快照没收录);X 页面显示 2801,**差 2 人**,用户判定可接受
(多半是 23:10 之后又新关注的)。

⚠️ **查库有个坑**:`counts_at > '2026-09-19T23:00:00Z'` 这种**裸字符串比 datetime**,
SurrealDB **不报错但结果不对**(本该 50 行,返回了全部 2799 行)——
我差点把 2799 当成「这跑采了 2799 人」。改成全量取回、在 python 里按前缀筛才对。

#### 设计上必须知道的三条

1. **它看不见取关**。取关者是从名单**中间**消失的(实测那位在 seq 868),
   只翻前几页永远发现不了。报告里每次都会明说,并提示距上次全量多少天。
   → **「谁取关了」只有全量答得出**,建议每周跑一次全量。
2. **它绝不写快照**(`mayWriteSnapshot = !ranFast`)。这是最危险的一条:
   快速模式只采几十人,存成快照会让**下次差集报「取关 2700 人」**,
   一次就毁掉基线,而且**在数据里看不出来**(表里确实有条完整记录,只是只有 60 行)。
   守卫 `fast-incremental.test.ts` + `list-snapshot.test.ts` 钉死,已注入验证变红。
3. **取不到基线就退回全量**,不是「当成谁都不认识然后按快速模式跑」——
   后者会翻满闸门,报出一个**看着像增量、实则是残缺全量**的结果。
   ⚠️ 判据是 `ranFast`(真拿到名单了吗)不是 `opts.fastIncremental`(人想不想快),
   两者差一个字、行为相反:退回全量那跑**是**完整列表,必须写快照。

#### 停止判据(PDCA)

```
翻一页 → 回读(这页有几个人?几个是已知的?) → 判断
   ├─ 这页全是新人      → 还没追上,继续翻
   ├─ 连续 30 个已知    → 追上了,停
   └─ X 说没有更多了    → 到底了,停(小号场景)
```

⚠️ 阈值 30 是**连续**不是累计(见到新人清零)。小于一页人数(50-100)
才触发得了,又要大到不被零星交错误判。
⚠️ **判据必须用「这一页」的人**,不能用累计 Map —— 累计表里已见过的人
不会再出现,「这页有几个已知的」恒为 0,判据永不成立。
这与「采人页数 article 恒为 0」是同一形态的开环缺陷。

⭐ **没追上就停会报 problems**,并说清连续已知数/阈值/翻了几页 ——
「追上了」和「撞闸门」在报告里本来长得一模一样,而人会照着数字下结论。

## 🔴 给接手者的工作方法提醒

今天绕的弯路都源于同一件事,**请避免**:

1. **没有基线就别改第二次**。用户说「怎么越修改越差了呢」时,
   我该立刻完整回退确认基线,却又改了两轮,把 2691 改成 250。
2. **平台侧问题先搜社区**。GET/POST 那个真因,我在自己代码里查了六轮全错,
   用户提醒「可以到社区论坛查找一下方法呀」后一次搜索就中。
3. **守卫容易假绿**。今天写的守卫有 3 条第一版是假绿的
   (整块 `toMatch` 被同名符号兜住)—— **必须切片到分支/赋值,并注入违规验证变红**。
4. **别把自己的判断写成结论**。「2500 天花板」那条我写得像事实,还进了记忆,
   结果是错的,误导了后续好几轮排查。
