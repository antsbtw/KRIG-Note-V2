> v0.1 · 2026-09-01 · **原则确立,先于任何落地**
>

## 0. 一句话总则

> **先把每个实体独立地描述清楚,再谈它们之间的关系。
> 关系不得反过来决定实体的归属、形态或存储位置。**

---

## 1. 三条根本原则

### 原则 1:实体优先(Entity First)

**每个实体必须能被独立地、完整地描述,不依赖任何关系才成立。**

判据:**把这个实体单独取出来,它的描述是否还完整?**

- ✅ 一本书:书名、作者、文件路径、格式 —— 单独存在就是完整的
- ✅ 一条推文:id、正文、作者、发布时间、互动数 —— 单独存在就是完整的
- ❌ "这本书关联的笔记" —— 这不是实体,是关系

**推论**:
- 实体不得为了"方便建立关系"而被拆散、混入公共池,或改变自身形态
- 若某个字段只有在"和别人关联时"才有意义,它属于关系,不属于实体

> **反例(现状)**:`atom` 表把 pm / ebook / thought / folder / graph 全塞在一起,
> 靠 `payload.domain` 区分,`payload` 类型是 `any`。
> 这是**为了让边能统一指向而牺牲实体独立性** —— 违反本原则。
> (见 [storage-isolation-boundaries.md §7](storage-isolation-boundaries.md))

### 原则 2:关系是第二性的(Relations Are Secondary)

**关系是实体之间的第二性事物,后建、可重算、可删除,不得侵蚀实体本身。**

- 关系**不决定**实体存在于哪个空间
- 关系**可以**被删除、重建、整批清空,而实体不受影响
- 删除关系不得损坏任一端的实体

**关系分三类**,生命周期不同:

| 类 | 例 | 性质 |
|---|---|---|
| **结构关系** | 块的父子、文件夹树 | 与实体同生命周期,**优先做成实体的属性而非边** |
| **业务关系** | 这条想法关于这本书 | 用户意志产生,持久,显式删除 |
| **分析关系** | 相似度、共现、推荐 | 算法产生,**随用随建、整批清除** |

> **结构关系优先用属性** —— 这是 [decision 028](../90-archive/refactor-v2/data-model/persistence/decisions/028-block-structure-via-attrs.md)
> 已确立的结论:文档本体零边,靠 `noteId`/`parentId`/`order` 属性。
> 理由是可靠 + 快:导入即完整,不会出现"实体在了但边丢了"的半残状态。

### 原则 3:分析维度是计算属性(Derived, Not Source)

**任何可以从实体和关系推导出来的东西,都不是真源。**

- 计数、比率、排名、聚合 —— 一律**可重算**
- 存它们**只为查询快**,不为正确性
- 一旦与真源不一致,**以真源为准,重算覆盖**

**推论**:
- 不得把派生值当唯一真源(否则一旦算错,数据永久污染)
- 派生表/物化视图必须能**整表清空后从真源重建**
- **默认不做物化** —— 先直接聚合,量大到真慢了再物化

> **反例**:曾把 `accepted_count` 之类的计数字段直接写进作者表。
> 采纳了但计数没加、删了但计数没减 —— 计数与真实数据不同步是最常见的 bug 源。

## 2. 由原则推出的设计纪律

### 2.1 实体描述必须自足

每个实体表的字段回答"**这个东西是什么**",不回答"**它和谁有关**"。

| 属于实体 | 属于关系 |
|---|---|
| 推文的正文、发布时间、作者 handle | "我采纳了它"(可以是属性)、"它回复了谁"(是关系,但…) |
| 书的标题、格式、路径 | "它关联了哪些笔记" |

> **边界情形**:`in_reply_to` 这类**外部世界自带的、随实体一起抓到的**引用,
> 存为实体字段是合理的 —— 它是推文自身的事实,不是我们建立的关系。
> **判据**:这个引用是"这个物体本来就有的属性",还是"我们后来建立的连接"?

### 2.2 引用必须自描述

跨空间引用**不得存裸 id**,必须标明对方是什么、在哪:

```
SpaceRef { space: string, id: string }
```

理由:裸 id 无法判断指向何处,一旦空间划分变化就是悬空引用。
自描述引用让"这个引用指向哪"成为数据本身的一部分,而不是靠调用方记忆。

### 2.3 实体的唯一标识由自己定义

- 用**业务 id**(ULID),不用存储引擎的内建 record id
  > 教训:曾把内建 record id 声明成 `TYPE string`,SurrealDB 3.x 下
  > CREATE 后同事务 UPSERT 触发 readonly,新建/保存静默失败。
  > **永远别 DEFINE FIELD id。**
- 外部实体用**外部世界的标识**(推文用 `tweet_id`、邮件用 `message_id`),
  便于去重和对账

### 2.4 生命周期是实体的属性,不是表的划分

同一类实体不得因"状态不同"被拆进不同的表。

> **反例**:曾计划"采纳的推文进 archive 表、未采纳的留 inbox 表"。
> 采纳与否是**状态属性**,不该决定行存在哪张表。
> 正确做法:一张表 + `expires_at`(NONE = 永久)表达生命周期差异。

**允许按生命周期分表的唯一情形**:两类数据的**保留策略根本不同**
且**从不互相转化**(例如"日志"与"业务数据")。

### 2.5 边界清晰:一个实体只有一个真源表

- 不得同一实体在两处各存一份(必然不同步)
- 需要冗余快照时,**明确标注它是快照**并说明为何不算重复
  > 例:推文行存 `author_name_at_post`(发推时的展示名)与
  > 作者表的 `display_name`(当前名)语义不同,不算重复。

## 3. 空间划分原则

### 3.1 划分依据:实体的自然归属

**按实体本身属于什么来分,不按 UI 的 view 来分。**

- ✅ 推文、邮件 —— 外部采集的独立实体,各自成空间
- ❌ "pdf 空间" —— PDF 导入后就是 note 的块,它不是独立实体类别

判据三问:
1. 这类实体**能否独立存在**(不依赖其他空间就完整)?
2. 它的**生命周期/清理策略**是否独立?
3. 它是**用户创作**还是**外部采集**?

三问都指向"独立" → 应有自己的空间。

### 3.2 跨空间关系落在应用层

**实测约束**(2026-09-01,SurrealDB):
- **不支持**跨 database 的单语句查询(`SELECT` 跨库报表不存在;
  全限定名 `ns:db:table` 是 parse error)
- **支持**同一请求内 `USE DB` 切换,且 `LET` 变量跨切换存活

因此跨空间关系必须由应用层解析:按 space 分组 → 逐空间查询 → 拼装。
**这是成本,但它换来实体独立性 —— 按原则 1,这个交换是值得的。**

### 3.3 关系的存放位置

跨空间关系**存在独立的关系空间**,不塞进任一端的空间。

理由:关系是第二性的(原则 2),放进任一端会让那一端"拥有"关系,
删除该空间时关系跟着消失 —— 而关系的生命周期本就该独立管理。

## 4. 反模式清单

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 为了让边统一指向,把不同实体塞进同一张表 | 违反原则 1 | 各实体各自建表,引用用 SpaceRef |
| 用边表达"块的父子"这类结构 | 结构关系与实体同生命周期,边容易丢 | 用属性(decision 028) |
| 计数字段存进实体表当真源 | 违反原则 3,必然不同步 | 聚合查询;真慢了再做可重建的物化表 |
| 按状态(采纳/未采纳)分表 | 违反纪律 2.4 | 状态是属性,一张表 |
| 存裸 id 做跨空间引用 | 空间划分一变就悬空 | SpaceRef 自描述 |
| `DEFINE FIELD id` | 撞存储引擎内建标识,静默失败 | 业务 id(ULID) |
| `option<T>` 字段写 `null` | SurrealDB 的 NONE ≠ NULL,写 NULL 不是"空" | 写 `undefined` |
| 先建一堆边"以后可能有用" | 边的形态在真实数据跑出来前是猜的 | 需要时再从字段算;确有需要再物化 |

## 5. 落地纪律

1. **任何模块的数据模型设计,必须能逐条对照本文的原则**,
   说明哪条适用、如何满足;不能对照的部分要显式说明为何例外
2. **原则冲突时,实体独立性优先**(原则 1 是根)
3. **本文修改需要理由**:发现原则本身有问题时改原则,
   而不是为了让某个落地方案通过而放宽原则
4. **既有代码不追溯改造** —— 本文约束新设计;
   存量(如 `atom` 表)的改造单独评估收益与风险
