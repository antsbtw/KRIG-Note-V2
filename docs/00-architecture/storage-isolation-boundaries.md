# 存储隔离边界:哪些模块该分独立库,哪些不该

> v0.1 · 2026-09-01 · **分析结论,未开工**
>
> 起因:X 模块拍板走独立 database(见
> [x/persistent-tracking-and-profiling.md §4.1(3.5)](../10-business-design/x/persistent-tracking-and-profiling.md))后,
> 用户提问:note / pdf / web 等工作空间是否也都该用独立表空间?
>
> 相关:[charter.md](charter.md)、[relations/spec.md §11.2](../90-archive/refactor-v2/data-model/relations/spec.md)

---

## 0. 结论先行

> ⚠️ **§0~§5 是初版结论;§7 是 2026-09-01 与用户讨论后的修订,
> 部分论证被推翻(尤其"分库会切断边"这条推理不成立)。
> 读到 §5 请务必继续读 §7。**

**初版判断:不是"都该独立",而是有一条清晰的分界线:**

> **共享知识图谱的模块必须同库;外部采集的数据该分库。**

| 模块 | 归属 | 理由 |
|---|---|---|
| note / pdf / ebook / web剪藏 / thought / folder / graph | **同一个库(现状不动)** | 它们**共享 atom + edge**,彼此有真实的跨域边 |
| X | **独立库 `krig_x`**(已拍板) | 外部采集,与知识图谱零关联 |
| mail | **建议独立库** | 同上 |

---

## 1. 关键实测:note 系模块之间有真实的跨域边

这是判断的**决定性证据**。查库实测(2026-09-01):

### 1.1 atom 的域分布

```
pm              102918   ← note 正文(块)
bookmark           256   ← web 书签
folder              59
thought              8   ← 读书想法
ebook                4
reading-state        4
graph-canvas         1
graph-instance       1
```

**它们全都住在同一张 `atom` 表里**,靠 `payload.domain` 区分。

### 1.2 边确实跨域连接

实测把边的两端 atom 解析出域:

| 边 | subject 域 | object 域 | 含义 |
|---|---|---|---|
| `user:krig:thoughtOf` | **thought** | **ebook** | 这条想法是关于这本书的 |
| `user:krig:hasReadingState` | **ebook** | **reading-state** | 这本书的阅读进度 |
| `user:krig:hasReadingThought` | **ebook** | **pm(note)** | 这本书关联的笔记 |
| `user:krig:hasNoteView` | pm | — | note 视图 |
| `user:krig:inFolder` | folder | folder/pm | 文件夹树 |

**`ebook → pm`、`thought → ebook` 这些边是真实存在的跨模块关系。**

如果把 ebook 分到独立库、note 留在原库:

- 这条边的两端**分属两个 database**
- SurrealDB **无法跨库 JOIN**
- "这本书关联的笔记"这个功能**直接断掉**

> 用户提问里说"包括数据边的建立会更好" —— 实测结论恰恰相反:
> **对这些模块,分库会让边无法建立。**

## 2. 判据:什么样的模块该分库?

不看"是不是不同功能",看**三个客观属性**:

| 判据 | 该同库 | 该分库 |
|---|---|---|
| **是否共享实体/边** | 有跨域边 → 必须同库 | 零关联 → 可分 |
| **数据来源** | 用户创作的知识 | 外部采集(抓取/同步) |
| **生命周期** | 与笔记同生命周期 | 独立过期/清理策略 |

按此判据:

**note / pdf / ebook / web / thought / graph —— 同库**

它们本质是**同一个知识图谱的不同视图**:一本书(ebook)可以关联笔记(pm)、
产生想法(thought)、记录进度(reading-state);一个 PDF 导入后就是 note 的块。
**"模块"是 UI 层的划分,不是数据层的划分。**

**X / mail —— 分库**

- 外部采集,不是用户创作
- 与 atom/edge 零关联(实测 X 的 `tweet_inbox` 与 atom 表无任何外键)
- 有独立的过期策略(X 7 天 TTL、mail 按账号同步)
- schema 演进节奏与笔记无关

---

## 3. 那"后期数据维护"的诉求怎么满足?

用户的担心是合理的 —— 都挤在一个库里,维护确实有压力。但**解法不是分库**:

| 担心 | 分库能解决吗 | 更合适的解法 |
|---|---|---|
| 表太多、看不清归属 | ✗ 分库后要跨库查,更难 | **命名规范** + schema 文件分节(现状已按模块分段) |
| migration 互相阻塞 | 部分能 | migration 按模块分文件、独立编号(不必分库) |
| 误删风险 | ✓ | 备份策略 + 删除前校验(edge 的孤儿清理已有先例) |
| 查询变慢 | ✗ | **改写查询**。实测一次跨表 `INSIDE` 子查询耗时 **15.3 秒**(见 §4),是写法让索引失效,与分库无关 |
| 数据边混乱 | ✗ **反而更糟** | 边的命名空间分层(`user:krig:*` / `ai:*`)已在 §11.2 确立 |

> **关键**:上表里只有"误删风险"是分库真能解决的,而它对 note 系模块并不突出
> (它们本来就该一起备份、一起恢复)。

## 4. 一个真实的性能信号

实测中一条跨表子查询跑了 **15.3 秒**:

```sql
SELECT VALUE payload.domain FROM atom
WHERE <string>id INSIDE (SELECT VALUE 'atom:' + object.atomId FROM edge WHERE ...)
```

10 万行 atom + 全表扫描 + 字符串拼接比较。**这说明真正的瓶颈是查询写法,
不是"表里东西太多"。** 分库不会让这条查询变快 —— 它在任何一个库里都一样慢。

**注**:`edge` 的索引其实是齐的(实测 [schema.ts:70-80](../../src/storage/surreal/schema.ts#L70):
`predicate` / `subject.atomId` / `object.atomId` / `subject.atomId+predicate` 都有)。
所以这条慢查询不是缺索引,而是**查询写法**的问题 ——
`'atom:' + object.atomId` 这种字符串拼接后再 `INSIDE` 比较,
使得索引无法命中,退化成全表扫。

**结论不变**:瓶颈在查询写法,分库同样解决不了。真要优化,
方向是改写这类查询(用 record link 而非字符串拼接),而不是拆库。

---

## 5. 建议

1. **note / pdf / ebook / web / thought / graph 维持同库** —— 它们共享知识图谱,
   分库会切断真实存在的跨域边
2. **X 按已定方案分出 `krig_x`**
3. **mail 建议同样分出** —— 判据与 X 完全一致(外部采集、零关联、独立生命周期);
   可与 X 的 client 多连接改造一并做,边际成本低
4. **图查询慢的真因是写法不是分库** —— `edge` 索引已齐备;
   慢在字符串拼接式的跨表比较使索引失效。要优化就改写查询,分库无助于此
5. **不做"每个 view 一个库"** —— 那是把 UI 划分误当数据划分,
   会把一个完整的知识图谱切碎

## 7. 补充讨论(2026-09-01):实体独立性 vs 关系可达性

用户提出方法论质疑,值得正面回应:

> 首先保留物体的独立性,然后再为物体建立关系,这才是正确的自然方法。
> 如果为了建立关系把物体切碎了,数据的管理将会很混乱。
> 每个空间应该有自己的独立存储空间,然后在存储空间中的 item 建立跨空间的查询关系才是正道。

### 7.1 这个原则是对的,而且 §1~§5 的论证有一处偏颇

**先承认问题**:上文用"分库会切断边"来反对分库,是**拿当前实现的限制,
去论证架构方向的对错** —— 这个推理方式不成立。

正确的顺序应该是:先确定**什么是对的建模**,再看**实现能不能支撑**;
若支撑不了,是补实现,而不是让建模迁就实现。

用户的原则本身站得住:

- **实体独立** —— 一本书、一条推文、一封邮件,各自是完整的物体,
  不该因为"要和别人建立关系"就被拆进公共池
- **关系后建** —— 关系是**物体之间的第二性事物**,不该反过来决定物体存在于哪里
- **跨空间查询** —— 这是正常需求,不是异常

### 7.2 但有一个实测约束必须摆上桌

**SurrealDB 不支持跨 database 的单语句查询。** 实测(2026-09-01):

```sql
-- 在 krig_note_v2 里查 probe_test 库的表
SELECT * FROM probe;
→ ERR: The table 'probe' does not exist

-- 全限定名
SELECT * FROM krig:probe_test:probe;
→ Parse error: Unexpected token `:`
```

**但同一次请求里可以 `USE DB` 切换,且变量跨切换存活**:

```sql
USE DB probe_test;
LET $v = (SELECT VALUE v FROM probe);
USE DB krig_note_v2;
RETURN $v;
→ ["hello"]          ← 成功
```

这意味着:**跨空间关系是可实现的,但要在应用层做**,不能靠数据库的 JOIN。

### 7.3 所以真正的取舍是什么

不是"能不能分",而是**关系解析的成本落在哪一层**:

| | 单库(现状) | 多空间 + 应用层关联 |
|---|---|---|
| 实体独立性 | ✗ 都挤在 `atom` 表,靠 `payload.domain` 区分 | ✓ 各空间自治 |
| 关系查询 | ✓ 一条 SQL | ✗ 应用层两次查询 + 拼装 |
| 数据管理 | ✗ 备份/清理/migration 全绑一起 | ✓ 各自独立 |
| 误删爆炸半径 | ✗ 全局 | ✓ 限于单空间 |
| 实现成本 | 0(现状) | 需要一层"跨空间引用"抽象 |

**用户的判断是:实体独立性和数据管理的收益,大于关系查询要多写一层的代价。**
这个判断是合理的 —— 尤其考虑到:

- 实测跨域边总共只有 **9 条**(thoughtOf 3 + hasReadingState 4 + hasReadingThought 2)
- 相比之下 `pm` 有 102918 行。**关系是稀疏的,实体是海量的**
- 为了 9 条边的查询便利,让 10 万个实体挤在一张表里,**性价比确实不对**

### 7.4 若采纳,需要什么

**一层"跨空间引用"抽象**,把 §7.2 的机制包起来:

```
SpaceRef { space: 'note' | 'ebook' | 'x' | 'mail', id: string }
```

- 关系表**存 SpaceRef 而非裸 id** —— 引用明确标注对方在哪个空间
- 提供 `resolveRefs(refs: SpaceRef[])` 批量解析:按 space 分组 →
  每组一次 `USE DB` + 批量查 → 合并返回
- **关系本身存哪?** 两种选择:
  - 各空间存自己发出的关系(ebook 库存 `ebook→note` 的边)
  - 或独立的 `krig_relations` 库专存跨空间关系
  *倾向后者* —— 关系是第二性的,单独一个空间管它,符合"物体独立、关系后建"

### 7.5 但这是一次大改造,要认清代价

- `atom`/`edge` 是 **V2 的地基**,102918 行数据 + 60 处边查询调用点
- 拆分意味着:重新划分 domain 归属、迁移全部数据、改所有跨域查询、
  重写 migration 体系
- **风险等级远高于 X 分库**(X 是新表,拆分是动地基)

### 7.6 建议的推进方式

**不要现在整体重构**,而是:

1. **X / mail 先按新原则做**(它们本来就该独立,且是新建/低耦合)——
   顺便**把"跨空间引用"抽象打磨出来**,在低风险场景验证
2. **note 系维持现状**,直到抽象层被验证成熟
3. 届时再评估:note/ebook/graph 拆分的收益是否值回改造成本 ——
   那时有真实的抽象层可用,决策依据比现在充分

> 这不是否定用户的原则,而是**同意原则、分歧在节奏**:
> 地基改造应该在新场景验证过之后再动,而不是一次性推倒。

### 7.7 修正 §5 第 5 条

原文"不做每个 view 一个库 —— 那会把知识图谱切碎"**措辞过重**。
更准确的表述:

> **按"空间"划分存储是合理方向**(用户原则),但:
> - 划分依据应是**实体的自然归属**,不是 UI 上的 view 划分
>   (例如 pdf 导入后就是 note 的块,不该有独立的 "pdf 空间")
> - 需要先有"跨空间引用"抽象,否则跨空间关系无从实现
> - note 系地基的拆分,应在抽象层于 X/mail 验证成熟后再评估
