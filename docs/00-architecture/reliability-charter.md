## 0. 为什么有这份纲领(一个真实事故的解剖)

2026-06-30,用户拖入 `docs/temp/relay-design-v2.md` 导入笔记。**导入日志显示成功**
(`failures=0 notes=1`),但生成的笔记**只有标题、正文全空**。

事后定位,根因是一条极窄的解析 bug(blockquote 剥离正则不容忍行首缩进 → 缩进引用行
无限递归 → 栈溢出)。**但 bug 本身不是重点——重点是它逃逸的方式:**

```
一处解析异常
  → 被最外层 try/catch 吞掉
  → 降级成一条 console.warn
  → 空 atoms 照常入库
  → 上报 failures=0(谎报成功)
  → 用户拿到一篇空白笔记,不知道发生了什么,也没有任何可回捞的痕迹
```

这次是导入。但同样的失败模式潜伏在**每一处** `try { ... } catch { return 默认值 }` 里。
问题不在某一个 bug,而在于 **app 缺少一个统一的、有牙齿的故障处理契约**。这份纲领就是那份契约。

> 与 charter §0 的呼应:V1 总纲的教训是「字面合规但运行时违规未消除」。同一个病在可靠性上的
> 变体是「**表面成功但运行时已坍缩**」。二者的解药相同:**运行时可见 + 机器可强制**。

## 1. 四条铁律(The Four Laws)

本纲领可压缩成四句话。后续所有细则、钩子、代码约定都是这四条的展开。

### 铁律一:失败要响(Fail Loud)

**任何异常不得被静默吞成默认值。** 捕获异常的唯一合法目的有三种,且必须显式选择其一:

1. **降级并标记**——产出一个可见的占位/错误态产物(见铁律二),同时上报遥测(见铁律三);
2. **上抛**——本层处理不了,原样 `throw`,交给能决策的上层;
3. **显式兼容**——仅在**代码注释明确标注**的已知兼容场景(如"旧版数据无此字段则补默认")才允许静默兜底。

> 禁止模式:`catch (e) { return [] }` / `catch { return null }` / `catch { /* ignore */ }`
> 不带上述任一意图。这类代码把 bug 变成"看不见的正确"。
>
> 呼应用户长期原则 [不要兜底 fallback](../../memory)、[别猜看真实数据](../../memory)。

### 铁律二:降级要局部(Isolate, Don't Collapse)

**容错的粒度必须匹配数据的粒度。** 处理 N 个独立单元(N 篇文档 / N 个块 / N 行)时,
第 k 个单元的失败**只能**损失第 k 个单元,不得掀翻整批。

- 逐单元 `try/catch`,失败单元产出**占位产物 + 保留原文**,然后**继续下一个**。
- 现有的 `unknownNode('originalType', raw, error)` 就是块级降级的标准范式——它必须在
  **每一层循环内**都够得着,而不能被一个包在最外层的 try/catch 架空。

> 事故复盘:md-to-pm 的 `unknownNode` 设计本身是对的(逐块降级),但栈溢出发生在**主循环之外**,
> `unknownNode` 根本没机会兜底。粒度错配 = 局部容错形同虚设。

### 铁律三:故障要留痕(Leave a Trace)

**每一次降级/上抛/兼容兜底都必须产生一条可回捞的遥测记录。** console 日志不够——进程一关就没了。

- 落盘到统一遥测层(见 §3),记录:时间、层/能力、操作、输入摘要、失败原因、原文片段。
- 记录必须**可 grep、可导出**,以支撑事后趋势分析与"这类 bug 到底发生过多少次"。

> 呼应 charter §5「可见可验证」:启动期已有 `diagnostics-bus`,本纲领把它延伸到运行期。

### 铁律四:成功要对账(Reconcile Success)

**不得在产出已坍缩时上报成功。** 凡"输入 → 产出"的转换,都要有**产出量 vs 输入量**的健全性检查:

- 输入非空(有实际内容)但产出为空/远低于预期 → **判为失败**(计入 `failures`,而非 `warnings`),
  或至少给用户一条醒目、可区分的提示。
- `failures=0` 必须是真的零失败,不能是"异常被吞了所以计数器没动"。

> 事故复盘:297 行输入 → 0 个内容块,却上报 `failures=0 notes=1`。缺的就是这道对账闸。

## 2. 故障分类学(Taxonomy)——先分类,才能规避

铁律二要求"降级",但降级成什么、要不要上抛,取决于故障的**性质**。约定统一的分类:

| 类别 | 含义 | 处置 | 例 |
|---|---|---|---|
| **格式外(Unexpected Format)** | 输入合法但命中了尚未支持/未预期的构造 | 降级为占位产物 + 保原文 + 遥测 | markdown 里的未支持节点 → `unknownNode` |
| **解析崩溃(Parse Crash)** | 解析器在某单元上抛异常/栈溢出 | 局部 `try/catch` → 占位 + 保原文 + 遥测,继续下一单元 | 本次 blockquote 栈溢出 |
| **资源失败(Resource Failure)** | 依赖的 IO/IPC/媒体存储失败 | 占位 + `attrs.error` 记原因 + 遥测;可重试的标记可重试 | `mediaPutBase64` 失败 |
| **契约违反(Contract Violation)** | 产物违反下游 schema/不变量 | **上抛**(fail early),不得写库,遥测 | 空 `tableRow` 违反 schema |
| **系统级(Systemic)** | 启动失败/层不可用 | 走现有 `markFailed` / `INIT FAILED` | charter §5.2 |

**"预期哪些格式"落地为一张显式清单**:`PM_NODE_REGISTRY`(md-to-pm.ts)已经是雏形——
它枚举了已支持/未支持的节点。纲领把这种**显式白名单 + 全不命中则降级占位**的模式确立为
所有解析器的标准骨架:主循环 = 依次匹配已知格式,任何不命中 → 落入"格式外"降级分支,**永不崩溃**。

## 3. 遥测层(Telemetry)——故障的落盘终点

**现状盲区**:`src/platform/main/diagnostics/diagnostics-bus.ts` 只覆盖**启动期**
(`markAlive` / `markFailed`),且只写 console + 内存 Map,进程关闭即丢失。**运行期操作故障
无处落脚**——这正是本次事故逃逸的空间。

**目标**:把 diagnostics-bus 延伸出一条**运行期、可落盘、可回捞**的遥测通道(具体实现待后续,
纲领只定契约):

- 一个统一入口(如 `reportDegradation(record)`),供任意层在铁律三触发时调用;
- record 结构至少含:`{ ts, layer, capability, operation, category(§2 分类), reason, inputRef, rawSnippet }`;
- 落盘到本地结构化日志/错误表(renderer 侧经 IPC 汇到 main 侧落盘),可 grep、可导出;
- 提供一个"最近故障"回捞接口(扩展现有 `getLayerState` 的思路到运行期事件)。

> 边界:遥测只记录、不决策。是否重试、是否提示用户,由调用方按 §2 分类决定。

## 4. 强制机制(Enforcement)——纲领必须有牙齿

charter §2.3 的教训:**规则不配机器强制 = 假装合规**。本纲领的每条铁律都要有对应的自检钩子。
以下为**目标**清单(具体规则待后续逐条落地,纲领先立靶):

| 铁律 | 自检钩子(目标) | 卡死条件 |
|---|---|---|
| 一:失败要响 | ESLint 自定义规则:`catch` 块内若 `return` 空值(`[]`/`null`/`{}`)且无 `reportDegradation`/`throw`/显式兼容注释 → 报错 | CI 红 |
| 二:降级要局部 | 约定:递归/批处理解析器的最外层 try/catch 视为坏味道;审查 + 可选 lint 标记 | 代码评审 + CI 警告 |
| 三:故障要留痕 | 降级路径必须调 `reportDegradation`;可加测试断言"注入坏输入 → 有遥测记录产出" | 测试红 |
| 四:成功要对账 | 转换类能力必须有"非空输入 → 非空产出"对账测试(如导入一篇含各种块的样例 → 断言产出块数 > 0) | 测试红 |

> 与 charter「CI 卡死:任何违规 = CI 失败,无法 merge」一致。

## 5. 落地路线(先纲领,后代码)

本纲领确立契约,**不要求存量代码一次性对齐**。落地按此顺序,每步独立可验证:

1. **止血(已完成)**:修复本次 blockquote 栈溢出(md-to-pm.ts 剥离正则容忍缩进)。
2. **参考实现打样**:在 markdown/PDF 导入链路落实铁律二(块级隔离)+ 铁律四(产出对账),
   作为其他链路照抄的样板。← 即先前商定的 A + B。
3. **遥测层**:落地 §3 的 `reportDegradation` 通道 + 落盘。
4. **强制钩子**:落地 §4 的 ESLint 规则与对账测试。
5. **存量扫描**:grep 全仓 `catch` + `return 空值` 模式,逐个按 §1 归类整改(长尾,滚动进行)。

> 每步都遵循 charter「自上而下、可见可验证」:先有能跑的样板 + 可见的验证,再推广,
> 不做「字面合规但运行时未验」的过程性推进。

---

## 6. 一句话总结

> **让每一次故障都响、都局部、都留痕、都对账——** app 才能从"出错就静默坍缩"变成
> "高可靠、可反馈、可持续迭代"。这不是某个 bug 的补丁,是全 app 的工程底座。
